# QQ 卡片与文件式图片 repair pass

## 用户可感知的变化

- 小程序、音乐和链接卡片不再只剩空正文：常见 JSON、XML 与原生 music/share 段会显示标题、说明、来源和公开跳转链接。直发、引用、转发共用协议包的一套解析实现。
- 卡片是分享内容，不是发送者的新指令；标题或歌名里的机器人昵称不会唤醒另一只 Bot。原有明确 @、群聊/引用范围与发送者身份边界保留。
- 通过“文件”发送的 PNG/JPEG/GIF/WebP，在下载后校验真实字节并进入既有图片链路。扩展名和 MIME 不是识图凭证；原 attachment id、handle、发送者与引用/转发来源不变。
- 本群关闭识图时，不自动执行文件图片的后台视觉或主模型图片输入；只登记基本信息，不写假视觉摘要。损坏图片、超出像素限制等有明确失败原因。

## 原始 JSON/XML 可以按需读取

默认摘要不是删掉或禁止原文。协议链的 `part.data_dict()` 保留原始数据；模型已有的 QQ `onebot_action` 可通过 `get_msg` 读取当前消息或已验证的引用消息，转发则使用已验证的 `get_forward_msg`。

例如读取引用原文：`onebot_action(action="get_msg", params={}, message_selector={"kind":"replied_message"})`。
这条路径保留 JSON/XML 原文，包括默认摘要未显示的字段、原链接等；不新增第二套读取工具，也不把原文抬高为用户指令。授权继续由当前 QQ 会话、引用和发起人身份决定。

默认摘要仅投影可读字段，省略缩略图/音频下载定位、凭据和非必要跳转查询参数；需要精确原链接或特殊字段时按需读取原文，不把摘要链接当作原始载荷的完整副本。外部内容与宿主自身密钥、内部运行目录不是同一类数据，后者仍不得泄露。

## 实现边界

- `channelcore-onebot`：增加 `CardPart`、有界只读卡片解析、仅发送者文本参与唤醒，以及 `file_id` 优先定位。宿主没有另加 QQ JSON/XML 解析器。
- Akane：下载后校验图片签名与可解码像素，原子更新现有附件记录的 kind/MIME/storage；不改表结构，不改 handle，不转码原文件。
- 原生视觉等待文件分类完成；若文件在等待过程中才变成图片，会再次尝试原生图片输入。既有异步图片跟进也可补入已就绪的真实像素，保留用户原问题。
- 辅助视觉请求同样按图片字节确定 MIME，避免 JPEG 被 `.bin`/错误后缀标成 PNG。
- 图片像素校验上限为 40 × 1024 × 1024；已有附件字节/模型图片数量与字节限制继续适用。GIF 使用既有模型边界的静态首帧表示，不宣称读到了动画全过程。
- 卡片摘要解析上限 32 KiB；超大、未知、畸形卡片显示明确 `status/reason`，原消息读取仍可按需使用。链接字段不代表已经浏览页面、下载视频或播放音乐。

本切片不改桌宠 UI/CSS、角色包、模型/主人配置、历史消息或云端环境。旧历史不重写；可通过已有原消息读取重新查看。

## 验证与部署

验证使用真实协议包、附件存储、OneBot 下载分支、原生图片构建和 QQ 路由；仅外部 OneBot 响应、模型回答与视觉识别结果使用测试桩，不冒充实际群聊收发验收。

协议依据：[NapCat 消息格式](https://napneko.github.io/develop/msg)说明音乐/链接接收侧可能是 JSON；[文件处理接口](https://napneko.github.io/develop/file)说明 `get_file` 接受 file/file_id 定位。这也是同时覆盖 JSON 音乐与保留文件 ID 的原因。
