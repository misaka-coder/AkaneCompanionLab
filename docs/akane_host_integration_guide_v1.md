# Akane Host Integration Guide v1

> 给外部宿主、未来协作者、以及需要把 Akane 接到新入口的人看的最小接入说明。
>
> 这不是内部实现说明，而是“宿主至少要遵守什么，才能让模型表现不被接坏”。

---

## 这份文档解决什么

Akane 的核心不是“后端功能有多少”，而是**模型最终看见了什么、能不能继续正确行动、用户最终感受到了什么**。

因此，接入宿主时不要先问“Akane 内部有多少模块”，而要先确认三件事：

1. 这轮输入是否稳定、可复现、可缓存；
2. 工具调用、工具结果、记忆投影是否按顺序进入模型；
3. 最终回复是否把真实状态正确渲染给用户。

如果这三件事接对了，宿主实现可以相对轻；如果这三件事接歪了，代码再多也没用。

---

## 最小接入原则

### 1) 先保证稳定契约，再谈功能扩展

宿主最少要稳定住：

- `session_id` / `profile_user_id` / `character_pack_id` 等会话身份；
- 时区和时间戳；
- 角色/人设/当前模式；
- 工具注册名与参数契约；
- 最终回复的结构化字段；
- 工具结果是否需要再次展开。

不要在每轮请求里随意改这些字段的形状或语义，否则缓存、记忆和工具历史都会变得不稳定。

### 2) 模型可见内容优先于内部复杂度

内部模块可以复杂，但最终要落到模型面前的只有几类东西：

- 当前 prompt；
- 可用工具；
- 记忆/摘要/卡片；
- 工具调用轨迹；
- 工具结果；
- 最终回复。

宿主的任务不是把这些都做得“看起来很高级”，而是把它们组织得**清楚、可归属、可展开、可追踪**。

### 3) 长证据卡片化，短反馈直接保留

不是所有工具结果都应该压成卡片。

- 长、重复、可延后查看的证据：适合卡片化，并保留稳定 `id` / 时间 / 归属 / 展开路径；
- 短小、即时、对操作有用的结果：适合直接结构化返回，例如生成文件、播放器切换、发送状态、当前进度。

不要为了省 token，把模型完成当前判断需要的信息改成空壳。

---

## 宿主必须负责什么

### 输入层

宿主必须把真实输入整理成稳定 turn payload，至少包括：

- 用户消息；
- 会话身份；
- 角色身份；
- 当前模式；
- 时区/时间；
- 图片、附件或其它多模态输入；
- 工具前置状态；
- 需要进入记忆系统的额外上下文。

### 回合层

宿主必须保证：

- 同一轮内的工具调用顺序可追踪；
- 工具结果在模型看见前后的一致性可解释；
- 同一轮结束前不要把稳定前缀随意改写；
- 流式与非流式在业务上是一致的两种 transport，而不是两套语义。

### 输出层

宿主必须保留：

- 结构化回复字段；
- 工具事件；
- 失败原因；
- `final_ui` 与 `final` 的区别；
- 任何需要继续展开的 handle / id / source。

`final_ui` 是给界面看的最小交付，`final` 是给调试与审计保留的完整交付。不要把两者混成一个字段，也不要把调试字段塞进用户展示面。

---

## 宿主最容易接错的地方

1. **把流式和非流式当成两套业务**

   它们只是两种 transport，核心语义必须共用。

2. **工具结果直接丢弃**

   工具轨迹是模型继续推理的重要证据，不要只保留最终一句话。

3. **每轮都改 prompt 结构**

   这会破坏缓存命中，也会让模型判断不稳定。

4. **用一堆隐形规则替代明确字段**

   能结构化就结构化；能给 id 就给 id；能说明状态就说明状态。

5. **把短反馈也压成卡片**

   这会让用户看不见立即有用的信息，反而损失体验。

6. **把宿主内部位置和模型执行所需路径混为一谈**

   密钥以及数据库、缓存、run log、backing file 等宿主内部物理位置不得进入
   prompt、snapshot 或公开日志；但用户提供的路径、工具命令参数、工作区文件和
   工具发现的操作路径是完成任务所需证据，必须保留原样，不能用 `[local_path]`
   一类标记破坏其可执行语义。

## 最小可用集

如果你只想做一个“能接上 Akane”的宿主，先确保下面几件事成立：

1. 能构造稳定的 turn payload；
2. 能接收并转发工具调用；
3. 能区分工具结果和最终回复；
4. 能把结构化最终结果正确渲染给用户；
5. 能保留可展开证据；
6. 能在失败时返回结构化原因，而不是静默吞掉。

只要这 6 件事都对，宿主就已经在正确轨道上了。
