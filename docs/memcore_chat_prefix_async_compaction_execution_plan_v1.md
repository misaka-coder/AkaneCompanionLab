# MemCore 聊天前缀复用与异步压缩执行单 V1

日期：2026-10-11。

状态：实现与隔离验收完成；2026-10-11 已按用户授权提交、启用新模式并重启，后端、桌宠及 QQ 连通验收通过。第 13 节记录实现、配置和部署验收。

## 1. 目标与范围

增加一种可选的记忆整理方式：由宿主提供实际聊天请求的快照，MemCore 选择来源范围，在该请求的原有前缀后追加整理指令，使用当时的聊天模型生成记忆。整理在后台运行，普通聊天和工具执行继续使用一致的旧上下文，结果在后续请求边界生效。

本轮同时解决长任务尚未最终交付时的上下文管理。达到阈值先 fork 当前有效的已配对旧段生成工作摘要；成功后一次应用卡片与摘要，新增步骤保留在其后。选择完整保留时，直接以工作摘要接替旧段，不先收成卡片。

首版统一 fork 当前有效上下文。里面已有卡片就按卡片理解，里面是完整调用与结果就按完整内容理解，不另外比较或挑选投影前后的两套输入。沿用现有卡片内容，卡片结论增强留待真实使用出现问题后单独处理。

长期记忆生成也已接入该模式，输入来源仍然是选定的阶段摘要；不适合复用当前前缀时沿用独立请求。

沿用 MemCore 的摘要字段、来源关系、检索、后台维护和提交机制。保留现有独立摘要请求模式；不另建一套宿主记忆库，不增加由模型自行删历史的工具。QQ 队列、主人干预与被动消息批量处理另按审计处理，不并入本执行单。

## 2. 已核实的实现与基线

| 当前实现 | 本轮影响 |
| --- | --- |
| 未单独配置摘要模型时，`call_memcore_json()` 可以跟随会话聊天模型 | 这只决定用哪个模型，不代表请求已复用聊天前缀 |
| `memcore_integration/adapters.py` 传入独立的 `system_prompt` / `user_prompt`，使用 `memcore:<task_type>` 缓存标识 | 新模式需要复用实际聊天请求与对应缓存身份，不能仅改模型名 |
| SDK 的 `LLMRequest` 目前接收摘要提示、任务类型与扩展信息 | 需要受支持的、可选的请求上下文接口，不能让宿主直接改 SDK 私有流程 |
| raw 压缩按旧的完整终态轮选择，工具参数与结果结算也在完成轮后执行 | 开放长任务需要增加分段能力，不能简单去掉终态检查 |
| `full_until_raw_compaction` 不建立终局工具卡片；另有结束后收起结果/参数的策略 | 新链路沿用所选历史策略，完整保留时不能因上下文压力偷偷改用卡片 |
| 阶段摘要、代码生成的操作摘要和来源分配一起提交 | 新请求方式继续使用这条写链，操作证据不因切换模式而消失 |
| 长期记忆从选定阶段摘要构造独立的 `TaskType.SEMANTIC` 请求 | 前缀复用需要判断这些来源是否已出现在实际聊天请求里 |
| 已有后台压缩允许摘要等待期间追加消息 | 复用现有调度与并发能力，主要补齐请求输入、分段选择及生效边界 |

## 4. 聊天前缀复用：实际输入是什么

### 4.1 请求形状

以下数值仅用于解释，表示 raw 历史的近似 token，不包含系统、工具、已有记忆和新摘要：

```text
普通聊天请求：
  原有系统/工具/已有记忆 → 原始历史 A≈32000 → 近期历史 B≈16000

后台阶段摘要请求：
  相同前缀             → 相同历史 A        → 本次整理指令

成功启用后的聊天上下文：
  原有背景 → 摘要(A) → 保留的 B → 整理期间新增的 C
```

截掉 B 不会改变截点之前的前缀；能够争取缓存的是该相同部分。A 的末尾追加整理指令，不在 A 的正文里插入起止标记，不在尾部再复制一份 A。

图中顺序是示意。实现必须保留当前客户端及 provider 的真实顺序，不能为迁就示意图重排已有提示、记忆或工具。

### 4.2 捕获与调用

1. 从正常聊天请求构建链取得当前有效上下文的不可变快照，覆盖同步、流式和工具续轮。包含实际模型/路由、系统块、工具声明、历史投影、缓存身份及影响前缀的 provider 选项。有同版本的已准备/已发送快照时直接复用；刚投影后的上下文按正常链路构建，不退回投影前的旧快照，也不发额外请求预热缓存。
2. 使用内部来源映射，把 MemCore 选出的来源范围对应到快照的消息或内容块边界。映射包含 source coverage 与版本，不作为新文本喂给模型。
3. 基于该快照截取到 A 的结束位置，追加一份简短的整理指令。切片必须保持协议合法；同一原生调用批次不能只留下部分结果。
4. 走捕获时的实际聊天模型和路由。不能后台临时读取一个已切换的全局模型，再把旧请求误当作同模型缓存；子代理使用其自身会话的请求与模型。
5. 保留原有工具声明以争取前缀复用，整理任务不执行工具。使用 provider 支持的调用控制，并验证 `tool_choice` 等控制是否影响其缓存；意外工具输出按整理失败处理，不能执行其中的调用。
6. 生成结果只交给 MemCore 的 JSON 校验与提交流程，不经过用户最终回复的 UI、QQ、语音或角色状态副作用。

快照主要为进程内短期引用，不重复落库存储整套系统提示、凭据和图片正文。持久状态仅保存必要的来源、版本、模式及失败原因；重启丢失未完成请求时，来源仍保留，可重取快照重试。

捕获点必须核对 provider 转换后的实际内容。只比较宿主转换前的字符串不足以证明 Anthropic、Responses 或 Gemini 原生请求保持相同前缀；转换、工具净化和签名续接仍走现有适配器。

卡片路径 fork 的调用与结果已经是有效投影，完整保留路径 fork 的则是原有完整历史。两者都直接供模型理解，不另行导出、重渲染或重复包装一份操作正文。

### 4.3 整理指令与输出结构

由代码选范围和来源，模型负责提炼该范围的内容。指令只包含：本次任务、目标范围、背景与来源的区别、必需的记忆字段及整理重点。

- 原有阶段摘要与长期记忆是背景参考，不能算成本批新增来源。
- 前缀中已有记忆随原请求保留，尾部不再追加一份参考正文；现有独立模式继续至多参考紧邻的一条聊天摘要，不恢复多条或操作摘要参考。
- 普通对话保留事件、人物归属、关系与时间依据，避免只有工具清单。
- 开发任务保留目标、用户修正、实际完成项、验证结果、失败与待办、下一步及必要证据 ID。
- 用户要求、模型猜测和已验证结果必须分清；“打算修复”不能写成“已经修好”。
- 继续使用现有阶段摘要 JSON 字段和检索元数据，目录字段与来源关系仍由 MemCore 管理。

“已有原始历史”指由当前快照的来源映射限定的 A；不要让模型凭日期或 token 数猜范围。整理指令位于截取后的末尾，必要时引用现有可见锚点，不新增遍布历史的范围标签。

要验证当前客户端最终回复格式与记忆 JSON 的指令优先级。若确有冲突，可在稳定提示里增加一次极短的适用条件，说明宿主内部记忆整理使用指定的记忆格式；不把完整摘要规则放进每轮聊天，不要求生成 `text/say/style` 等用户回复字段。尾部不重复整套人格、工具规则和聊天输出示例。

## 5. 来源选择与窗口

继续由 MemCore 根据 token 计数、比例和完整关系单元选择旧区间。当前运行配置核查为 raw 触发值 48000、批次比例 0.67，对应计划整理量约 32160；这不是硬切片长度。

1. 不另设一套与现有比例冲突的最小窗口配置。16k/48k 的讨论示例先映射到现有触发值与批次比例，确需改变配置模型时另行确认。
2. 普通聊天保留近期尾部，切点沿用完整消息与配对边界。任务结束后若投影仍超量，应按当前体积与目标保留窗口一次选足旧范围，不能固定只整理约 3.2 万，也不能为保护“最近一轮”留下整轮四五万 token，再等下一条消息触发第二批。特别大的已结束任务允许整体纳入，实际尾部可少于目标；来源超出单次合法请求预算时才按必要边界分批。
3. 普通 raw 触发值、计划整理量和保留窗口只按已结束轮的当前有效投影计算；当前开放轮的完整工具调用与结果不参与该判断。终局先投影再判断；选择完整保留策略时按结束后的完整投影计数。完整工具体积仍参与真实请求预算和第 7 节的工作压缩。
4. 新摘要本身、已有记忆、系统及工具也占上下文。保留 raw≈16k 不代表整份请求只有 16k。
5. 同一来源不能同时落入聊天阶段摘要和另一份重复聊天摘要；操作摘要继续按原有分区由代码生成。

不把完整聊天窗口带给摘要模型再让它自行寻找“前 32000 token”。V1 优先截取合法旧前缀，以减少额外输入和范围歧义。缺少可用快照、快照无法对应合法切点或协议不支持复用时，使用现有独立摘要请求，并记录原因；不能重建一份近似聊天请求后宣称其已缓存。

目标保留量优先由既有触发值与比例推导，不新增一套最低窗口配置。例如 48000 与 0.67 对应约 15840 的目标 raw 尾部；当前 raw 超量较多时，计划整理量按当前 raw 减去该目标计算，并按合法边界调整，不保证精确保留这个数字。

## 6. 后台执行与生效

```text
已结束轮的有效历史达到普通 raw 阈值
  → 选定来源并冻结请求快照
  → 后台生成摘要（不持有共享数据库锁等待网络）
  → 校验选定来源并原子提交
  → 后续模型请求读取新版本上下文
```

摘要等待期间，新用户输入、工具调用和结果仍可追加。已发出请求继续使用自己的旧快照，不能在其执行中修改消息数组。

结果就绪后，在上下文读取/构造的安全边界生效。A 轮终局投影后独立达到普通阈值并启动摘要，结果可以在 B 轮工具执行期间的下一请求边界生效；不等 B 轮终局或整个会话空闲。B 轮开放工具正文不能提前推动普通 raw 压缩 A，也不能改变 A 的计划保留量；B 自己的工作压缩仍走第 7 节。优先利用现有原子提交和一致性读取实现，不另造一套持久的“待激活”任务框架。

提交校验聚焦选定来源的存在性、版本、投影覆盖与归属。仅在尾部追加了 B/C 不应让 A 自动失效；被选来源确实修改、删除或已被另一批消费时，继续拒绝过期提交。不能为允许并发而删除全部 generation / version 校验。

同一来源的重复调度复用已有合并与幂等机制。失败、取消、格式错误或来源冲突均保留原始数据和明确原因；不提交 fallback 空摘要。已有有限重试可沿用，不在模型失败时持续发请求阻塞聊天。

重启后不依赖旧的进程内请求句柄，也不重放工具。已提交记忆照常恢复，尚未提交的来源仍未消费，按现有维护流程重试。

### 6.1 软阈值与真实上限

后台整理需要在真实请求上限前留出空间，覆盖摘要生成期间可能追加的工具结果。沿用现有预算机制核对完整请求，不只看 raw 触发值。

若下一次请求实际已经无法容纳，卡片路径可使用合格的紧凑投影；完整保留路径不自动转卡片。仍放不下时，等待正在生成的有效摘要，或按现有合法来源边界缩小整理批次；无法发送时按明确失败路径返回状态。不能承诺在真正超出模型窗口时还始终无等待，也不能悄悄丢弃当前任务和用户输入。

## 7. 长任务中途整理

### 7.1 卡片路径：先总结，再批量投影

工具轮增加可配置的上下文软触发值，按开放轮当前有效投影计数，已有卡片按卡片大小计数；完整请求另由宿主预算核对。20 万 token 是大窗口模型的默认软阈值，具体使用须留出系统、工具、输出及后续结果的空间，并早于真实上限。两条路径共用触发判断，触发后按所选历史策略处理，不为每个会话再设一套阈值。

卡片路径在模型请求边界达到软阈值时，处理旧的已配对工具批次：

1. 先从实际请求 fork 合法旧段 A，生成工作摘要；此时不修改 A。已有卡片按卡片理解，尚未投影的调用和结果保持当时的完整形式，不额外重渲染。
2. 保留近期工作的必要内容。正在执行的后台任务必须保留可用任务 ID 与状态；不能为了收起旧记录等待所有后台任务完成。
3. 一个 assistant 消息发起多个原生调用时，以协议允许的完整批次处理。缺少对应前台工具结果的批次不能拆开收起；已返回后台任务 ID 的调用与后台实际终态是两件事。
4. 成功后复用 MemCore 的结算、投影账本和 `open_memory` 回读能力，一次提交 `卡片(A) → 工作摘要(A)`。真实执行参数和原始操作记录不变，不重新执行历史调用。
5. 新增 B 保留在其后；摘要失败或整个替换没有节省空间时保留原文。每次工作分段只生成一份摘要，不再叠加“先卡片、仍超限再摘要”的旧候选流程。

同一轮再次触发时，处理后续新增及已变旧的未投影合格批次，已冻结的卡片不重新压缩。每次处理释放足够的工作空间，避免刚落到触发值下面就反复触发；不引入固定等待或冷却时间。

不在每个工具返回后立刻改写前文。按上下文压力批量处理，减少无意义的反复缓存重建。新能力采用明确的新策略或版本，保留旧 `compact_after_terminal` / `compact_arguments_after_terminal` 的已发布含义及冻结配置。

### 7.2 完整保留路径与开放轮来源

选择 `full_until_raw_compaction` 时，达到软阈值直接 fork 当前完整上下文生成工作摘要，跳过工具卡片投影。原有完整工具调用和结果进入该请求供模型理解；当前独立摘要路径会分离工具条目，新 fork 路径不能继续在输入中把这些条目剥掉。原始证据、操作分区与来源关系仍由 MemCore 保存。

完整保留路径成功后仅用工作摘要接替 A，保留 B 和全部 SQLite 原文，不调用卡片结算；不会因压力偷偷切换工具历史策略。已完成轮的普通 raw 压缩仍走原有聊天/操作分区与阶段摘要写链。

需要 SDK 支持同一开放轮内已经稳定的旧段，而不是把整轮伪装成 completed：

- 保留原 turn_id、发言人、来源渠道及 correlation_id 关系。
- 选择与提交基于该段 entry/source coverage；后续轮尾追加不能被当成旧段变化。
- 所选条目的实际变更仍参与冲突校验。未完成轮的后续 metadata、最终回复与终态提交必须继续正常工作。
- 后续工作分段不得再次处理已经投影的 A；最终普通 raw 压缩可以依据当前有效的卡片、工作摘要和后续记录生成阶段记忆，并一次消费该轮来源。检索可见排除、完整轮读取和 summary lineage 保留原语义。
- 最近步骤、待办、未完成任务及有效回读凭据保留在新摘要和尾部，不能只剩“做过开发”。

卡片与摘要共用来源版本和提交边界，避免同一段被并行重复替换。provider 的不透明签名/续接内容不能伪造、静默删除或绕过验证；不能安全处理的内容保留，走受支持的降级方式。

### 7.3 后续审计项：完成通知正文

审计发现后台任务完成通知会携带完整测试输出和堆栈进入聊天摘要，部分开发轮的通知占摘要正文约 98%。首版 fork 使用当前有效上下文，不新增通知专用裁剪流程；本问题保留在后续独立修复项中，不作为复用前缀的前置条件。

后续若处理，复用已有任务结果证据，保留终态、必要结论、失败原因与回读凭据，避免全文重复注入。不能删掉所有通知或只留一个无意义的“完成”；不新增通知等待窗，不改变用户消息队列策略。

### 7.4 已采用的顺序与摘要位置

最后讨论已采用本节顺序，7.1、7.2 已与之对齐。不开第三套模型循环或逐工具摘要器。

达到软阈值时，先 fork 当前有效上下文，选定待收起的已配对旧段 A；尚未投影的调用和结果保持完整。主任务可以继续追加 B，后台请求只总结 A。结果就绪后，在下一次主模型请求构建边界，一次应用 A 的卡片投影与工作摘要，B 原样保留。已在途请求不修改，不等整个任务结束。

```text
fork 时：       原有背景 → A（截至选定工具批次）
结果返回时：   原有背景 → A → 新增 B
下一次请求：   原有背景 → 卡片(A) → 工作摘要(A) → B
```

建议把工作摘要固定放在其覆盖的完整配对旧段 A 之后，后面接新增 B。既然本次卡片已改写 A，首次应用时把摘要放在 A 后或 B 后，通常能复用的旧前缀相同；尾部放置的主要便利是追加接线和末尾注意力，不构成额外缓存优势。放在 A 后更清楚地表达旧段结论与后续进展，让 B 保持最新记录的位置。

摘要明确其覆盖的旧段，当时的待办不作为当前强制指令。模型结合 B 判断哪些事已经完成；B 的正常追加不使 A 失效，所选 A 的真实变更仍须校验。工作摘要只呈现一份，插入后位置与内容冻结，不随着新工具轮增长反复搬到尾部，也不在已有记忆区重复渲染。不把它当作用户指令、业务完成通知或助手最终交付。存储与来源管理沿用 MemCore，具体投影应与开放轮分段 API 一起验证，不能只在数据库写入而让工具续轮继续消费旧副本。

fork 表示复制请求上下文，与同步或异步等待是两个维度。同步时仍可由宿主发送这份内部整理请求、等待后继续主工具循环，摘要结果不走 `complete_turn`、QQ 或 TTS。无需模型主动调用总结工具，也不伪造一次工具调用来配对摘要。

建议正常预算下后台运行；接近真实请求上限时，主工具循环在下一请求边界等待同一个整理任务，后台工具继续按原机制运行。不是另发一轮同步摘要。若主任务已经最终结束，整理结果用于后续上下文，不因维护完成再次唤醒模型。

本方案在工具轮达到阈值时增加一次内部 LLM 整理请求，换取连续性；没有阈值压力的普通工具执行沿用当前行为。整理失败时保留原文，不先收起而丢掉生成交接总结的依据。

## 8. 长期记忆生成：同一原则，不同来源

原则同样成立：保留可复用的原始聊天前缀，在末尾说明本次只归并指定阶段摘要，后台生成长期记忆，成功提交后让后续聊天读取新记忆。

但不能直接假定所有阶段摘要都已缓存：

1. MemCore 仍按现有触发数量和批次选择 `source_summary_ids`，不归并 raw 原始对话，也不自动把已有长期记忆当作本批新来源。
2. 判断所选阶段摘要是否已完整出现在捕获的聊天请求中，并核对其可见文本是否足够生成原有长期记忆字段。当前聊天渲染含阶段回忆、关键事件、核心事实和记忆 ID；独立语义请求的渲染还可能包含其他目录信息，不能只比较摘要条数。
3. 目标摘要已在相同形式的前缀中时，沿用该前缀，在尾部用已有记忆 ID 明确本批目标。其他阶段摘要与旧长期记忆仅为参考，不改变它们的来源归属。
4. 刚生成、尚未发给聊天模型的摘要没有可证明的缓存；旧摘要被可见窗口排除、或必要字段未注入时，使用现有独立语义请求或补充必要输入，明确记录复用范围。不为了声称命中缓存拖入整段无关原始历史。
5. 能合法截到包含目标摘要的必要前缀时，可省掉后面的 raw 历史；若实际协议/记忆块无法安全裁切，就评估输入成本并沿用独立请求。不得在稳定区插入新的范围标记或重渲染已有摘要来凑前缀。
6. 继续保留连续来源批次检查、摘要版本校验、原子 `commit_semantic_batch`、检索元数据与语义记忆 lineage。期间新增的阶段摘要不被消费；失败时所选摘要保持原状。

已有长期记忆的强化合并沿用现有策略，不顺带改写强化算法。阶段摘要可见数量和长期归并数量也不在本轮改动；是否恰好覆盖整批目标，由运行快照判断。无需给每个会话或子代理新增一套模型配置。

## 9. 本地耗时与可观察性

优先复用当前耗时与缓存统计，补齐能够区分问题的必要边界：选择来源、取快照、模型等待、校验提交、下一请求构造。模型等待与本地处理分别记录。

缓存路由身份与统计用途分开：整理请求可复用聊天缓存身份，但以内部任务类型区分聊天、阶段摘要和长期记忆的 usage，不把后台维护算成用户聊天轮，也不为区分统计再改缓存标识。

审计中的两个 SDK 慢点需要在受维护源码中处理并验证：

- `get_previous_episodic_summary`：避免在共享 store 锁内先扫描会话大量消息，再按 JSON 来源排序；保持同一会话、来源先后与回填语义。
- 摘要提交的 projection hash 校验：缩小到选定来源与有效投影范围，不为一条新消息重新读取整个历史账本；保持必要校验。

网络调用不占共享数据库锁。请求快照与投影缓存按实际变更更新，不对每条消息处理整个数据库，不新增全库归档步骤或等待收集窗口。

普通聊天本地处理维持先前约 200–300 ms 的体验目标，实际按相同计时边界比较；不把历史只读探针的 4 秒中止界限变成生产超时，也不靠提高 worker 数遮掩慢查询。

审计只保存完成判断需要的模式、范围计数、版本/hash、原因和 usage。凭据、生产对话全文与大型操作正文不写进执行记录。

### 11.2 真实模型与缓存

在隔离会话/数据库上比较现有独立模式与新模式，不用生产群消息制造压力：

1. 先发送真实聊天请求，再基于它生成阶段摘要；比较输入 token、缓存命中/未命中、模型等待、本地耗时和有效摘要内容。
2. 覆盖常规对话与长开发任务。摘要后模型应能说清目标、做过什么、验证到哪里和下一步；抽查事实来源，不能只检查 JSON 可解析。
3. 在服务商实际支持的协议下检查回复/工具控制变化对缓存的影响。使用 provider usage，缺失缓存数据时明确记为不可确认。
4. 连续聊天以原先至少 95% 的缓存目标对比，重建轮和稳定轮分别记录；不是要求每次摘要、模型切换或压缩重建的单轮也达到 95%。
5. 长期记忆只对实际已出现在前缀里的来源评估缓存收益；新生成或未注入来源不得当作“已命中”样本。
6. 投影发生后允许该次缓存重建，核对模型输入确实缩小、后续请求稳定。普通前缀缓存通常只保证第一处改写之前的部分可复用；从改写点到尾部可能都需重算，不把未命中量仅估算为被替换的片段，也不要求刚投影的整个新前缀已在上游缓存。

相同前缀只是缓存复用的必要条件之一。路由、缓存寿命、provider 序列化与缓存粒度都会影响实际结果；本地 hash 相同不能代替计费 usage，更不能提前承诺 97% 或 98%。

## 12. 最终实施选择

1. 默认仍为 `independent`；`chat_prefix` 可显式启用，先用隔离数据库和真实 provider 验证，不自动切换全部生产会话。
2. 开启时在主模型和子代理的稳定区追加一句内部记忆契约例外。普通聊天仍用当前客户端字段，进度与工具调用格式不变；整理结果不送 QQ、桌宠或 TTS。
3. 宿主全局工作触发值默认 200000 token；SDK 默认 0 表示关闭。实际请求预算可以降低本次快照的可用工作额度，不修改全局/其他会话配置；不增加逐会话设置或固定工具个数。
4. 长期记忆只在选中的阶段摘要完整出现在捕获前缀且形态相符时复用；刚生成或隐藏来源独立调用。没有为提高命中率扩大可见窗口。
5. 工具轮使用“先工作总结，后提交投影”的顺序，工作摘要固定在 A 后；真正装不下下一请求时等待同一个维护 Future，不重复请求摘要。

配置回退只关闭未来的前缀整理与工作分段。已提交的分段仍按新包正常读取；schema 11 数据库不通过降级旧包回滚。
