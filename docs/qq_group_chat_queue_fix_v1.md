# 群聊普通回复期间的新消息排队修复

日期：2026-10-13。

## 问题与证据

另一位群友的普通聊天还没有回复时，主人发出的新问题会被当成当前任务的干预输入，没有独立请求和答复机会。这是宿主的输入分流问题。

只读核对当前实例：10 月 13 日 11:49:34 接收的队列项已 `committed`，对应输入以 `steer_inbox_*` 来源写入同一个 MemCore 轮；该轮有两条用户输入、一条助手回复，没有工具调用或结果。消息留在数据库中，但被合并处理。

原先 `QQTurnRunner._run_admitted` 无论普通聊天还是工具任务都会尝试 `offer_steer`，并允许主人跨发起者干预。`committed` 只表示输入被当前轮接收，不保证每个问题都有答复。

## 修复后的分流

| 当前会话状态 | 新的应答消息怎样处理 |
| --- | --- |
| 普通群聊，尚未实际执行工具 | 按既有 FIFO 排队，独立发起请求；主人、原发起者和其他群友都适用 |
| 当前轮已经进入工具执行，仍未收尾 | 主人或任务发起者可干预当前任务；其他群友继续排队 |
| 当前轮进入终局收尾 | 新消息排队，留给下一轮处理 |
| 被动记录、主动搭话或插件事件 | 保留原有不可干预／应答消息优先规则 |

这里的“应答消息”沿用既有 QQ 接收规则，例如明确 @ 机器人。没有 @ 的普通群消息仍走被动记忆规则。

不从文字猜测是否为开发任务，不要求模型新增输出字段。工具状态来自同步、流式共用的 `execute_tool_round`：开始执行真实工具批次前，以当前轮 token 设置内存状态。该状态在工具批次之间保持，下一轮重新置空；旧 token 不能改变新轮。

## 接线与边界

- `turn_coordination.py`：新增当前轮 `tools_started` 状态及 `mark_tool_activity`；`offer_steer` 的工具前提检查与终局／权限检查在同一锁内完成。
- `engine_services/turn_tools.py`：真实工具执行入口设置状态；普通生成、无效工具决策和初始检索不设置状态。
- `qq_turn_runtime.py`：仅群聊的隐式插话要求已有工具活动。`busy_chat` 使用既有持久队列释放领取、保留原顺序并唤醒处理的路径，也覆盖内存队列。

私聊和显式桌宠干预入口的行为保留。没有新增队列、等待窗口、配置、数据库迁移或模型提示；普通聊天不再因为插话丢弃当前回复并重新生成。队列仍按到达顺序追加，不将新输入插回历史前缀。

## 验证与部署

修复前，两个通过真实 QQ HTTP 路由、临时 SQLite 收件箱和受控模型流的复现用例均失败：主人新问题返回 `steer_accepted_without_visible_ack`，没有独立排队。

修复后覆盖：直接普通回复、从 FIFO 取出的普通回复、多发起者顺序、同一发起者后续问题、OneBot 重发去重、工具任务主人干预、工具任务收尾插话，以及同步／流式真实工具入口的状态接线。相关队列失败、恢复和场景隔离用例一并复验。

共 180 项相关用例通过：核心接线、QQ 入站与协调器 59 项，收件箱、队列恢复、QQ 场景隔离、插件、主动搭话和私人记忆共享 121 项。修改的 Python 文件编译、Ruff 与 `git diff --check` 通过。

验证阶段未向 QQ 发送测试消息，没有修改生产记忆。修复通过当前实例的后端重启加载；实际 QQ 界面的答复体验需部署后复验。
