# Akane 扩展生态与插件生命周期 V1

插件贡献类型、事件投递、Hook、多后台服务、AI 自开发和市场的分阶段实施细节见
`docs/plugin_contribution_event_market_plan_v1.md`。本文件继续作为扩展生态的总原则，
实施计划不得另造 PluginHost、消息链、MemCore 或能力执行权威。

## 1. 目标体验

用户只需要面对一个“扩展中心”，但系统必须保留三种扩展的真实语义：

- Skill 是模型执行知识，发布成功后从下一轮开始可见；
- MCP 是外部工具连接，配置并探测成功后可以按需加载；
- Plugin 是可信宿主代码，负责能力、QQ 命令、后台任务等宿主级扩展。

安装、更新和重载必须报告真实状态。候选版本失败时继续使用 last-good；不得用
“已发送”“已生效”或假进度掩盖尚未完成的动作。插件目录或稳定提示只有在扩展
代次真正变化时才更新一次，不能在每次请求中动态改写稳定前缀。

最终的热重载体验是：候选插件在隔离运行时完成加载、配置、能力枚举和健康检查，
成功后切换能力快照；当前模型回合继续使用开始时冻结的旧快照，下一轮看到新能力；
旧调用完成后旧代退出。失败时旧代继续运行，并向用户显示可执行的失败原因。

## 2. 唯一权威

| 领域 | 唯一权威 | 不负责 |
| --- | --- | --- |
| 消息链 | channelcore-onebot | 记忆、人格、插件生命周期 |
| 上下文与工具轨迹 | MemCore | 插件发现、工具执行、权限审批 |
| 能力语义 | CapCore | 具体执行、配置持久化、UI |
| 插件生命周期 | PluginGenerationRuntime | 直接修改 MemCore、动态改写每轮提示词 |
| 工具执行 | Engine / ExecutorBroker | 插件安装与市场分发 |
| 市场 | Extension Catalog | 插件运行、权限判断、提示词拼接 |

插件能力进入 Engine 后与原生工具、MCP 使用同一条执行与 MemCore 记录链路。插件不
获得 MemCore、Engine、QQ Gateway 或 system prompt 的任意引用；宿主只提供明确的
注册器与端口。

## 3. 权限边界

当前 Python 插件运行在独立 worker 进程中，宿主只持有版本化协议客户端和不可变贡献快照。
进程隔离提供生命周期与故障边界，不等于恶意代码安全沙箱；manifest 权限表示宿主允许插件
使用哪些端口。V1 只接收用户信任的插件包，安装或新增敏感权限必须由主人确认。

## 4. 生命周期

### 4.1 当前可安全提供

- 查看启动快照、插件版本、能力和结构化错误；
- 由一个统一管理服务列出、持久启用或停用当前实例已配置的插件；
- 模型工具与管理 API 共用同一服务，不各自维护插件状态；
- 对当前插件运行时代次执行受控重建；
- 重启时拒绝新调用，等待在途调用到达有界终点；
- 先停止后台任务，再逆序关闭适配器；
- 在隔离候选代中重新发现、审计、注册并健康检查已安装插件；
- 候选完整就绪后原子切换，Python 模块缓存不会跨 worker 代次复用。

插件启用状态由“实例声明默认值 + 实例目录中的原子 overlay”共同形成。变更先让候选
选择通过完整候选代生命周期并达到目标状态，再写入 overlay；候选失败或持久化
失败时恢复上一份选择。不存在只在内存中生效的 enable/disable 开关，因此管理 API、
模型工具和进程重启后看到的是同一份状态。

管理服务默认不设置整次操作的固定时长上限。插件健康检查、在途调用、后台任务停止
和适配器关闭仍由各自生命周期边界负责反馈；部署方可显式设置管理总超时，但默认不
因为插件数量或正常排空时间把一次有效变更截断。

管理服务在安装、启停、更新和回滚时构建完整插件候选代，并在就绪后原子接替旧代，
不重启 Bot 进程。调用方不需要手工串联 publish、enable、restart 或 reconcile；市场
搜索和下载尚未完成时不会返回假成功。

### 4.2 无感热重载

独立 worker 中的 PluginHost 提供真正的运行代次：

1. 市场或本地包下载到 staging；
2. 校验包、API 版本、配置和权限差异；
3. 候选运行时加载插件并完成健康检查；
4. 发布新的不可变能力快照；
5. 下一模型回合使用新快照；
6. 旧代排空在途调用后退出；
7. 任一步失败都保留旧代。

不要使用 `importlib.reload` 拼装一个无法保证清理线程、全局对象和原生依赖的伪热
重载。进程间协议只传递 JSON 可表达的 manifest、调用、结果、事件和状态。

## 5. 插件贡献

插件至少贡献一种真实功能即可，不应被强制要求注册模型能力：

- CapCore capability adapter；
- QQ 命令；
- 消息或平台事件处理器；
- 后台任务；
- 稳定启动提示块；
- 随插件发布的 Skill。

当前宿主以注册后的真实贡献为准：Capability、QQ 命令、事件处理器、后台任务、稳定提示块、Skill 任一
即可激活；完全没有运行时贡献的空插件会收到 `plugin_registered_no_contributions`。
辅助权限不算独立贡献，例如只申请存储目录而不注册任何功能仍会被拒绝。QQ 命令、
事件处理器、后台任务和稳定提示块不需要为了通过启动而虚构 Capability 或声明网络读取权限。
Capability 也按真实效果声明：纯计算可以只有 `capability.prompt.invoke`，读取网络再声明
`network.read`，读写插件隔离状态使用 `plugin_state + storage.write`。宿主核对已知权限与效果，
但不把今天已知的效果名称做成未来插件的固定白名单；中高风险仍必须由 CapCore 要求确认。

Capability 调用默认没有统一的固定时长上限；用户取消和任务取消仍会沿调用链传播。
部署方确有资源边界时可以显式设置调用超时，届时超时原因会结构化返回。健康检查和
能力枚举属于启动探测，仍保持有界，避免一个损坏插件卡死整个宿主启动。

`/admin/plugins/status` 与 `manage_extension list` 会公开当前运行契约，包括：每插件
最多 16 个 Adapter、64 个 Capability、32 条 QQ 命令、8 个稳定提示块，单提示块
16,000 字符、合计 32,000 字符，以及各生命周期步骤实际采用的超时；这些边界不再
只藏在实现常量里。

稳定提示块只在扩展代次变化时进入稳定前缀。常规使用说明优先放入工具描述或 Skill，
避免插件以事件钩子在每轮任意修改 system prompt。

随包 Skill 通过 `skill.contribute + add_skill()` 事务式注册，并进入现有的按需 Skill 目录；
PluginHost 只发布当前活动代的只读根快照。停用插件后下一次请求不再看见该 Skill，启用或升级
也不把文件复制进 managed 目录。目录仍只常驻名称和 description，完整正文与资源仍由
`load_skill` 按需读取，因此插件增加 Skill 不会把整份操作手册塞进缓存前缀。

## 6. 扩展市场

市场是目录与分发层，不是第二个 PluginHost。第一版只需要：

- 静态索引或 Git 仓库源；
- 插件 ID、作者、版本、API 兼容范围、包哈希和权限说明；
- staging 下载、校验、安装、更新与卸载；
- 更新失败不覆盖现有版本；
- 本地包与市场包使用同一安装入口；
- 真实错误和 last-good 状态。

第一版不做账号体系、评分推荐、自动更新、复杂依赖求解和任意源码在线编译。

## 7. 多语言演进

Python 继续负责模型、消息和工具编排。CPU 密集或需要强隔离的模块通过 stdio、
JSON-RPC 或 localhost 协议独立运行，可以逐步替换为 Rust、C#、Go 或其他语言。

优先适合替换的模块包括插件运行时、媒体处理、向量索引、文件扫描和浏览器执行器。
替换前先冻结 wire schema、错误语义和黑盒测试；不为尚未出现的性能问题提前拆服务。

## 8. 分阶段验收

1. 已安装插件运行时代次可受控重建，状态和失败原因真实；
2. 启停获得持久配置权威，控制中心与重启后状态一致；
3. 扩展中心管理 Skill、MCP 和 Plugin，但显示各自真实生效方式；
4. 市场完成可靠分发，不参与运行；
5. 独立 worker PluginHost 已实现 last-good 无感热切换；
6. 至少两个真实社区插件通过升级失败、长调用、后台任务和权限变化验收。
