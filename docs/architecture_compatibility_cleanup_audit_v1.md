# 兼容逻辑与架构清理审查

日期：2026-10-13。范围：当前工作区的启动、配置、控制中心动作、记忆入库与调度、存储兼容、插件续答及桌面状态读取。

本轮继续检查代码和真实调用方。结论是：可以删除无人执行的旧入口与空调度，但仍在读取历史数据、适配模型协议或承接当前启动方式的兼容，需要按用途收敛。文件名含 `legacy`、版本号较早、测试中仍有引用，均不足以单独决定保留或删除。

前一轮的前后端入口对应、小屋会话/养成接线及聚合快照问题见 [前端与后端接线审查](frontend_backend_architecture_audit_v1.md)。本轮不重复迁移这些状态。

## 1. 本轮已清理

| 残留 | 查到的实际行为 | 本轮处理 |
| --- | --- | --- |
| 通用控制中心动作 API | `GET /control-center/actions` 只描述未实现的 API；`POST /control-center/actions/{id}` 固定返回 `not-implemented`，不会执行动作 | 删除这两个空入口及其专属处理、日志和占位测试。调用旧 URL 得到 404 |
| 前端动作 HTTP 兜底 | 明确的后端动作与原生桥接都不适用时，仍请求上面的空 API；旧测试甚至让这个假的通用响应把桌面动作标为成功 | 删除兜底网络请求及专属分支。没有桌面桥接的桌面动作立即返回已有不可用结果；真实任务、插件、MCP 等后端处理器保留 |
| 旧摘要调度函数 | `_schedule_summary_cycle` 的函数体只有 `pass`，用户消息、助手终局、工具轨迹和 QQ 被动入库仍有六处调用 | 删除空函数及全部调用。不改真实 MemCore 调度入口和同步维护入口 `_run_summary_cycle` |
| 假维护回执 | QQ 批量被动入库在不具备 MemCore 压缩条件时，调用空函数后仍返回 `maintenance={ok:true,status:scheduled}` | 不再制造该回执。没有实际调度时 `maintenance={}`；有条件时仍只安排一次真实 MemCore 维护，并返回其结果 |
| 旧宿主摘要队列 | `summary_queue.py` 没有生产导入或实例化，只有自身两个单元测试使用它 | 删除模块及这两个专属测试。当前 MemCore 压缩线程并非此队列，不受影响 |
| `MEMORY_BACKEND` 设置 | `config._apply_settings` 在清理前已经固定设置为 `memcore`；配置字段、设置目录和示例仍声称可以选择 `legacy/dual` | 删除无效设置字段、目录条目和示例值。旧 `.env` 键进入已有退役键提示；内部运行标记仍为 `memcore` |
| 云端配置同步要求 | 同步脚本仍复制并强制要求提供上述无效键 | 从同步白名单和必需字段中移除，避免继续传播无效配置 |
| 旧阶段验收的过期调用 | E4/E5 仍传入无效记忆模式；E4 还用空动作 API 验证认证 | 移除无效模式值，E4 认证检查改用真实设置写入接口。完整外部验收仍未在本轮运行 |
| 当前项目地图 | 仍描述旧摘要队列和通用动作 API，还把聚合快照写成五个字段 | 更新为现行动作接线、七个快照字段、真实设置路由与 MemCore 压缩适配器 |

这些清理不移除真实任务控制、工具并行、后台任务、主人共享记忆或现行压缩。没有改稳定提示词、工具描述/schema、历史投影、压缩阈值、选择区间和同轮冻结规则，也没有修改生产数据库。

### 1.1 当前动作在哪里执行

控制中心仍沿现有三条路径执行动作：

1. 明确的后端处理器：任务控制、插件管理、MCP、提供者、审批等，各自调用对应服务路由。
2. 主窗口设置桥接：使用 `SETTINGS_ACTION_SPECS` 派生的命令，并通过真实回执/状态确认结果。
3. Tauri 原生命令：窗口、文件选择、角色包与本机设置等。

动作找不到可用实现时直接报告不可用，不再尝试第四条“通用动作服务器”。这能消除无效请求，也避免开发者往一个空入口继续添加业务。

### 1.2 当前摘要维护在哪里发生

真实调度为 `_schedule_memcore_compaction` → `MemcoreManager` → MemCore 的会话维护与 worker。`_run_summary_cycle` 虽沿用旧名字，但实现已经调用 `manager.compact_due_sync`，仍是有效的同步维护适配器。

本轮移除的旧函数从未安排压缩；删除它不会改变当前何时 fork、何时替换、工具轮何时投影或何时触发维护。QQ 批量被动入库继续保留逐条成功/失败结果，真实维护仍按批次安排一次。

## 2. 需要适配当前架构的部分

### 2.1 旧记忆模式分支仍散落在宿主中

虽然正常配置始终使用 MemCore，`MemcoreManager` 的程序化构造、`response_projection._memory_backend`、`retrieval_engine`、可见上下文和索引适配等仍保留 `legacy/dual` 判断。部分隔离测试也直接替换内部运行标记。

不能再把这些分支描述为可由 `.env` 选择的正式运行模式。建议作为后续一个完整切片处理：

- 常规入库、渲染、检索、压缩只从 MemCore 主线取权威数据。
- 为历史数据导航、迁移与特定隔离测试保留明确的适配入口。
- 先确认所有程序化构造、维护脚本和历史读取用途，再删除已无消费方的旧模式分支。

不建议边改一处分支边补一个兼容开关；这容易让“故障回退、历史读取、测试桩”继续混在同一个模式里。

### 2.2 主权判断与可用性判断仍有耦合

`_memcore_owns_legacy_vector_index` 当前同时检查内部模式、管理器是否启用以及是否可用。`_upsert_raw_record`、旧向量重建等据此决定是否使用旧索引。导航模式不构造 Embedding/旧索引；混合检索的管理器失效路径仍需要一起核对。

建议把两个问题分开：记忆由谁管理，是架构选择；当前管理器能否完成某次请求，是运行状态。正常宿主已经选择 MemCore时，故障应清楚报告、恢复或重试，不能仅因 `available=False` 就把旧索引当成新的主线。

本轮没有重写这些故障路径，也没有据此认定当前出现了双写。实施时需要覆盖正常、启动失败、服务失效及恢复，核对是否有额外模型调用、旧向量写入或错误的成功回执。

诊断也需要一起校正：`memcore_integration/diagnostics.safe_status(None)` 仍把“没有管理器”标成 `backend=legacy`，不能仅凭这个标签认定宿主切换了记忆引擎。未配置、不可用与架构选择应分别表达。

### 2.3 旧摘要表的读写接口需要拆开评估

`store/legacy_summaries.py` 仍同时拥有摘要写入、历史查询、按 ID 读取与索引遍历。`store/messages.py` 的历史 source 读取和 `service_factories.py` 的索引适配也仍使用其中的读取能力。

因此不能直接删除整个 mixin 或 SQLite 表。较合适的下一步是先把当前仍需要的历史读取用途列清，再清理没有生产调用的旧写入/旧压缩接口。已有 ID、摘要内容和回读凭据应保留；删除写入代码不等于删历史数据。

### 2.4 旧验收脚本不能再用无效环境键隔离 MemCore

`scripts/smoke_m65_e4_dual_instance.py`、`smoke_m65_e5_two_instance.py` 较早使用 `MEMORY_BACKEND=legacy`。该键在本轮清理前就不能改变实际运行模式，本轮已移除；E4 的认证检查也已从空动作 API 改到真实设置写入接口。模块说明不再声称可以通过该环境变量启动无 MemCore 的宿主。

其余旧阶段参数与验收范围仍建议按目的分别梳理：实例隔离检查用清楚的测试依赖/模型桩；验证真实当前记忆的检查则使用安装的 MemCore 与临时数据根。旧阶段验收如已没有维护用途，可以退出当前验证清单或归入历史资料。

本轮未运行这些外部验收脚本，也未借清理执行 QQ 发消息、启动旧服务或操作生产数据。

### 2.5 全局配置与 Bot 配置需要按性质继续收拢

模型、语音已经逐步使用 `BotSettingsView` 和对应服务配置；部分旧逻辑仍读取进程级 `config`。并非所有全局配置都需要变成每会话设置：宿主坐标、共享压缩策略和统一阈值可以继续共享。

后续逐项确认：哪些属于宿主，哪些属于 Bot，哪些只是用户/会话状态。让已有配置所有者负责读取与应用，避免同一参数在环境变量、设置覆盖和专用页面分别建立一份权威。子代理模型单独配置、公共阈值复用的现有方向保持。

### 2.6 小屋与聚合工作台的接线仍需完整处理

小屋直接调用 Engine/Care 底层、缺少主线可信来源与共享会话协调，商店又有自己的编辑规则；聚合快照中的工作台读取也没有经过专用入口的主人素材范围处理。这些在前一轮已经明确定位。

应一起复用身份、协调、养成、商店与资料服务来处理，不能只改 UI 文案或只换记忆 ID。细节及修改顺序见 [前后端审查第 3–4 节](frontend_backend_architecture_audit_v1.md)。

| 单 Bot/实例启动 | 没有 `bots.toml` 时，`host_bot_bootstrap.py` 仍构建有效的单 BotRuntime，模式标签叫 `legacy_single` | 属于当前有效启动方式。若要收敛，先让启动器能生成/选择规范配置，再处理旧标签和选择逻辑 |

| 默认本机认证兼容 | `AdminWriteAuth.local_compatibility` 仍支持默认本地实例；具名实例按既有凭据运行 | 保留已支持的部署方式。与删除空动作 API 无关，不能借清理放宽具名实例认证 |
| 旧素材目录读取 | `AttachmentInboxService`、`GeneratedFileService` 仍允许按已有记录从 `legacy_base_dirs` 找回文件 | 保留受控回读。迁移已有记录和文件并确认旧根无人引用后再删，不能因为文件目录较早就让历史 handle 失效 |
| 养成 v1/v2 → v3 迁移 | `care_state_migration.py` 冻结旧状态，并把账号、身体、关系拆开；还支持从原备份修复关系锚点 | 保留升级和修复能力。不能重新根据今天的群成员推断旧关系，也不能删除原快照后重建余额 |
| 桌宠状态与 localStorage 迁移 | Tauri 只在默认实例缺少新状态时读取旧状态文件；旧全局存储键也只允许默认实例迁移 | 保留限定范围，防止升级后丢设置或把别的实例资料带进来。前一轮已退出的无效字段不恢复 |
| 角色包与历史语音格式 | 旧角色包字段、校准容器和部分历史回复仍需正常读取；`speech_segments` 有现行派生消费者 | 保留读取和派生，内容仍以当前规范结果为准。未来统一交付格式应先核对所有消费者 |
| OpenAI compatible ASR/TTS 等适配器 | `compat` 表示协议兼容，仍连接真实模型服务 | 正常能力，不能按文件名当旧逻辑删除 |
| 设置 HTML 跳转 | 旧地址跳转到当前控制中心，代码很小 | 保留已有快捷方式；无需把一个跳转重新做成一套设置实现 |

保留兼容并不意味着恢复旧界面、旧自动感知或第二份记忆主线。读取历史格式、适配现行协议和日常业务实现应在代码与当前文档中分清。

## 4. 建议后续切片

| 顺序 | 任务 | 完成后减少什么混淆 |
| --- | --- | --- |
| 1 | 小屋复用主人会话、协调、养成、商店与资料服务 | 同一个角色为何在两个界面记忆/状态不一致 |
| 2 | MemCore 主线、历史读取、故障恢复分离；梳理旧摘要写入及索引分支 | 哪个模块才是当前记忆与压缩权威，故障时谁接管 |
| 3 | 随新前端整理快照读取、日常配置与创作/诊断入口 | 一个开关或文件为何在多页有不同状态、改哪里才生效 |
| 4 | 更新或归档旧阶段验收脚本及其历史说明 | 环境变量和测试桩为何看起来支持实际上不能选择的模式 |

这些任务适合分别执行和审查。无需为了方便阅读再增设通用路由、额外模式或每会话配置；应把入口接回已有服务，再删除被替代的重复部分。
