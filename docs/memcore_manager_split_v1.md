# Memcore 管理器拆分

## 基线与修复

开始复查时 `companion_v01/memcore_integration/manager.py` 为 4563 行、96 个方法，同时负责运行时租约和关闭、命名空间系统构造、回合与语音写入、材料和工具目录、上下文投影、检索及后台压缩。

先整理并提交现有后端改动，包括摘要模型跟随会话、请求模型名与上游别名分别记录、QQ 模型编号稳定、关系历史迁移和 Skill 加载说明。未纳入未跟踪的实验工具目录或运行数据。

复查确认并修复两项回归：

- 压缩调度收到的是回合启动时的模型快照。现在显式会话选择与回合模型提示分别保存，显式选择优先（包括恢复默认模型的空值），旧回合的同步或后台压缩不会撤销新的选择。没有显式会话选择时仍跟随回合模型提示，LLM 重试继续读取当前选择。
- 关闭测试通过 `__new__` 创建管理器，补齐新增的模型路由状态，并验证后台任务完成后系统、存储及路由状态均被释放。

新增回归在修复前复现后台/同步调度撤销模型切换和默认选择的问题。修复后 17 个相关测试模块共 553 项通过，覆盖模型配置、流式调用、记忆写入、QQ、关系迁移、后端路由、主人共享会话及关闭流程；lint 和差异检查通过。测试使用临时存储和受控 LLM/传输，不替代真实供应商请求或用户数据迁移验收。

## 拆分原则

`MemcoreManager` 保留兼容入口、实例状态初始化及明确的职责组合。实现模块按职责静态声明方法，每个方法只有一个所属模块；不在运行时注入方法，不反向导入管理器入口。共享锁、队列和关闭状态仍属于同一个管理器实例，后台任务沿既有调用链执行。

优先分离运行时生命周期与压缩调度，再处理回合写入、语音投影、材料/目录、上下文投影和检索。每片核对方法签名、装饰器和实现，并执行对应行为回归后提交。

## 第一片：生命周期与压缩

- `contracts.py`：配置归一化、状态契约和共享常量；原入口继续导出同一个契约对象。
- `lifecycle.py`：进程运行时租约、命名空间构造、索引预热、协作取消和延迟关闭。
- `compaction.py`：会话模型选择、合并队列、失败冷却、同步/后台压缩及结果诊断。

管理器由 4578 行降到 3760 行。对全部 97 个方法和 23 个顶层定义逐一做 AST 核对，仅静态命名空间哈希的所属类引用随方法移动。新增模块边界检查覆盖未绑定全局名称、导入可达性与无循环、唯一方法归属、兼容导出和延迟加载 Memcore。8 个相关测试模块共 170 项通过，lint 和差异检查通过。

扩大检查时，`tests.test_package_independence` 的 4 项发行检查失败：精确版本集合断言、工作区绝对路径断言和两项依赖审计。使用基线提交 `f9bd3e95` 的 requirements/脚本及现有兄弟包环境复现同样结果，确认与此次管理器拆分无关。本次保留这些环境和发行配置，不宣称发行检查全绿。

## 第二片：写入、投影与检索

最终入口仅保留实例状态初始化、`from_engine`、可用状态属性和 `status`，共 135 行。97 个原有方法都有明确归属；签名、默认值和装饰器保持一致。93 个方法的实现 AST 完全一致，1 个哈希方法仅调整静态引用的所属类，另外 3 个方法只移除不再使用的全局 `_llm_client` 字段、重复构造及对应检查。各命名空间实际使用的 LLM 适配器保留，会话模型回调继续在每次请求和重试时读取最新选择。
