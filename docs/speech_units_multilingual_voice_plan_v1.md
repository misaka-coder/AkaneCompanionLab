# 中文显示、多语言配音与分段声线执行方案

日期：2026-09-29。状态：第一版已接入普通桌宠、QQ 和实时语音的真实代码链路，并完成模型试答和本机合成试听；运行中的塞西莉亚已启用四种参考风格，后端已重启。下文保留设计背景；当前实现、开关与验收边界以 [实施与验收记录](speech_units_multilingual_voice_v1.md) 为准。

## 1. 建议结论

保留现有标点分句、下一段预取、播放队列、取消与失败后显示文字的机制，升级它们接收的数据。把“显示文字、实际朗读文字、配音语言、参考风格”放在同一个可交付单元中，不通过两份完整长文本的位置猜测对应关系。

短期可先试听最终模型直接说中文。如果听感可接受，中文显示、中文合成能沿用现有链路；但这不能解决显示动作描述与朗读内容分离、同一回复多参考风格的问题。长期仍建议统一交付单元。独立翻译请求不作为本方案的默认主路径。

新协议由 Akane 宿主拥有，MemCore 继续提供通用文本分句和记忆能力，不加入角色专用参考音频、日语翻译或 UI 表情规则。

普通桌宠的 fetchTtsAudio 当前只传 text 与角色上下文，未单独传分段 emotion；小屋则显式传 beat.emotion_id。不能假定各入口已经统一执行了表情选参考。

## 3. 模型输出与宿主单元

### 建议的模型协议（字段名为本方案拟定）

新能力名暂定 `speech_units_v1`。支持该能力的回合以 `utterances` 为唯一正文来源，模型不要同时生成一份完整 speech。

```json
{
  "emotion": "normal",
  "utterances": [
    {"style": "calm", "text": "（把茶杯放到你面前）回来啦。", "say": "おかえりなさい。"},
    {"text": "今天过得怎么样？", "say": "今日はどんな一日でしたか？"}
  ]
}
```

- `text`：当前显示语言的正文。可以保留合适的动作描写、排版。
- `say`：真正要读出的内容；配音语言不同，或显示含不应读出的描述时填写。只读台词，不读动作说明；允许角色自然说出的感叹词。
- `style`：可选的声音风格短 ID，不是表情 ID，也不是文件路径。省略使用角色配置的默认风格；不跨单元隐式继承上一个 style。
- 显示/配音语言由角色与本轮配置提供，普通单语言配音不要求模型反复填语言字段。明确需要混合语言时再扩展单元级语言覆盖。
- 当前第一版要求配音明确填写 say；省略或 null 都不会朗读 text。同语言的旧角色可继续使用原 speech 协议，避免重复输出。后续若支持省略 say 的同语言简写，必须由可信语言配置决定，不能猜测。
- 明确仅显示的单元使用 `say: null`。空字符串作为异常诊断处理，不能模糊地变成“改读显示文字”。
- 不同语言下缺失 say：照常显示 text，此单元不错误地把中文送进日语前端；记录可观察失败。无需为补配音重跑主对话。
- 一项可以包含若干句话；风格改变时再分组，长段也可按完整意思分组。每个 say 内部仍按标点拆成多个音频句子，桌宠还保留原音频长度细分。
- 当前仅已选的平静参考经过用户认可，不预先宣称已有可靠的 shy/happy 等完整参考库。

“整篇 speech + 整篇 speech_ja”不推荐作为主协议：模型须先写完一份才开始另一份，且中日标点、分句数量和语序未必一一对应。内嵌 `[voice=...]` 标签也不优先，避免展示泄漏和与括号/引用/代码解析混杂。

### 宿主规范化后的内部单元

宿主生成 ID 与版本信息，不增加模型填写负担。单元至少具有 `unit_id`、`display_text`、`spoken_text`（可为空）、`speech_language`、`voice_style`、`turn/stage/generation`。

旧 speech 字符串进入兼容适配器后也变成同一种单元；新协议面向旧消费者时，speech/speech_segments 从 display_text 派生，不让模型维护两份权威正文。保留旧客户端路径，避免已有 QQ、桌宠或工具前言突然失效。

小屋保留 beats 的场景字段，但正文与配音部分复用该单元的验证/编译逻辑。不要独立维护三套声音语义。

## 4. 保留分句与流式优化的方法

1. 显示文字增量与配音提交分开：解析器进入某项 text 字符串后，就将正确解码的增量送入原有分句器，不等待 text、该项或整个 JSON 完成。配音基础版在一项对象闭合、字段校验通过后提交；进一步的配音增量模式须先固定 style、语言与显示关联，再对 say 的稳定句末提交，不能提前朗读风格尚未确定的内容。两个版本的首声差异须实测，不能把“逐项流式”等同于原有逐标点首声时机。
2. 单元内部对 spoken_text 调用现有标点分句器，编译成 1..N 个音频片段；所有片段携带所属 unit_id、显示文本和不可变风格配置快照。
3. 中文和日语按单元关联，不要求每一个中文句号匹配一个日语句号。第一版普通桌宠让中文按标点独立流式展示，配音按队列播放；不会因一个日语句子拆成多个音频块反复重置中文。严格字幕同步仍需后续体验验收，不能宣称已经逐句对齐。
4. 保留一个下一段预取槽、播放顺序、turn token/AbortController、取消后的旧音频丢弃。风格在入队时固定，不能在出队时读取已经变化的 UI emotion。
5. 极短片段合并只在同一语言、同一有效参考风格、同一权重版本且显示映射可保留时进行；相邻不同风格不能被合成一个请求。
6. 新协议的事件/最终帧对账使用宿主单元身份与内容指纹。相同中文不代表同一条音频，重试回显也不能把已播放单元再次入队；恢复时保存 accepted 单元并复用映射，不临时重新生成身份。
7. 协议修复不得覆盖已交付内容。新字段不能绕开现有工具协议过滤、明确静默、工具前言和取消边界。新旧协议同时混用应按本轮协商模式处理，并留下诊断，不能双发。
8. QQ 仍可整段交付：按相同计划合成各风格块，统一格式后顺序拼接成一条语音。相邻同风格块可批量处理；不能只拿第一项风格合成整篇。
9. 普通聊天记忆保留显示语言正文；配音译文和实际 audio/text 播放回执作为交付元数据关联，不当作第二条角色回复入库。实时语音仍区分已播放与未播放，不用全文推定用户已经听到。

### 讨论澄清：模型项不是发消息边界

不能先汇总全部 text 再分句。正确方向是：`text 增量 → 连续的显示分句状态 → 显示片段 → 原客户端投递策略`；最终 speech 只是显示正文的兼容投影与入库来源。

一个 text 内有多句时可以增量产生多个显示片段；某项只是一个分句时，也不能仅因为 JSON 对象闭合就强行发送一条 QQ 消息。跨 text 项保存分句状态与来源范围，保留自然标点，不额外插入换行制造新句。声音风格边界可以结束一个音频块，却不必强制结束一条显示消息。

这意味着“模型内容项、显示分句、音频块”是三个有关联但不强制一一对应的层次。一个显示句跨多个风格项，或一个中日对应项存在不同数量的标点，都需要保存映射。需要字幕随每个配音小句精确切换时，模型必须提供更细的中日对应项；无法从两份大段文本中无损猜出对齐。

普通 QQ 文字本身存在 speech_segment 流式发送路径；整段交付主要指其 record 语音。继续保留 stream_enabled、阶段前言、合并/限流及最终补尾等原投递策略，不把 JSON 项数量当成消息数量。

新协议下显示事件与配音事件必须在消费者边界显式区分。可保留 speech_segment 的显示含义，但语音消费者不可再无条件拿它的 text 合成；新增的配音事件名和 schema 需在 P1 定稿。旧协议仍通过显式适配使显示与朗读同源，不允许新旧两路同时触发 TTS。

实时语音 VoiceResponseStreamBridge 当前只接收 speech_segment/final，单个 text_artifact_ref 同时服务 TTS 与播放上下文；它不是天然兼容双语。需要分别关联显示正文、实际 spoken artifact、风格和播放回执。未升级的实时入口必须继续协商旧协议；若要统一启用，新旧输入、取消、打断、恢复及已播放语义必须同批验收。不能等普通桌宠上线之后才发现实时语音仍把中文显示事件拿去读。

## 5. 声音风格与 emotion 解耦

新请求采用“显式 style → 角色默认 style”的规则。UI emotion 继续表达表情，不自动决定配音；例如 shy 表情可以使用 calm 声音，避免把害羞一律变成急促/高亢。

旧 emotionVoiceMap 保留为旧协议的兼容配置，迁移时可将已有映射条目显式导入语音风格库。新协议不再默默走 emotion 回退。不要直接删掉现有用户配置，也不要把新 style 塞进旧 emotion 字段假装完成解耦。

风格由宿主解析为参考音频、对应台词、参考语言和调音参数，作为一次调用内的配置快照。模型只看到已配置且可用的短 ID 与一句描述。未知 ID 回默认风格并记录诊断；已存在风格的资源丢失属于合成失败，不伪装成另一个声线成功。

权重选择与参考风格是两层概念。本机当前客户端只把 voice_profile_id 传给 /tts，不负责切换 GPT/SoVITS 权重；不同角色的权重归属需在运行时另行明确。单个角色切参考时维持同一组权重，不在每句话重载模型。

可采用的简短提示块：

> 按自然短句输出 utterances：text 用于显示，say 用于配音。配音使用配置语言，忠实表达原意，只写实际说出口的话；动作描写留在 text。显示与配音相同时省略 say，仅显示时填 null。style 从可用声音风格中按需要选择，省略用默认；不必随每句表情变化。

字段格式和缺失行为由 schema/代码保证，不通过反复堆砌提示词限制模型。

## 6. 本机性能实验与实际限制

实验路径：`F:\Anime\Cecilia_GPTSOVITS_20260929\integration_review_20260929`。

- 最终 GPT15 / SoVITS8，RTX 5060 Laptop，FP16，batch=1，seed=42，speed=1，cut0。
- 与宿主启动器一样启用 inference_mode；独立进程内直接调用 TTS，并同步 CUDA 计时。未修改供应商安装文件或正在运行的服务。
- `timings.json`、`probe_reference_latency.py` 和 stdout/stderr 为原始证据。
- 同一句日语，对两个参考先预热，再取得 4 次保持参考、4 次切参考样本。

| 项目 | 本次观测 |
| --- | --- |
| 同参考，音频就绪中位数 | 约 1.041 秒 |
| 切参考，音频就绪中位数 | 约 1.276 秒 |
| 每次切参考的语义/频谱准备 | 约 0.173–0.450 秒，中位数 0.185 秒 |
| 首次冷参考准备 | 约 1.53 秒（另有模型初始化等成本） |

这些是少量、带计时插桩的直接模型调用，不含 HTTP、插件、LLM、队列和扬声器；输出长度也随参考改变，不能把总耗时差全部算作缓存开销，不能据此承诺线上 p95。

本机 TTS.py 只有当前一份 prompt_cache。C→D→C 会重新读取/重采样参考音频、执行 HuBERT 与语义特征提取、频谱计算和参考文本处理；v2Pro 的 speaker embedding 在每次生成中仍计算。因此“仅切参考、完全不降速”不成立。

两次整句/三段对照：整段音频就绪约 1.884/1.604 秒；分段的首段就绪约 0.515/0.420 秒，但三段调用全部结束合计约 2.384/2.151 秒，整段调用结束约 2.043/1.755 秒。独立同步调用还包含每次生成器收尾清理；线上已有延后空闲清理，不能直接套用这个总差值。

区分两种情况：

- 已经按三个自然句分成三次合成，再为每段选不同参考：主要增加参考处理，调用次数未增加。
- 原本一次合成的一句话为了三种风格变成三次：除了参考处理，还增加独立解码/调度/收尾，并可能破坏连贯语气。可能改善首段就绪，但不保证总计算量或句间衔接不变。

### 后续性能切片

在独立 GPT-SoVITS 运行时适配层做有限容量参考特征缓存与预热，不把张量缓存塞进 Bot 宿主或通用 TTS 插件。缓存应覆盖参考语义、频谱、参考文本特征及 speaker embedding；键包括参考内容版本、台词、语言、权重版本、相关前端/说话人模型版本、精度和设备。换权重或参考内容后失效。

运行时当前有可变 prompt_cache，不能让不同参考的并发调用互相覆盖。短期每个模型实例串行生成；长期如做批量推理，需真正将每个请求的参考条件隔离，而不是并发调用同一个可变 TTS 对象。缓存预热不会消除生成每段语音本身的开销。

## 7. 中文合成验证

相同最终权重与用户认可的日语参考，输入语言改为 all_zh，参考语言继续 all_ja。

首次三条测试中，自动 ASR 对第 1/3 条回读匹配；第 2 条“有点累了吗？我给你泡一杯热茶。”只读出了前半句。不能据此宣称中文完全稳定，也不能把问题全归因于跨语言。

随后按现有标点机制拆成两个请求进一步验证：“有点累了吗？”回读匹配；“我给你泡一杯热茶。”被回读成“我給你拍別人家”。这可能包含实际发音问题与识别误差，尚不能认定该中文声线足够稳定，不能仅靠拆句宣布修复。

`chinese_asr.json`、`chinese_split_asr.json` 和 `chinese_split_timings.json` 保留结果。`chinese_trial_matched.wav` 为最初三句的试听合集，保留第 2 条的问题，没有挑选正确片段冒充完整成功；对应预期台词依次为“欢迎回来，今天过得怎么样？”、“有点累了吗？我给你泡一杯热茶。”、“不用着急，我会一直陪着你的。”。

中文声调、口音、音色相似度仍需要用户试听；ASR 正确不是听感验收。当前更稳妥的正式方案仍是日语配音配合中文显示，或先进一步验证/改善中文能力。

## 8. 分阶段实施与验收

### P0：确定首个可用模式

试听直接中文的样本，确认是否作为先用方案；保留日语参考与原模型，不重新训练。无论选中文还是日语，数据结构为未来的显示/朗读分离留同一条入口。本次没有激活运行配置。

### P1：统一内部交付单元，先保持旧模型输出

- 新增宿主纯数据契约/编译器；旧 speech 适配到单元。
- 扩展桌宠队列、/tts 参数、公共服务与 QQ 交付，保持默认显示文本等于合成文本；贯通身份、语言、style 和取消上下文。
- 先验证旧行为等价，再开新模型协议，避免同时更换所有层而无法定位回归。

### P2：新增模型增量协议与提示，支持中日对应

- 能力协商与逐项 parser；新模式只生成 utterances。
- 同步修改 prompt_blocks、prompt_profiles、llm_runtime、final_output_engine、engine 中的流式恢复和正文投影、think 字段白名单及 petdesk/插件投影。
- 兼容旧 speech，明确不同语言缺配音、仅显示和错误单元的行为。模型 ID、文件路径、内部权重位置不进入提示。
- 新协议“先输出一项、随即分句合成”，不等后续项或最终整个 JSON。一次模型请求可能多生成翻译 token，但不再额外串行请求翻译模型。

### P3：分段参考风格、配置迁移及缓存

- 在维护中的 `capcore-adapter-speech` 源码、TTS 插件和宿主配置完成显式 style 契约，不直接改 site-packages。
- 参考路径/台词/语言原子解析；指纹加入有效语言、风格、参考版本和模型版本，避免缓存串音。
- 先准备并试听少量风格参考，再加入模型可见目录。对照测试已经证明部分参考会引入漏句或重复，不能只按台词语义给参考贴标签就上线。
- 增加运行时有限缓存；与无缓存的相同文本、相同分块、相同参考序列做实测对照。

### P4：小屋、实时语音与完整回执

- scene ModelBeat 复用配音字段的通用契约，保留 emotion_id/motion/advance。
- voice_runtime 的文本 artifact 和 TTS 命令传播 spoken 文本及配置快照，播放回执关联显示单元；打断和恢复沿用现有 durable 语义。
- QQ 生成一条拼接音频，桌宠按单元播放；一条失败不能重播已成功播放的前缀。QQ 拼接中某段失败时明确报告失败/保留文字，不能悄悄漏掉中间句。

### 必须覆盖的检查

- 旧 speech 与纯中文行为；中文显示/日语朗读；显示动作而语音不读；真正要读的括号内容不能被粗暴正则删除。
- 多个任意 token 边界、转义引号、Unicode、未闭合单元、错误字段、工具前言、空回复、明确静默。
- 首项闭合即交付，最终帧不重播；同文不同 style、合法重复句、模型重试及补尾。
- 420 ms 短句合并不跨 style/语言；一个显示单元拆多个音频块不重复闪烁；中日句数不一致。
- 队列处理中换角色/风格、关闭语音、打断、重新进入、旧请求迟到、风格资源失效和低内存。
- 默认风格、旧 emotionVoiceMap 兼容、未知 style、参考替换后的缓存失效；并发请求不互相串参考。
- QQ 一条 record 与普通桌宠、scene、实时语音三个入口的真实链路；禁止仅以 HTTP 200 当作用户已经听到。
- 相关 pytest/unittest、桌宠 build 与浏览器检查、git diff --check；沿用现有 speech-delivery/tts-presentation/实时语音 smoke 与取消回归。
