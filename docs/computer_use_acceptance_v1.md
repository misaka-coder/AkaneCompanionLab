## 2026-09-21 闲置会话永久占用桌面

实际记录：主会话约 10:34 完成 QQ 操作，群会话约 10:44 请求点歌。10:44:43–10:49:28 同一设备连接返回 **21 次 `desktop_busy`**，包含启动应用与选择窗口；两次任务属于不同调用作用域。旧实现只在主动停止/交接等路径清理逻辑持有者，没有闲置到期，且设备选择窗口另有一层旧会话拦截。该问题与用户是否操作鼠标键盘无关。

修复：

- 共享控制权自持有者最后一个请求结束起计时，闲置 **60 秒**后允许其他已授权会话通过重新选窗、显式窗口操作、启动应用或个人浏览器连接取得控制权。正在执行的请求始终持有互斥锁，长请求不会因计时到期被抢占；失败的竞争请求不会续期旧持有者。
- 交接时清除旧控制会话、截图和流程检查点；旧输入/观察不能取得其他会话的控制权。用户本机解除停止后，原会话仍可重新观察；明确停止、输入开关、真实鼠标键盘活动及同会话跨工具交接规则保留。
- `desktop_busy` 专指请求正在执行；`desktop_owned_by_other_session` 表示近期其他会话持有控制权，返回不含持有者身份的 `retry_after_ms` 和恢复说明。模型不得将其解释为用户动了桌面，也不得连续重试。
- guide v8 加入忙碌恢复规则及用户指定的日常优先级：适用且可用的 CLI → 无障碍控件 → 截图坐标，可相互辅助；用户要求纯 computer_use 测试时维持该测试范围。指引标题改为复用版本常量，避免内容和版本号漂移。
- 个人浏览器复用相同错误恢复说明，去掉已由共享控制权判断覆盖的旧会话阻断。

验证：Rust 普通测试 **78 passed / 16 ignored**；相关 Python 测试 **42 passed**。真实临时原生窗口覆盖新旧会话交接、旧动作拒绝、实际文字输入、无重复 Enter、窗口整理及审批恢复；闲置时间在测试中推进，不真实等待 60 秒。另单独通过原有活动恢复回归，覆盖本机停止/恢复后的重新观察。首次原生批次测试被 `user_takeover` 中断，后续独立重跑通过，未关闭活动检测。本轮未向 QQ 发送消息或重播歌曲，模型端到端使用仍待实际体验确认。

部署：最终 `npm run tauri -- build --no-bundle`、`git diff --check` 和本轮文件空白检查通过；已重启 `local-qq-test` 后端、设备执行器和桌宠。健康检查、设备在线和 UI ready 均通过，两个运行副本的 SHA-256 与最终 release 一致；恢复更新前已开启的电脑输入，本机状态为 `idle`、`input_enabled=true`。

## 2026-09-21 普通输入干扰由模型重新观察恢复

用户反馈点击「恢复控制」仍无效。原实现把任何非 Akane 标记的鼠标移动/按键都计为新的输入代次，而本地恢复只承认点击时的代次；下一次移动又立即暂停。`observe` 虽然返回新画面，却不更新会话及共享控制租约的代次，因此模型无法凭刷新自行恢复。

已将普通输入活动与明确停止分开：输入仍立即打断正在执行的动作并使旧观察失效；模型显式调用 `observe` 时，最多等待 1.2 秒，需连续 600 毫秒无新输入且没有按住键/鼠标按钮，再取得稳定观察。只有观察全过程的输入代次一致、输入许可仍开启、同任务/同工具/同设备租约有效，才同步更新会话和租约。观察过程中发生输入或仍在持续活动时返回暂停与重新观察提示。内部步骤和输入后的自动观察不会自行吸收用户输入代次，已执行及结果不明的动作不重放。

首次选择就被打断、尚无会话 ID 时，`select_window` 可先只读刷新目标窗口，不激活窗口；由返回的 `next_action` 引导模型确认目标后再次选择。`stop`、关闭输入、断线停止等仍不能通过观察解除。本地按钮改名为「解除停止」，面板说明普通输入停下后由 Akane 重新观察继续；工具 `status` 也准确报告 `paused`，说明升级为 guide v4。本次调整适用于 `computer_use`；个人 Chrome 的独立操作恢复策略未在本轮扩展。

验证：64 项普通 Rust 测试、15 项相关 Python 测试、控制器测试通过。新增独立进程测试 `activity_recovers_after_observation` 使用自建非激活窗口进行真实 WGC/UIA 观察，在输入监控层模拟活动（没有向操作系统注入鼠标/键盘），确认首次选择恢复、重复干扰、点击本地恢复后再活动、持续输入暂停、旧观察拒绝、新观察后下一步 preflight 成功、明确停止不可绕过、关闭输入不可自动开启、任务/工具隔离。390px 浏览器检查覆盖暂停、明确停止、离线和流程状态，无横向溢出。

## 2026-09-21 首次截图后执行器崩溃：生命周期修复

87 群本次记录显示：能力加载与窗口枚举成功，ChatGPT 窗口选择返回了截图，后一次观察才变成 `capability_not_available`。并非输入许可被撤销。设备 PID 48880 已退出，宿主仍存活；Windows Application 事件 1000（01:08:46）与 1001（01:08:51）记录独立设备执行器在 `GraphicsCapture.dll_unloaded` 发生 `0xc0000005`。宿主 WebSocket 同期关闭。

根因与复现：旧 `capture.rs` 在每次截图调用中执行 `RoInitialize` / `RoUninitialize`。WGC 关闭会话后仍有异步原生清理工作；调用返回时关闭 WinRT，使相关 DLL 在清理完成前被卸载。独立测试进程只创建一个自己的、不抢焦点的原生窗口，不初始化 UIA：旧实现输出第一帧尺寸后立即以 `STATUS_ACCESS_VIOLATION` 退出，与现场故障一致。此前以 UIA 常驻线程、已运行进程为主的验收没有覆盖首次使用时的生命周期边界。[Microsoft 对 RoUninitialize 的说明](https://learn.microsoft.com/en-us/windows/win32/api/roapi/nf-roapi-rouninitialize)明确指出关闭运行时会卸载线程加载的 DLL；[WGC 示例维护仓库中的同类问题](https://github.com/robmikh/Win32CaptureSample/issues/99)也记录了关闭后卸载时的异步崩溃。

修复让截图由唯一、与执行器同寿命的 MTA 线程负责；WinRT 和 D3D 对象均在该线程创建、关闭与释放，单张截图结束及设备重连不再反复拆除 WinRT。会话/帧池采用 RAII 关闭，包括中途失败路径。请求队列有界；停止和 4 秒等待截止会取消未完成请求、丢弃迟到结果，原生调用卡住也不无限创建线程。没有添加延时卸载、截图后重启、协议别名或替代截图 API。能力不可用的恢复说明补充：不可用本身不能证明用户撤销许可。

## 2026-09-21 连续流程与交互增强

本节对应执行单第 11 节。新增能力已接入宿主契约、真实 Satellite 传输、Windows 执行器和控制中心；使用说明升级为 guide v2，宿主/设备 schema hash 同步更新。需要同时重启后端与新版桌宠，旧进程不会热加载这些修改。

- `run_steps` 一次提交最多 12 步的声明式计划，不限同一页面；支持预期可验证的页面变化、所属弹窗和已枚举窗口的显式切换。输入前复核当前窗口和控件，执行后检查 `expect`。`wait_for` 只等待，不把等待成功记作输入已发生。
- 每次运行预算默认 8 秒、最大 15 秒，单步等待最多 3 秒；达到预算返回暂停和检查点。流程检查点在当前设备进程内最多 64 个、15 分钟有效，不在未知结果后自动重放输入。预算不保证每个 OS/UIA 调用都精确在截止瞬间返回；宿主传输等待上限为 30 秒。
- `resume_steps` 复核当前状态：已经执行但后置条件未通过的步骤只重新检查结果；从未执行的步骤才可能输入。用户接管/停止后仍需本地恢复。改变控制会话、设备 epoch 或失效流程不能继续。不存在通用业务回滚。
- 未来步骤需要审批时，先停到那一步的真实现场，再生成包含流程和步骤身份的具体审批。宿主保留先前步骤进度与最后截图。内容改变会使授权不匹配；审批不能从一个步骤沿用到下一个步骤。未知应用可能多次要求具体审批，因此并非每种应用都能一口气执行全部步骤。
- 新增 `set_value`（可验证的 UIA ValuePattern，目标须聚焦且原值完整）、`set_checked`（明确目标勾选状态）、右键/中键、双击和当前窗口内的有界拖拽。目标值或勾选已满足时连续流程跳过修改。QQ 富文本没有 ValuePattern 时不能声称支持 `set_value`，继续使用受控文字输入或编辑按键。
- QQ 编辑区新增有证据的 Ctrl+Z/Ctrl+Y、删除、选择、Esc 等编辑按键策略；这些是可调用操作，不保证应用具有撤销历史，也不等于撤回已发消息。
- 中间步骤使用本机文本观察，正常完成或中断时只返回最后现场截图。控制中心显示连续流程进度、暂停、审批与未知结果状态。schema 和说明比第一版更大，不能承诺每个短任务都减少总 token；验证的是减少连续步骤的模型往返与中间媒体投影。

## 使用入口

重新构建并启动桌宠和 Python 后端后，在控制中心「系统 → 电脑操作」开启本机输入。默认每次启动关闭；鼠标或键盘的真实输入会暂停自动输入，通过本地「恢复控制」继续；「立即停止」独立于模型、截图和 UIA 队列。

`computer_use` 默认按需加载。模型先枚举、选择窗口并观察，再依据返回的设备 epoch、控制会话、观察、控件或截图引用操作。窗口属于当前执行 Satellite；宿主/云端 shell 路径不能直接当作该电脑文件路径。

个人 Chrome 使用同一个 `browser_page` 工具，参数 `session_source: personal_chrome`。依次 connect、list_tabs、select_tab；后续调用携带 browser_session_id、device_epoch，输入携带 observation_id。现有托管浏览器默认行为保留。

个人 Chrome 的设备需要 Node.js 和固定版本 `chrome-devtools-mcp@1.9.0`。首次运行项目脚本 `scripts/install_personal_chrome_adapter.ps1` 预热缓存；运行时仅离线启动适配器。控制中心开启个人 Chrome，并由用户在 `chrome://inspect/#remote-debugging` 开启连接、批准 Chrome 的提示。适配器退出只解除连接，不关闭个人 Chrome。不同连接可能再次请求许可。

## 状态与恢复

- `action_state`：not_started / executed / unknown；`observation_state`：complete / partial / failed。输入发生后截图失败保留 executed；未知执行结果不得自动重发。
- 用户接管后不能由模型重新选窗恢复输入。Chrome 只读观察可以继续，不更新输入许可或接管代次。
- 断线、旧 epoch、目标变化、过期观察和审批内容变化拒绝操作；重新连接/观察后继续。
- 没有应用送达回执时 delivery_confirmed 为 unavailable。QQ 的目标/草稿无法核实时要求接管，不用通用点击批准绕过发送边界。
- QQ 富文本使用 TextEditPattern，并核验 IsReadOnly=false、非密码、稳定身份和完整草稿。单凭控件类型或插入光标不授予输入许可。QQ 多行输入暂不支持，避免换行被应用当作提交。具体发送审批包含实际观察的会话和完整草稿；布局识别严格，不覆盖所有 QQ 版本。
- 操作 ledger 有 2048 条会话进程预算，不逐出仍可能重试的操作；预算耗尽明确返回原因，需要重启设备执行器。截图字节不驻留终态 ledger。
