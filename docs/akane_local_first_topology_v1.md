# Akane 本地优先拓扑契约 V1

## 目标

Akane 默认作为完整的本地应用运行；同一套 Akane Host 也可以部署到远程机器。部署位置可以改变，权威上下文和能力契约不能分裂。

## 三个角色

- **Akane Host**：唯一权威宿主。负责人设、会话、配置、MemCore 投影、插件与工具注册、模型请求和权限裁决。
- **Client**：桌宠、控制中心或 QQ 等交互入口。负责呈现和输入，不维护第二份正式上下文。
- **Desktop Satellite**：可选的设备能力提供者。只把看屏幕、桌面操作等明确能力交给 Host，不复制人设、MemCore 或会话决策。

## 支持的部署形态

1. **本地默认**：Host 与桌面 Client 在同一台电脑，开箱即可运行。
2. **远程 Host**：Client 连接一台远程 Host；远程地址必须显式配置，不得静默回落到本地 Host。
3. **远程 Host + Satellite**：远程 Host 仍是唯一大脑，本地 Satellite 只提供用户明确启用的设备能力。

本地与远程使用同一套 Host 实现、配置结构和工具协议，不维护“云端专用脑”或“本地专用脑”。

## MCP 执行位置

MCP 的执行位置由真实 transport 派生，不由 UI 猜测：

- `host`：`stdio` MCP 由 Akane Host 启动。Host 在本机时进程在本机；Host 在云端时进程在云端。
- `remote`：`streamable_http` MCP 是独立网络服务，Host 通过受信地址连接。
- `device:<id>`：为未来真实 Satellite MCP 预留；能力尚未接通前不得写入目录或提示词。

控制中心必须展示执行位置。完整命令、认证头、URL 和物理路径不进入公开摘要；受信配置接口仍可管理完成任务所需的真实配置。

## 不变量

- 全局只有一个正式会话与一个 MemCore 投影权威。
- Satellite 故障只能使对应设备能力不可用，不能创建第二条回复链或第二份记忆。
- MCP、内建工具和未来插件都进入同一能力目录与 CapCore 审批链。
- 执行位置是稳定能力元数据，不动态改写 system prompt，也不制造新的缓存前缀。
- UI、插件和宿主不得把 `host` 错写成固定的“本机”或“云端”。
- 未实现的远程编辑、设备路由和热重载不得以假按钮或假成功占位。

## 演进顺序

1. 完成 Host 上 `stdio` MCP 的持久生命周期与卸载体验。
2. 完成 `streamable_http` 的受信配置和健康检查。
3. 在真实 Satellite 能力协议稳定后，再引入 `device:<id>`。

每一步都应减少宿主自有分支；不能以并行维护旧注册表和新注册表的方式完成。
