# 本地运行链复查与修复 V1

2026-09-07。范围是桌面感知清理后的本地命令、QQ 文件、工作区与桌面工具衔接；
语音/ASR/RVC 链留在后续目标，不在这里宣称接通。

## 已确认的原因与处理

| 入口 | 真实证据 | 处理 |
| --- | --- | --- |
| QQ 文档读取 | `character.card.final.md` 的材料记录为 `remote_url_private_address`；域名解析进入 `198.18.0.0/15` fake-IP 段；已绑定 NapCat 的 `get_file` 成功，原文件已在缓存，但不在仅覆盖图片的配置根目录内 | 本地启动器开启 NapCat 现有 `enableLocalFile2Url`，复用后端已有的鉴权 base64 接收与解析，不新增下载器、不放宽任意 URL 或任意本机路径 |
| QQ 停止进程 | 用户确认未启动桌宠；实际能力目录的 `exec_run/status/cancel` 就绪而 `system_process_*` 离线；当时 QQ 原生工具记录同时包含两类工具 | 共用宿主提示明确两类工具的执行位置；自己启动的命令使用 `exec_cancel`，宿主上的其他进程用现有命令工具先查再操作；桌面离线结果不再笼统否定全部本地动作 |
| 系统浏览器能力展示 | 桌面离线时 `open_browser` 因缺少状态查询被目录默认标为就绪 | handler 绑定已有 Satellite offer source，以真实 receipt 判断可用性；不改变工具 schema 或执行路由 |
| “桌宠本机”提示 | 桌宠连接远端后端时，旧描述仍把执行宿主称作桌宠本机 | 改称执行宿主，避免错误推断两端 PID、路径属于同一台机器 |

模型继续负责根据用户意图选择已有工具；没有添加关键词路由、独立常驻服务、
云到本机自动回退或额外的群聊限制。现有身份、实例绑定、CapCore 策略和真实结果
确认仍然生效。尤其不能把某台桌面上的 PID 自动提交给另一台后端宿主。

## 扩查结论与边界

- 检查了实际本地能力目录和 QQ 原生工具记录：命令、项目/工作区读写、附件检查/
  重试/分段读取、文件交付、托管浏览器均存在；不能把离线桌面工具概括成“本地不可用”。
- 本地启动配置已允许托管浏览器访问本机网络；普通公网下载器仍按公网策略校验，
  fake-IP 代理环境下可能不适用。需要操作宿主文件或网络时，可由模型选择本轮
  已提供、已授权的命令工具；不把公网下载器偷偷改成无鉴权内网访问入口。
- 群聊存储身份与发起人操作权限分开。主人群聊可到达进程终止 broker；其他成员
  不继承主人的桌面控制权。原有审批与精确参数/设备绑定不变。
- 文件发送复用既有本地/远端 OneBot 传输，工作区按会话和材料句柄定位。组合回归
  覆盖这些调用链；本次没有向真实群聊发送测试文件，也未关闭用户的任意进程。
- 能力目录中未配置的语音/图像服务不等于本地权限被禁止；没有将缺失服务伪报就绪。
