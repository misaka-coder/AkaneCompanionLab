# 场景架构与迭代约束

状态：计划基线。以下路径、类型和字段为拟新增设计，不是当前已存在接口。

## 1. 四种数据各自负责什么

| 数据 | 权威来源 | 内容 |
| --- | --- | --- |
| 世界/角色状态 | 宿主动作与资源服务 | 角色、装备、场景、物品、养成状态及版本 |
| 交互事实 | 宿主确认事件 | 谁做了什么、成功或失败、发生时间、变化结果 |
| 演出内容 | 校验后的模型输出或固定事件 | 台词、表情、动作资源、播放顺序 |
| 播放进度 | 当前持有播放权的前端，宿主持久确认 | 哪段已显示、语音是否完成、暂停或中断 |

Pinia 是这些数据的前端投影。模型输出不能直接扣款、赠送物品、修改好感数值或宣称动作成功。自然语言调用工具与界面点击必须走同一动作入口。

首版场景由当前已绑定的 Bot、profile、角色和会话进入，不能硬编码 master 或重建匿名会话。日常行为的作用域沿用当前宿主策略；独立剧情存档另有 run_id。切 Bot/角色时取消旧订阅并递增客户端代号，旧响应不能覆盖新对象。

## 2. 建议目录与依赖方向

```text
desktop_pet_next/
  scene.html
  src/scene/
    app/                  # 装配、窗口生命周期、App.vue
    contracts/            # 生成的类型、schema 与版本检查
    domain/               # 纯 TS 状态转换、命令/事件、无 Vue/Pixi/IPC
    presentation/         # 演出队列、推进规则、取消与交付状态
    stage/                # StageRenderer 接口
      pixi/               # 图层、角色、命中区域、资源释放
    audio/                # TTS/BGM/环境音/音效调度
    features/
      dialogue/           # 对白、历史、推进控件
      wardrobe/           # 衣柜与试穿
      inventory/          # 商店、背包、投喂
      touch/              # 热区与反馈
      resources/          # 导入与资源抽屉
      story/              # 剧情呈现与选择
    stores/               # 按领域拆开的 Pinia 投影
    bridges/              # HTTP/Tauri/订阅/宿主旧接口适配
    ui/                   # 按钮、抽屉、提示、焦点等小原语
    styles/               # tokens、排版、场景布局
  src-tauri/src/scene_window.rs   # 窗口与桥接注册

companion_v01/
  routes/scene.py          # 校验并转发到服务，保持薄路由
  scene/
    contracts.py          # 新契约唯一字段定义
    actions/              # 按触摸/换装/投喂等职责拆分
    presentation/         # 模型输出校验、片段编排与回执
    resources/            # 导入、注册、变更事件
    story/                # 后续情节执行、变量与存档
    repositories/         # 持久化边界、迁移及版本控制
    adapters/             # care/角色包/MemCore/回合入口的窄适配
    composition.py        # 组装依赖，不承载业务规则
```

依赖方向：界面 → 功能协调器 → 领域/演出服务；桥接实现领域声明的端口；Pixi 实现舞台接口。Python 路由 → 场景服务 → 端口适配 → 现有宿主服务。

- `domain/`、演出队列状态转换不依赖 Vue、Pinia、DOM、Pixi 或 Tauri。
- 组件不直接 `fetch`、调用 Tauri 或操作数据库；store 不创建音频设备、ticker 或全局监听。
- `features/` 之间通过公开端口通信，不导入对方内部 store/helper。禁止循环依赖。
- Pixi 对象保持在渲染器内部，不进入响应式 store。所有 listener/timer/texture/audio 有明确所有者和释放方法。
- `engine.py` 仅允许必要的注入与委托；新动作规则、剧情和演出代码归入 `scene/`。旧 `web/app.js`、桌宠 `src/main.js`、Rust `main.rs` 同样只增加必要入口。
- 不把完整 engine/store 作为万能 context 传给所有模块；适配器只暴露真实需要的方法。

## 3. 防止新的大单体

- 新手写生产文件目标不超过 300 行；超过 400 行必须先按职责拆分，禁止以新增大 `utils`/`manager` 规避。生成文件与纯数据表单独排除。
- `App.vue` 与入口装配目标不超过 150 行；不在入口堆 watch、请求、音频、动画和业务判断。
- 不为凑行数机械拆函数。以独立状态、变化原因、测试边界判断模块职责。
- M0 建立针对新目录的文件规模检查、受限导入与循环依赖检查；历史大文件建立基线，不要求本轮拆全仓。
- `engine.py` 等集成大文件的 diff 必须检查：新增内容只能是注册/委托，业务函数数量不增加。
- 类型检查、契约一致性、边界检查加入场景验证命令。每次交付更新本计划状态与验证记录。

## 4. 交互动作：反馈与成功分开

```text
点击/自然语言工具
  → command（request_id + 对象作用域 + 预期状态版本）
  → 宿主检查权限、库存与动作条件
  → 提交状态变化和待发布事件
  → action_result + state_revision
  → 前端演出结果；事件进入普通 Agent 回合入口
```

按下按钮可立即有视觉/触觉式反馈，但扣物品、消费和已装备标记只在服务确认后生效；预览必须与已确认状态可区分。模型不可用时已完成动作仍成立，回应显示暂不可用并允许重试回应，不能重新扣款。

request_id 支持重复点击/网络重试去重；并发版本冲突返回新快照供重新判断。事实与待投递记录须有一致的提交边界，进程中断后可补投；消费者按 event_id 去重，不宣称跨服务天然 exactly-once。

本轮核对到现有 care API 与 desktop authority 契约，因此 M0 要确认每项字段现在由谁写入。新场景交易以宿主服务为入口，复用原规则和原台账；必须先消除同一状态的双写路径，不能简单再开第二份余额/好感/背包。

触摸即时反馈本地执行，默认约 800ms 防重复触发；短时间连续触摸合并，默认最多每 10 秒发起一轮触摸回应。换装/投喂成功产生各自事实事件，可合并模型回应但不能合并掉消费账目。参数集中配置，后续按体验调整。

## 5. 分段演出契约

继续使用纯 JSON。新场景协商 `scene_presentation_v1`，模型输出 `beats[]`，每个片段可包含 `speech`、`emotion_id`、`motion_id` 与 `advance`（click/auto/audio_end）。片段数量与文本长度设上限。

宿主校验并补充 turn_id、generation_id、beat_id、sequence、资源版本和关联交互事件；音频引用由真实 TTS 结果产生，模型不能伪造路径/资源 URL/执行回执。模型只能使用资源清单里存在的表达，未知项使用显式默认表达并记录诊断。

- 第一次点击补全当前打字；后续点击推进片段；队列耗尽后等待输入，点击不隐式请求模型。
- AUTO 等待文字和语音完成，再按可配置间隔推进。停止/换角色立刻取消当前播放代号，迟到语音不能复活旧演出。
- 生成、展示、听完分别记录。display_started、text_revealed、audio_started、audio_completed、interrupted 不混为“用户已收到整轮”。
- 固定动作反馈和模型回应进入同一播放调度，优先级默认用户输入/停止 > 当前交互回应 > 环境闲置反馈。
- 同一会话只允许一个主播放端；场景和桌宠通过宿主租约/代号交接，对端可以显示状态但不能重复 TTS 或重复确认交付。失联恢复通过快照与游标，不重放已完成内容。

首版等待完整有效 JSON 后按片段播放，避免不完整 JSON 被当成已提交内容。后续若做低延迟流式，增加带序号和完成标记的完整 beat 事件，不用临时正则解析半截 JSON。

新协议在最终输出生成、校验、传输、TTS、MemCore 和 UI 全链路接入。旧端的现有协议保持原状；新端不把整轮 emotion 复制到每一段冒充新能力。若需要旧端投影，集中在单一 output adapter，明确版本和移除条件，不到处写兼容分支。

MemCore 保留真实 provider 原文和工具轨迹；播放回执是附加事实，不改写原文、不重新序列化冒充 provider 输出。待呈现内容与已交付内容的下一轮投影需专项验证。

## 6. 资源与二维舞台

- 场景 manifest 描述背景、前景遮挡层、角色站位点、光照、音频和热点。坐标采用归一化场景空间，宽高比改变时统一变换，前端不散落像素常量。
- 首版两个站位点，支持角色偏移、缩放和预览校准；角色服装下可有不同的触摸区域与锚点。二维图层不承诺自动生成坐姿、透视或三维行走。
- StageRenderer 暴露场景/角色更新、播放动作、命中检测和 dispose；静态差分先实现，后续 Live2D 只替换角色渲染实现。
- 资源导入复用角色工坊的路径校验和原子更新机制。场景入口提供快捷导入，复杂校准仍进入工坊，不另造一套角色包权威。
- 图片先预览并识别用途，歧义时在前端选择背景/服装/表情；不把任意图片默认为完整角色包。情节包按版本化 manifest 校验引用、类型、尺寸和体积。
- 发布成功才更新 registry_revision 并产生 resource_added/updated 事件；加载失败保留上一有效版本。新请求看到新资源，当前演出固定使用已验证资源版本。
- 新增资源与装备/进入场景是不同事件。导入不暗中换装或进入剧情。
- 稳定目录确定性排序，不放时间戳、绝对路径、密钥和健康探针；变化事件追加在上下文尾部，正文与图片按需读取。功能变更导致的必要目录变更要诚实计入缓存变化。

## 7. 剧情和存档（M4）

采用版本化 JSON 情节包，首版由模板导入；未来编辑器输出同一格式。先实现固定对白/旁白、背景/音乐、角色表达、AI 对话、选择、变量和章节跳转。条件先支持布尔值与相等/不相等，校验器拒绝不支持的表达式。

宿主推进剧情状态；前端确认当前节点演出完成后才推进到下一节点，避免后台已经跑完而屏幕仍停在第一句。输入/选项节点等待真实用户输入；AI 节点才打开模型回合。每个副作用有 run_id/node_id/attempt_id，重入不重复执行消费。

存档保存包版本、章节和节点、变量、已确认动作、已生成片段与交付游标、场景状态、会话引用。通过实际重启恢复验证；有字段、有保存按钮不算完成。播放中的声音本身不持久化，恢复时按已交付状态重新定位。

首版只有一个活动剧情和手动检查点。重玩使用独立 run_id/剧情会话，日常持久库存与外部工具结果不可回滚。默认剧情里使用独立剧情道具；需要影响日常状态时，经显式宿主动作提交并去重。完成后由有依据的经历事件连接回日常会话。
