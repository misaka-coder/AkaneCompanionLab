# SUNDIAL 持久化工作流引擎：Akane × DSH 对比执行单 V1

## 一、实验目的

用同一项有真实工程深度的任务，对比 Akane 与官方 DeepSeek Harness 在以下方面的表现：

- 长程工具调用稳定性；
- 代码阅读、创建、局部修改与调试能力；
- 对并发、崩溃恢复、事务边界和失败语义的理解；
- 是否会做真实验证，而不是只完成表面功能；
- 最终交付是否完整、诚实且可复现。

本实验不以文件数、代码行数或工具轮数为目标。复杂度来自必须闭环的状态机、多进程竞争、故障恢复与一致性验证。

## 二、控制变量

- 两组使用下文完全相同的任务正文。
- 模型均使用 DeepSeek V4 Flash，并使用各宿主可提供的最高稳定推理强度。
- 权限均为 Full access / 完全访问。
- DSH 使用官方 `web` profile，不接入 MemCore。
- Akane 使用当前生产链路及 MemCore。
- 两组只允许工作区物理位置不同；均在各自当前获准工作区内新建 `sundial_engine/`。
- 不向任一模型补充实现提示、参考代码或测试答案；发生环境故障时只修环境，不提示业务解法。
- Python 兼容目标为 3.10+。可使用环境中更高版本解释器，但交付代码不得依赖仅在 3.11+ 存在的 API。

## 三、统一任务正文

你是一名资深 Python、SQLite、分布式任务调度与可靠性工程师。请从零实现一个可真实运行的本地持久化工作流引擎 **SUNDIAL**。

请在当前获准工作区中新建 `sundial_engine/`，不得修改宿主项目或系统 Python。项目必须兼容 Python 3.10+，只使用 Python 标准库与 SQLite，不联网、不下载第三方依赖。不要用假实现、只测常量、预写期望输出或跳过关键路径来通过验收。

### 1. 工作流定义与编译

工作流使用 JSON 文件定义，至少包含：

- 工作流名称与用户版本；
- 一组具有唯一 `task_id` 的任务；
- 每项任务的依赖、命令参数数组、可选环境变量、超时、最大尝试次数和退避参数；
- 可选的成功条件与产物声明。

编译阶段必须：

- 拒绝重复任务、未知依赖、自依赖和有向环；
- 生成稳定拓扑序；
- 对语义等价的定义产生一致的规范化内容哈希，不受 JSON 键顺序、空白、绝对工作区路径和机器时间影响；
- 命令必须以 argv 数组执行，不能偷偷拼成 shell 字符串。

### 2. SQLite 持久化状态机

使用 SQLite 保存工作流定义、运行实例、任务状态、尝试记录、租约和事件。至少支持：

- `pending / ready / running / retry_wait / succeeded / failed / cancelled / skipped`；
- 合法状态迁移校验，非法迁移必须结构化失败；
- 每个运行实例内单调递增、无重复的事件序号；
- 关键写入使用显式事务；
- 多进程同时竞争时，一个可运行任务只能被一个 worker 成功领取；
- SQLite 的 journal、busy timeout 与同步策略必须有明确选择并写入文档。

### 3. Worker、租约与崩溃恢复

实现可由多个独立进程同时运行的 worker：

- 原子领取 ready 任务并写入 owner、lease deadline 与 attempt；
- 运行期间续租；
- worker 崩溃或被强制结束后，过期租约能够被其他 worker 恢复；
- 恢复不能重复提交同一次尝试的终态，也不能让下游在上游未成功时执行；
- 对外部命令执行只能诚实承诺 **at-least-once**。为每次尝试提供稳定的幂等键，并通过环境变量传给子进程；不要声称实现了无法证明的 exactly-once 外部副作用。

### 4. 任务执行

- 使用 `subprocess` 的安全 argv 形式启动任务；
- 分别捕获 stdout、stderr 和退出码；
- 大输出不得全部常驻内存或无界写入 SQLite，应流式落盘并在数据库保存有界预览、长度、SHA-256 与相对产物路径；
- 支持超时，并尽力终止整个子进程树；
- 支持运行级取消：不再启动新任务，并终止或回收正在运行的任务；
- 支持有限重试与确定性退避；测试不得依赖分钟级真实等待；
- 失败任务使依赖它且无法继续的任务进入明确的 skipped/blocked 语义，而不是永远 pending。

### 5. 恢复、检查与可观测性

提供命令行接口，至少具有等价于以下能力的命令（名称可合理调整）：

- `init`
- `register <workflow.json>`
- `start <workflow>`
- `worker`
- `status <run_id>`
- `events <run_id>`
- `cancel <run_id>`
- `recover`
- `check [--full]`

要求：

- 人类文本输出与 `--json` 单 JSON 文档输出都可用；
- 错误具有稳定的错误码、非零进程退出码和可操作说明；
- `status` 能展示每项任务、当前尝试、最近错误与整体结论；
- `recover` 幂等，多次执行不能损坏已经提交的状态；
- `check --full` 校验数据库引用、事件序号、状态不变量以及输出文件长度和哈希；
- 事件日志足以解释一次任务从 ready 到最终状态的关键路径，但不得记录密钥等敏感环境变量值。

### 6. 故障注入

设计明确、默认关闭的故障注入机制，至少覆盖：

- 领取任务事务提交之后、启动子进程之前；
- 子进程已经结束、保存终态之前；
- 写入输出文件过程中；
- 运行取消过程中。

故障注入必须让新进程能够验证恢复结果，不能只在同一 Python 进程里模拟异常后继续。

### 7. 测试与验收

必须提供自动化单元/集成测试以及一个可独立运行的 `scripts/acceptance.py`。验收至少真实覆盖以下 18 个场景，并逐项报告 PASS/FAIL/SKIP；除确有平台限制且说明原因外，不得静默跳过：

1. 单任务成功，stdout/stderr/退出码/哈希均正确；
2. 菱形 DAG 只在依赖成功后执行，稳定拓扑与事件顺序可解释；
3. 重复任务、未知依赖和环分别被拒绝；
4. 相同语义、不同 JSON 键顺序得到相同定义哈希；
5. 两个独立 worker 竞争同一任务，实际只产生一个有效领取者；
6. 多个互不依赖任务能被多个 worker 并发完成；
7. worker 在领取后崩溃，租约过期后由新进程恢复；
8. worker 在子进程完成后、提交终态前崩溃，恢复结果无双终态、无错误下游放行；
9. 失败任务按配置重试，尝试次数和幂等键正确；
10. 重试耗尽后，依赖任务进入明确的 skipped/blocked 状态；
11. 超时任务被终止，状态、事件和错误码正确；
12. 运行中取消后不再启动新任务，已运行任务得到明确终态；
13. 至少 8 MiB 输出流式处理，数据库只保留有界预览，完整文件哈希正确；
14. 输出文件被篡改后 `check --full` 能定位 run/task/attempt/path；
15. `recover` 连续执行两次结果一致；
16. 两个不同工作流/运行实例相互隔离；
17. `--json` 成功与失败输出均为单个合法 JSON 文档，退出码契约正确；
18. 端到端：register → start → 双 worker → 中途故障 → recover → 完成 → full check，并验证最终状态与产物逐字节一致。

另外提供一个不追求跑分、只用于暴露数量级问题的 benchmark：生成约 1000 个任务节点的 DAG，报告注册、调度到完成、事件查询与 full check 的耗时和峰值内存。可以使用快速的内置空操作任务，结果必须来自真实运行。

### 8. 工程交付

至少交付：

- 完整源码与清晰的模块边界；
- `README.md`：架构、状态机、事务边界、租约语义、at-least-once 边界、运行命令和已知限制；
- `docs/design.md`：关键不变量、崩溃窗口分析和恢复策略；
- 自动化测试；
- `scripts/acceptance.py`；
- `scripts/benchmark.py`；
- 示例工作流。

完成前必须实际运行测试、验收脚本和 benchmark。修复真实失败后再汇报。最终报告应包含项目绝对路径、实际命令、测试数量、18 项逐项结果、故障注入证据、性能数据、未验证项与已知限制。不要把计划、尚未运行的测试或模型自述当作完成证据。

## 四、验收与盲审口径

两组都完成后再验收，不在运行中依据输出风格提前评分。最终审查：

1. 直接读取源码与测试，确认不是自述式完成；
2. 在各自项目目录重新运行测试与 acceptance；
3. 抽查并发领取、租约恢复、终态提交和取消的事务边界；
4. 检查大输出是否真正流式、检查器是否真正发现篡改；
5. 比较工具轨迹中的失败恢复、重复劳动、长程稳定性和最终交付质量；
6. 将环境差异、模型差异与宿主工具差异分开归因。
