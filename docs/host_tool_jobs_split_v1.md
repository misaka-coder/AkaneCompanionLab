## 调用链与状态归属

工具编排仍通过原入口调用 `accepts`/`submit`，Bot 工厂继续创建同一个 `HostToolJobRuntime`，将其接到既有 `HostJobStore` 和 `BackgroundTaskRunner`。执行、工作流和子代理继续共用它的完成通知发布入口。`_artifact_references` 仍从原入口供执行处理器、子代理和插件产物投影使用。

各职责组合在同一实例中，继续共享 `_scheduled`、`_completion_scheduled`、`_admitted_handlers` 和 `_lock`。没有新增任务数据库、独立调度器或状态副本。任务执行与完成通知仍使用原有的两条队列，避免正在执行的慢任务阻塞通知。

插件引用保留仍在任务锁外完成，保留原来的锁顺序；释放也在任务锁外进行。正在运行的任务不会因停止请求被伪造为已经取消，实际取消确认、取消后仍成功的结果和产物按原规则保存。结果未知的已运行任务仍由共享 Store 隔离，不在此执行器重放。

## 同轮复现与修复

1. 处理器释放失败时，调用方清理会覆盖已经接受的任务回执；执行方清理会跳过后续通知。现在引用释放失败单独记录原因类别，继续返回任务回执或发布原有终态。日志不输出清理异常正文，不声称失败的释放已经成功。
2. 任务已登记但调度失败时，原回执丢失任务编号，并错误声称“没有成功登记，因此尚未开始”。现在回执保留 `job_id`、实际 `job_status`、`control_state` 和失败原因，工具上下文据此描述现有任务。若任务已经由其他执行方领取，保留该领取及运行事实。
3. 为执行方再次保留处理器引用失败时，异常直接抛出，已登记的新任务仍留在队列。现在通过同一提交失败分支处理；只有本次创建、仍可被本次领取的新任务才写入失败。重复提交的引用保留失败不会停止或覆盖原来排队的任务，也不会释放其有效引用。
4. 调度前失败已经通过当前工具调用返回时，原任务仍待完成通知，后续恢复会再次通知角色。现在仅在新任务失败已确认后，按既有子代理提交失败的规则确认该完成事实在当前调用返回，避免再次唤醒角色；静默任务继续遵守原策略。若数据库读写无法确认，保留实际记录，不伪造已结算或已交付。
5. 无法序列化或包含循环引用的调用在指纹阶段直接抛异常。现在返回既有 `host_job_payload_not_json_safe`，在持久化和派发之前拒绝，释放调用方引用。首次处理器选择/引用失败也只记录原因类别，避免将异常中的私有正文写入日志。

新增 `tests/test_host_tool_job_boundaries.py` 的 13 项检查使用真实临时 SQLite 和后台队列，控制释放/保留故障及排队顺序；只在调度故障、并发领取与数据库失败处注入故障。覆盖接受后的清理失败、终态通知、提交失败回执、重复请求归属、另一领取方的实际运行状态、无法序列化的调用，以及数据库领取/保存/查询失败时的真实状态。首批 10 个方法在修复前均复现失败，补充 3 个方法验证新增收尾分支的数据库失败处理。旧测试断言未改动。
