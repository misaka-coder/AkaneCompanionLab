# 前端与后端接线审查

日期：2026-10-13。基于当前工作区源码，而非已安装的桌宠 EXE。

大部分常用页面仍连接着有效的后端。问题集中在两类：有些旧设置只保存一个值，没有实际效果；有些较早做的独立功能复用了底层模块，却没有跟上后来统一的身份、会话和状态入口。后续前端重做应围绕现有真实能力整理入口。

## 1. 目前各入口实际做什么

| 前端入口 | 实际调用与数据归属 | 判断与后续方向 |
| --- | --- | --- |

| 片刻小屋 | Vue/Pixi 呈现 → `/scene` → 独立房间、剧情、呈现服务，同时调用 Engine 与 Care 底层 | 有完整实现，不属于死代码。但会话、养成和商店接线与当前主线存在落差，见第 3 节 |

## 2. 本轮已经修好的问题

### 2.1 清除没有执行效果的语音设置

桌面全局的 `voiceSpeed`、`wakeWord`、`wakeSensitivity` 原来经过表单、桥接、保存和确认回执，但没有进入合成请求、播放速率或唤醒检测逻辑。界面上的保存成功只证明状态对象变了。

本轮删除了这三个设置的 UI、表单控制器、动作登记、确认分支、主窗口处理器、快照字段和专属样式。加载旧状态时忽略旧字段；旧窗口发送对应命令时，由现有未知命令分支返回 `not-supported`，不会再报设置成功。

现在语音页保留播放开关、音量、语音输入、试听、服务状态和角色声线配置。声线档案中的 `speedFactor` 是有效的合成参数，未移除。QQ 的消息唤醒规则是另一条链路，未改动。

### 2.2 小屋不再擅自改连接身份

旧浏览器连接读取把保存的 `12001` 地址或 `master` 用户判定为测试配置，丢弃整份连接，换成写死的 QA 地址、用户与会话。连接面板还维护了第二份同样的默认值。

本轮移除该判断，统一连接默认值和归一化。已保存的真实配置保持原样，URL 只覆盖明确提供的字段；留空 Bot 可以继续使用宿主默认 Bot。首次浏览器打开使用项目通用地址，不再自动创建 QA 用户、会话；用户与会话需要明确填写。Tauri 启动仍使用已有实例绑定和桌宠状态。

### 2.3 私有小屋读取补齐现有认证

`/scene/snapshot` 会读取养成、背包和房间状态；`/scene/story/catalog` 还带有当前剧情节点、进行状态及已完成结局。之前这两个接口没有调用小屋其他接口已有的认证。

本轮补齐相同的宿主认证；Tauri 的快照读取改走已有 `backend_admin_request`，原生代理的地址名单同时加入快照，并将原来只称作“写入路径”的判断改名为小屋管理路径，与剧情及其他小屋请求一致。默认本地兼容实例仍允许本机使用；要求凭据的实例在认证通过前不会读取目标用户状态。没有新增一套凭据或授权框架。

## 3. 小屋后端需要跟上当前会话设计

### 3.1 相同的 Engine 不等于相同的主人会话入口

普通桌宠聊天会在可信 HTTP 入口标记来源，经过 `OwnerPrivateSessionPolicy` 确定共享记忆与协调身份，再进入队列、工具轮和交付链。

小屋 `scene/composition.py` 则以请求中的用户和会话直接申请协调锁，再调用 `engine.process_turn`。呈现与剧情消息虽然设置了 `client_mode=desktop_pet`，但没有普通入口签发的 `_memory_desktop_ref`。当前主人共享策略需要这个可信来源，因此仅在面板填写同一个用户名并不能保证共享主人私聊记忆，也不能保证使用同一个会话锁。

它确实运行同一个模型/工具引擎，并非另一套模型循环；欠缺的是统一入口的接线。后续应让小屋和剧情共用主线的可信身份、协调与入站服务，同时保留小屋自己的房间数据、剧情进度、`beats` 呈现和交付回执。不要让前端直接指定内部共享记忆 ID。

### 3.2 小屋养成绕过了会话状态的选择

普通桌宠经 `build_desktop_care_snapshot`、`manage_desktop_care_action` 选择会话身体、关系对象与共享账号。小屋 `CarePort` 直接调用底层 CareRuntime，没有传递 `session_id` 对应的会话范围、关系对象和 `shared_account`。

底层默认会把会话与关系回退为用户 ID。因此小屋的不同会话可能共用默认角色状态；与主人主线相比，部分身体数值偶然相同，也不能说明好感和个人账号都已正确共享。

后续小屋适配器应调用现有养成服务来确定归属，房间自己只保存布景、位置等呈现状态。切换身份前后要验证：主人桌宠/私聊共享应共享的部分；不同会话角色状态按现有规则隔离。无需再建一套养成数据库。

### 3.3 小屋另写了一份商店编辑规则

主线 `/desktop-pet/care/shop` 使用 `care_shop_settings.py` 的读取、创建、修改和删除服务。小屋 `CarePort.add_shop_item` 自行生成 ID、查重、修改角色 JSON 和替换文件。

两边的最终文件有关联，但两份编辑规则容易在后续迭代中分歧。宜复用主线的商店服务，小屋保留表单和展示。已有商品不应因入口收敛而换 ID 或重新导入。

本轮只修小屋连接与认证，没有迁移已有房间、角色状态或记忆。以上三项适合在确定小屋未来界面后作为一个完整接线任务处理，避免只改记忆归属却漏掉锁、养成或工具上下文。

## 4. 控制中心还有两处可收敛的后端设计

### 4.1 聚合快照与工作台专用入口不完全一致

`/control-center/snapshot` 一次读取健康、诊断、工作台、资源、指标和执行策略等七个字段；前端随后再读取能力、声线和审批目录。后端这七个字段目前逐项读取。工作台已在线程中读取，不能据此认定它阻塞了模型或是聊天慢的原因，本轮也没有做生产耗时结论。

更明确的差异是：聚合快照的 `_build_snapshot_workspace` 直接按查询用户、会话调用 Engine；工作台专用路由还经过主人素材范围处理。共享主人资料的前提不同，可能出现两个页面看到的文件集合不同。

后续应复用专用入口背后的资料读取服务，并核对私有字段的身份、认证和素材范围。等新导航确定后，再将较重的能力、诊断、工作台数据按页面需要加载；不要只为了减少 HTTP 请求把所有数据再塞进一张更大的快照。

### 4.2 通用动作兜底（后续清理已完成）

本次初步审查查到 `/control-center/actions/{actionId}` 固定返回 `not-implemented`，前端在无法使用部分动作时仍请求该兜底。2026-10-13 后续已核对消费方，删除通用空路由与前端兜底请求；动作不可用时直接返回已有的不可用结果。真实动作继续由设置桥接、Tauri 命令或明确的后端处理器实现。

完整清理记录及其他兼容逻辑的保留理由见 [兼容逻辑与架构清理审查](architecture_compatibility_cleanup_audit_v1.md)。

任务控制中的 `/admin/plugins/jobs/{id}/control` 名字也较早，但实际调用的是通用 HostJob 服务；仅凭 URL 里的 `plugins` 不能认定它只能控制插件任务，本轮保留。

## 5. 前端重做的建议顺序

1. **日常入口先收拢。** 桌宠保留聊天、语音、换装、播放、手边和一个设置入口。开发工具、深度诊断、角色包创作放到对应页面，避免右键菜单再重复一遍完整设置。
2. **按使用目的组织设置。** 日常设置、模型与服务、能力管理、角色创作分别有明确入口。同一份后端数据可以被引用，但不要在多页重复铺开完整编辑表单。
3. **单独接回小屋。** 先复用主线身份、协调、养成和商店服务，再决定小屋与桌宠如何呈现。这个任务比单纯改布局更值得优先完成。
4. **随页面精简读取与旧兜底。** 以实际页面消费为依据收敛快照和动作入口。保留当前失败、空态、慢请求和切换对象的处理，不新增与实际需求无关的限制。

聊天模型循环、工具并行/后台任务、历史投影和 MemCore 压缩无需为了重新布局再改一次。本轮没有修改聊天提示词或这些链路。
