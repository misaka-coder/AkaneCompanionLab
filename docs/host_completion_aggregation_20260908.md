# 后台任务完成事件聚合（2026-09-08）

## 范围与权威

把同一来源回合、同一授权/角色/交付上下文中已经完成的 Host Job，集中交给角色 Agent 处理。
不是文件插件特例，不新增任务执行器、内存通知队列、发送协议或 Provider 原生异步模式。

- `HostJobStore` 仍是任务执行、终态、产物和完成事件 ID 的唯一权威。
- `SessionInboxStore` 仍是输入持久化、FIFO、领取、恢复和结算的唯一权威。
- `DurableSessionWorkQueue` 每会话只运行一个处理信封，不同会话并发。
- QQ 与桌宠使用同一个 `host_completion_batch` 投影；正常工具/发送/表现链不被替换。
- 工作流的 `silent`、内部任务的 `silent + current_turn` 不会被聚合错误唤醒。

## 领取时聚合，不等待所有任务

完成事件先逐条可靠入箱。消费者准备处理下一项时，在同一 SQLite 事务中领取连续、已就绪且兼容的完成事件。
首个用户消息、其他插件事件、其他来源回合、不同授权或未就绪输入都是边界，不能跨过它们拼接后面的结果。

没有额外 debounce 定时器，不等待原请求全部任务完成，也不增加模型轮询工具：

- 模型忙期间 11 个任务都完成：下一轮可以一次处理这 11 个结果。
- 第一个完成时模型空闲并已经开始处理，随后另外 10 个完成：通常形成 `1 + 10`，不是保证永远一轮。
- 还有任务很慢：已完成结果先处理，慢任务完成后再入箱。
- 同一个后续轮次仍可能包含多个 Provider 请求，例如发送工具调用及最终总结。

默认每个信封上限为 32 条输入、65,536 字节原始 inbox payload。它们是有界读取/上下文保护，不是提交任务总量或并行执行上限。
超过上限的后续输入继续留在原队列，不截断或丢弃；超大单项仍完整单独处理。
`DurableSessionWorkQueue` 构造参数可调整边界；已领取的持久化批次重试时不会因为新边界被拆开。

## 隔离与协议

只对宿主来源 `host.jobs` 的终态事件启用，且必须具有原始 `origin_turn_id`、任务 ID 和匹配的完成事件 ID。
插件事件端口会替换调用方声明的来源，普通插件不能伪装成 `host.jobs` 进入这个策略。
旧的无来源回合事件仍按单项处理。

分组比较包括：

- 实例自己的队列、渠道、session key、profile/session、原始回合；
- 经宿主验证的会话引用上下文，包括群聊因果成员与授权 profile；
- 角色、回复/模型路由、记忆模式、呈现策略及其他执行上下文字段。

只排除明确的逐事件内容字段。新增上下文字段默认成为隔离边界，避免将来新增授权字段时忘记更新白名单。
批次只是通知外壳，各任务的原始完成事件 ID、job ID、tool call ID、能力、状态、错误与 artifact 句柄仍分别保留。
启动任务的 `accepted + job_id` 仍是原工具调用的完整结果，不伪造迟到的 `function_call_output`。

## 持久化与重试

inbox 原表增量增加三个字段：

- `batch_id`：第一次领取时冻结成员，单项完成事件也冻结；后续重试不吸收新任务。
- `input_fingerprint`：由宿主对不可变事件事实、授权上下文和交付政策计算。相同事件的重复通知沿用首次入箱的内容快照，不因重试时间或指令文案变化产生第二轮；不同事实/身份返回 collision。
- `processing_started_at`：在进入可能发生外部动作的角色处理前落盘。

批次的领取与结算都在事务中完成。部分/过期领取者不能确认整批，也不能单独确认一名成员。
长处理期间续租；结束时的空队列检查与消费者退休之间到达的新输入会再次检查，不遗留未唤醒通知。
重试延迟的队头不能被后来的输入越过。

### 外部副作用不能靠任务 ID 保证 exactly-once

如果 QQ 已经接受发送，但进程还没记录回执就崩溃，本地数据库无法判断远端是否实际发送。
因此不能通过无条件重放整个模型回合来假装可靠：

- 尚未开始处理：排队、离线等待、崩溃恢复可以安全重试，原批次身份不变。
- 已开始但未确认结果：取消、失联或重启后保留为 `failed / session_turn_outcome_unknown`，不自动重放模型及其动作。
- 已知模型/交付失败：inbox 不再记作成功 committed，也不自动重跑已成功的生成任务。
- 部分发送成功：保存现有逐文件回执，整个后续处理标记失败，不能自动再发整批。

`session_turn_outcome_unknown` 表示需要核查，不表示外部动作未发生，也不表示底层线程已经停止。
这类记录保留在现有 inbox，可结合任务终态、现有文件交付状态和真实渠道消息核查后明确重试需要的产物。
本切片没有新增人工核查 UI，也不为未知结果自动启动一轮模型回复。
未来若要自动恢复这种窗口，必须先有渠道级幂等发送/持久化动作回执或可恢复的 Agent continuation，不能直接放宽上述保护。

## 文件与表现

生成结果依旧不自动发送。Agent 集中看到句柄后，按原请求的交付意图调用已有 `send_file(targets=[...])` 等能力。
QQ 仍可以逐文件传输；节省的是逐文件重新启动角色处理的开销，不承诺一次 QQ API 传输所有文件。
“产物可用”“已提交发送”“真实渠道确认”继续区分，不能把 Host Job 的 completion delivered 当作文件已收到。

单项与批次完成通知都明确：未列出的任务状态未知，不能凭一个完成事件说其他任务仍在生成。
批次不改稳定 system prompt 或工具 schema；完成事实只进入本轮输入和现有 MemCore 事件投影。
正常 QQ 回复与桌宠完整 frame（文字、分段、表情、activity 等）继续走原来的渲染/交付入口。
队列完成日志增加 `batch_count`，不记录原始结果或宿主物理路径。

## 验证与部署边界

新增测试覆盖：

- 11 条终态输入合成一轮；忙期间新完成结果下一轮集中领取；极慢任务不阻塞已完成结果；
- 用户输入、来源、角色、授权/模型/未来上下文字段的隔离；
- 同批原子结算、旧数据库升级、重启、过期 token、冻结成员、分块不丢尾项；
- 长处理续租、退出瞬间新输入不漏唤醒、延迟重试 FIFO；
- 已开始的未知结果不自动重放、重复通知不覆盖首次入箱内容、改变事实拒绝；
- Host Job 实际投影经过 QQ/桌宠路由与 durable queue，进入一次正常处理；
- 真实临时文件登记、真实 `SendFileToolHandler`、正常 QQ 网关文件选择入口一次处理 11 个句柄；
- 部分发送失败不 committed、失败生成结果不被成功结果覆盖；
- 实际 Engine 事件解析和 MemCore 渲染保留每个任务与产物。

测试替换了模型响应与外部 QQ 传输，因此它们是进程内调用链验证，不是实际用户收到文件的证明。
不在本切片修改云端配置、角色包、模型设置、UI/CSS 或旧 Electron 桌宠。

验证记录：

- 核心队列/聚合、事件路由、BotRuntime、各类 Host Job：131 项通过；最终错误原因细化后再次执行相应聚合与渠道测试。
- 文件、原生工具 schema、工具并行配置、子代理引擎：61 项通过。
- 原始路由回归有 11 项受此前 QQ 自动昵称变更影响；在 `HEAD` 路由上复现其中两类失败。只在测试进程模拟 `_resolve_bot_nickname = Akane` 后，103 项路由测试通过。没有为消除这些旧测试假设而改回运行时硬编码昵称。
- Python 编译、变更范围 Ruff、`git diff --check` 通过。
- 未重启本地运行实例、未部署云端、未向真实 QQ 会话发送验收消息；加载新实现仍需重启相应后端。

升级时先确认没有活动模型回合，再正常停止旧进程。已存在的旧式 inbox 输入保持单项处理；不要在仍有冻结批次待结算时切回不认识批次字段的旧队列代码。

参考依据：DSH 本地 `packages/jobs/tool-jobs` 区分忙时注入和空闲唤醒；本实现没有复制其内存通知/唤醒预算机制。
Responses 的多结果收取语义参考 [官方异步工具文档](https://developers.openai.com/api/docs/guides/async-tool-calling)，但本实现不依赖该 Provider 功能。
