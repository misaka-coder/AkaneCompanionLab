# 主人私人对话单向写入群记忆执行单

日期：2026-10-04。状态：已按审阅方案实现，离线验收通过；真实群聊和上游缓存率待启用后验证。代码核查基线：`364a9176` 及当前工作区；已有未提交改动保留。本次实现未启用实际接收群、迁移历史、重启或提交。

补充讨论核查基线：`22b749c7` 及当前工作区。以下方案已落地；当前记忆显式读取与文件会话归属仍是两套独立机制。具体实现及验收限制见第 10 节。

## 1. 目标与已经确定的边界

主人与同一角色在 QQ 私聊、已绑定桌宠中的一轮真实交流完成后，将主人消息和助手最终回复作为独立副本追加到该角色已经开启接收的已有群会话。群聊照常处理自己的消息，将这些副本纳入本群原始历史，随后独立生成阶段摘要和长期记忆。

这项能力是写入时的单向复制。源私人会话仍是现有的共享私人记忆；每个目标群拥有自己的副本、压缩标记、摘要和检索来源关系。

- 只复制真实、已落库、已完成且有可见最终回复的私人聊天轮次；包括桌宠已正式落库的文字或语音转写交流。
- 复制主人输入与助手最终回复，保留真实来源、人物、原始事件时间、回复配对和有效记忆标注。已有追加输入应归入其原轮次，不能错配到下一条回复。
- 第一版不复制工具调用、工具结果、中间进度、系统提示、能力目录、主动观察事件、临时语音候选或投递控制记录。不为没有最终回复的轮次制造回复。
- 群消息不反向复制进私人会话；私人阶段摘要和长期记忆不搬运、不同步。
- 复制不触发群聊模型请求、主动搭话窗口、QQ 发消息、养成结算、金币或背包变化，也不重放助手历史里的工具或状态操作。
- 保留各端当前提示词、输出字段、语音合成、权限及显式跨会话检索政策。不同 Bot、不同角色、普通用户私聊和售货员等辅助人物不混入。
- 每个群独立决定是否自动接收，默认关闭；接收开关不同时授予私人文件权限，也不改变原来显式跨会话读取的开关。
- 第一版只从启用后的新完成轮次开始，不回填旧私人历史，不重建已有群历史。不为新加入的群补发启用前或入群前的记录。

## 3. 复制范围与启用方式

新增宿主侧开关 `OWNER_PRIVATE_GROUP_MEMORY_MIRROR`，默认关闭，接入现有配置和设置目录，按重启生效。要求 `MEMORY_BACKEND=memcore`、主人 QQ 已配置且 `OWNER_PRIVATE_SESSION_SHARED` 已启用。此开关不修改已有主人双端绑定及显式检索开关的含义。

同时在现有 QQ 偏好存储增加各群接收设置，默认关闭，运行时生效；当前 Bot 的设置存储继续独立，各群互不覆盖。实际复制条件为“宿主功能已启用 + 本群明确开启 + 同角色真实群会话符合范围”。不增加工具同步、文件同步、摘要同步等多档模式。

新增斜杠指令 `/私人记忆 [开|关|状态]`，无参数查询当前群；归入 `/help 群聊`。群内沿用现有目标 Bot 寻址，只允许核验后的主人修改，不把普通群管理员身份作为读取主人私人经历的授权。保存失败明确失败并保留原设置，不出现只在内存开启但重启失效的假成功。主人查询状态时还能看到本群待写入、重试数量及安全的错误类型。

源仅限宿主已核验的主人 QQ 私聊，以及已经绑定共享私人会话的主人桌宠。同一角色分别处理；未绑定的桌宠不纳入。来源和主人身份在可信入口或完成登记时冻结到持久记录，恢复不能依赖已经结束的请求 ContextVar。

目标使用本实例、当前 Bot、同一正式角色下已建立的真实 QQ 群会话，再按各群接收设置及已有排除配置过滤；不向其他角色域写入，不因副本创建新的群或角色会话。复制目标及对应接收配置版本在登记时冻结，之后出现或刚开启接收的新群只接收其后的新轮次。

启用边界由各群配置版本及最终完成收口时冻结的目标清单确定，未用用户消息开始时间过滤。登记仅接入新的最终完成收口，不扫描或回填旧记录；重启只恢复已经登记的待复制记录。登记序号用于同群待复制顺序，不额外扫描私人历史来推进恢复游标。

关闭后停止新登记及待复制执行，保留已写群副本与待处理状态。重新开启后按原身份去重续办已经登记的任务，关闭期间未登记的历史不自动回填。删除旧副本或撤销已形成摘要不属于普通开关操作。

上段描述宿主总开关的暂停与恢复。单个群关闭接收时，该群尚未导入的副本终止为 `skipped_disabled`；已经写入的历史与摘要保留。重新打开只接收重新开启后的新完成轮次，不补发停用期间的记录或复活旧 pending。使用配置版本或启用水位处理关→开的竞态，执行前再次核验接收设置；重试不能绕过主人新关闭的选择。

本群关闭自动接收，不表示撤销原有显式私聊记忆检索权限。该权限继续由现有跨会话检索设置管理，界面或指令的状态说明只描述自动接收，不能把它说成“本群完全无法知道私人记忆”。

## 4. 写入与并发：完整轮次末尾追加

### 4.1 最小数据流

```text
主人输入 -> 私人模型/工具链 -> 最终回复准备提交
                                   |
                                   v
                         预登记持久待复制候选
                                   |
                         私人最终回复与标注提交成功
                                   |
                         唤醒队列，核验源轮次已 closed
                                   |
                      对各目标群独立处理、失败独立重试
                                   |
               取得该群的会话协调边界，当前任务已结束
                                   |
               原子追加完整私人轮次 -> 记录该目标已完成
                                   |
               本群下一轮正常读取、压缩、检索这些新记录
```

预登记是轻量持久操作，避免私人最终提交成功、宿主尚未收到成功返回时退出而漏复制。候选源尚未 closed 时只等待，不写半轮；重试以该源轮次实际保存的唯一 final 为准。私人回复不等待各群导入、索引或摘要模型。等待目标群空闲采用现有异步协调方式，不同步等待另一个群的模型。无需新增模型驱动的同步服务或全局聊天锁。

### 4.2 时间与配对

- **真实时间戳**说明消息何时发生：保留私人输入和最终回复各自的原时间，不改成复制时间。
- **目标群写入序号**说明何时进入本群历史：分配新的本群序号，整轮追加到末尾。
- **本群副本轮次 ID**及回复来源关联说明哪条回复属于哪段输入：独立于私人源轮次，不能仅凭相邻时间猜测。

示例：私人输入 12:00:00，群输入 12:00:01，群回复 12:00:05，私人回复 12:00:08。本群依次保存群输入、群回复、私人输入副本、私人回复副本；副本仍显示 12:00:00 和 12:00:08。不得为了使时间戳递增而重排旧历史。

如果私人先完成而群任务还在运行，整轮副本暂存，等群任务最终回复落库并结束后再追加。等待范围包含整条原生工具链及最后收口，不是某一次模型响应结束。正在运行的群任务继续使用原有上下文，下一轮接上副本。

待复制的读取与群请求的上下文构建必须经过同一个会话协调边界：不能只 `is_busy()` 一次后直接写入，以免检查后群任务启动。优先在下一轮群任务读取历史前排空已登记副本，并为闲置群安排使用同一边界的轻量导入。多个 pending 按源完成顺序处理；重复通知不改变顺序。

### 4.3 原子性、去重与恢复

- 去重身份至少包含运行 Bot、角色、原私人轮次、目标群；副本消息 ID 再区分输入与最终回复。身份稳定，重试不重新随机生成。
- 保留原私人轮次、消息及角色来源凭据，供宿主追踪。目标群消息使用自己的 ID、轮次及压缩标记，不能复用源记录的数据库主键。
- 整轮导入必须原子可见；出现失败时，群模型及压缩不得读到只有用户输入的半份副本。
- 优先复用现有公开 V2 写入接口。若其不能原子提交已完成轮次，在 MemCore 增加最小通用的已完成轮次写入能力；宿主不调用 SQLite 私有方法或直接改 MemCore 表。库接口不包含 QQ、主人、群列表或业务开关。
- 待复制及每个目标的完成状态需要持久化，记录 `pending / applied / retry_pending / skipped_disabled` 等必要状态及简短原因。一个群失败不能阻塞其他群或私人聊天；成功目标不再次写入，停用目标不当作失败反复重试。
- 覆盖“私人完成提交后尚未登记”和“群副本已提交但尚未确认任务完成”两个崩溃窗口。优先复用已有完成日志；需要恢复补偿时，只按持久水位增量读取新完成记录，不在每条聊天请求中遍历历史库。
- 导入失败保留真实原因，使用有退避的重试；不能伪报成功、吞掉记录，或重发原 QQ 消息。
- 普通失败、取消、静默、没有最终回复或 `append_final=False` 的轮次不拼造完整私人交流。流式发送的前半句、重试中的旧候选都不能提前复制。

## 5. 来源、人物与模型可见渲染

### 5.1 聊天历史

沿用已有用户消息格式，不另造群聊转述模板。复制 QQ 私聊时补上宿主核验的主人 actor；复制桌宠时将其对应为同一个 QQ 主人 actor，并保留 `desktop` 渠道。昵称保留可信显示值，身份匹配依据稳定 ID，不能依赖昵称。

以下均为虚构示例：

```text
role: user
channel: qq_private
time: 2026-10-04 周日 08:00
actor: 示例主人 (id=qq:123456)
text:
  周末想做草莓蛋糕。
```

紧接该轮的助手消息保持 `role=assistant` 及现有冻结 JSON 投影：

```json
{"utterances":[{"text":"好呀，到时候陪你做。","say":"[archived]","style":"calm"}],"memory_metadata":{}}
```

来源及接收对象属于宿主持久元数据，不要求模型在新回复 JSON 中增加字段，也不给助手历史套一层转述文本。保持真实语义正文和现有归档规则；副本的原始内容及记忆标注可供正常回读、索引使用。

在群聊现有稳定来源说明中加入一句或同等长度的描述：

> qq_private、desktop 表示私人交流，qq_group 表示群内交流；按当时 actor、target 区分人物和场景，不把私人交流当成本群共同经历。当前回复对象和输出方式以本轮为准。历史材料编号属于原会话，操作材料以当前工作台为准。

说明放稳定区，不在每轮尾部重复，也不同时提供 QQ 和桌宠两份输出协议。当前群发言者的关系字段仍只约束当前发言者，不能让历史主人身份变成所有群成员的身份。

### 5.2 原始压缩、长期记忆与回读

压缩输入继续使用现有语义对话渲染。副本的输入和助手回复都必须能够确定所属渠道、发言人及接收对象；助手来源由宿主轮次关系提供，不从回复正文猜。通用渲染支持可选来源，缺少来源的旧记录保留原行为。

压缩输入可以沿用这种简短事件形式，具体键名复用现有约定：

```text
【对话事件】
channel: qq_private
time: 2026-10-04 周日 08:01
actor: assistant
target: 示例主人 (id=qq:123456)
speech:
  好呀，到时候陪你做。
```

在 Akane 现有摘要及长期记忆补充插槽中说明：

> 保留事件的发言人和交流场景；私人交流不得记作本群共同经历，阶段摘要和长期记忆延续这层归属。

涉及归属的摘要事实可自然写成“10月4日，主人在 QQ 私聊提到周末想做草莓蛋糕，我答应陪他”。不强制每一句重复渠道，不把来源塞成冗长固定标题，也不新增摘要输出字段。

检查原始片段召回、时间线、按发言人或关键词展开、记忆来源回读：这些出口省略完整 payload 时，仍保留必要的渠道和归属。不为保留 `channel` 而把全部协议、工具调试字段或完整助手 JSON重新塞进精简摘录。

### 5.3 私人工具记录与文件 ID

第一版沿用“主人输入 + 最终回复”的复制范围。工具使用不影响该轮被复制：私人模型读取论文、修改文件后的最终结论仍进入群记忆；原生调用、参数和结果卡片留在私人会话，不把整条操作轨迹再复制到各群。

| 对象 | 群里得到什么 | 如何进一步读取 |
| --- | --- | --- |
| 聊天输入、最终回复及正文中的结论 | 正常本群副本，可纳入本群摘要和检索 | 按本群副本 ID 使用现有记忆工具 |
| 私人原始工具调用、参数、结果卡片 | 不自动复制；源仍由私人 MemCore 保存 | 确需操作证据时，按现有授权显式选择 `conversation="master"`，取得相应记忆 ID 后回读；需要工具轨迹时使用现有 full/tools 投影 |
| PDF、图片、附件、生成文件及其工作台目录 | 不自动注册到本群工作台，不复制物理文件 | 现有文件工具仍按本群资产范围读取；私人文件不会因为复制一条对话而自动可打开 |
| 原私人 `file_001`、`gen_001` 等短 handle | 只是带私人来源的历史提及 | 不拿它当本群同号材料的身份证；查看或操作当前材料须使用当前工作台核验得到的对象 |

明确区分记忆 `source_id/memory_id`、原生 `tool_call_id` 与文件 ID/handle。原生调用 ID 是调用配对身份，不一定是 `open_memory` 可直接打开的记录 ID。私人记忆 ID 也不能在默认当前群的范围下打开，必须携带原会话选择或既有可信导航凭据。群内副本 ID 打开的是本群聊天副本，不伪造其拥有未复制的私人工具来源。

已有手动跨会话读取可查看当时记录的工具内容，但这不会使读出的文件 handle 自动获得文件访问权限；工具结果正文也不能代表原 PDF 仍在或已在本群重新读取。保持文件清理、归档、版本和真实可用状态，不让读到的旧成功卡片恢复被删除的文件。

若当前来源说明不足，可合并加入一句“私人历史中的材料编号属于原私人工作区；操作材料以当前可用工作台为准”，不新增大段提示或通用工具的特殊案例规则。原始存档不改写，助手 JSON 骨架继续保持。

以后确实需要在群里继续处理某份私人文件，可另做主人指定单个材料的显式共享：复用原物理文件或建立授权引用，为该群分配自己的材料入口和 handle；不迁移私人工作台，不为了方便去掉文件会话过滤。本轮不实现这个额外能力。

## 6. MemCore 管理与缓存约束

- 副本是真正属于目标群会话的记录，进入该群的正常原始窗口和压缩批次。源私人会话只压缩自己的交流；各群独立压缩本群交流与收到的副本。
- 复制有效源标注，走正常索引状态与重试；最终回复继续遵循已有派生标注和检索可见性。不得用永远不索引的临时事件承载全部副本。
- 保留源到副本、群内原始记录到阶段摘要、阶段摘要到长期记忆的来源关系。群内展开只能使用本群副本 ID，不能混用私人源 ID 导致跨命名空间报错。
- 不改检索评分、召回规则、压缩阈值、摘要滑动参数、工具轮数或显式跨会话权限。当前实例的摘要 8→15→8 配置继续沿用，本轮不顺手调参。
- 聊天历史和压缩按写入序处理；时间筛选仍使用真实事件时间。晚到副本可能令摘要覆盖的时间范围交叠，不能仅凭日期范围判定重复或串会话。
- 除正常压缩和首次更新稳定提示外，只追加新副本及其冻结投影，不重写先前请求的消息。副本 ID、来源、显示名及投影确定后保持稳定。
- 不逐轮对整个数据库做复制、归档、目录探测或历史投影迁移。使用完成事件、持久 pending、有限增量读取和已有会话目录。
- 额外成本包括每个群的记录、索引和后续压缩；私人消息多时，群原始窗口会更快触发正常压缩。新增内容本身有未命中 token，不据此认定旧缓存前缀失效。

## 10. 实现与离线验收记录

### 实际接入

- `owner_private_group_memory.py` 负责可信来源、同角色群筛选、异步复制和群任务边界；`private_memory_mirror_store.py` 只保存候选、目标、配置版本、完成状态及安全错误类型，不存第二份对话正文。
- `complete_input_turn` 是普通、流式及工具后最终回复的统一收口；正式语音通过 `record_voice_projection` 的最终完成收口登记。临时语音事件不入队。实际用户追加输入虽然属于 `INTERMEDIATE`，也随其原轮次复制。
- 候选在源最终提交前持久预登记，随后读取源轮次的实际 CLOSED/final。崩溃恢复不依赖原请求上下文，不遍历私人的完整历史；最终写入重试换 source ID 时也能找到真正保存的 final。
- `TurnCoordinator` 在群任务开始读取历史前清理合格待复制记录；闲置群后台导入复用同一个协调锁。导入后只调度宿主监督的异步索引修复，关闭后端时先等待这些任务再关闭数据库。
- 同一群的候选按登记顺序处理，对应现有私人任务协调中的完成收口顺序。原时间不参与群历史插队；每个副本分配自己的 turn/source ID 和压缩标记。
- 接收设置保存失败回滚；关→开递增版本，旧 pending 不复活。执行时再次检查主人、接收版本及真实群资格，已经删除的目标不会由 pending 重建。单群失败独立退避重试。
- 热路径只读指定轮次的消息 kind/final，不加载中间工具正文；接收群查询按群身份定位，pending 和状态查询先查待处理索引，不经过已完成的旧凭据。关闭宿主功能时不启动轮询。

MemCore 的改动位于独立 `memcore` 源码仓库：新增通用 `import_completed_turn` 原子导入、`get_turn` 和支持 role/kind 筛选的 `get_turn_entries`；保留通用 channel/target 归属渲染。内核没有主人 QQ、群开关、目标群或宿主投递逻辑。

依赖升为 `memcore-kernel==0.1.3`，已按正常 wheel 构建和 pip 安装接入；Akane 的依赖契约同时验证这些接口，旧 wheel 会明确失败。常规内部包构建检查通过（14 个包），安装契约检查通过（13 个运行时包）。本次临时内部包目录不作为包含完整运行时依赖闭包的离线一键启动 wheelhouse。
