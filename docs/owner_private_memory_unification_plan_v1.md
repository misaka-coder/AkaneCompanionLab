### 2026-10-03 缓存排查补充

用户补充：缓存未达标不预先归因于系统或反代，尽量从现有证据核查；无法确定的部分交给用户实测，不为追求比例盲目修改架构。

核查实际 `local-qq-test` 运行目录中的 prompt/usage 审计，而不是默认测试目录。2026-10-01 UTC 日志有 903 条请求指纹、15 个缓存键；同一实例、请求模型、进程及缓存键内，十分钟内的相邻请求共 794 对，其中系统消息指纹改变 0 对、工具 schema 改变 20 对、能力目录改变 5 对。这个分组只说明同键连续请求的稳定性，不能排除新键、切换、压缩或重启的影响，也不能用本地估算 token 代替上游命中统计。

一个已逐条核对、无请求交叠的样本（北京时间 10 月 1 日）：

| 请求/返回时间 | 上游回报模型名 | 输入 token | 审计缓存读取 token |
| --- | --- | --- | --- |
| 12:09:05 / 12:09:10.572 | gemini-3.8-flash | 71,592 | 69,164 |
| 12:09:10 / 12:09:16.210 | gemini-3.8-flash | 71,985 | 0 |

两次请求的系统、64 个工具 schema、缓存键和被审计的非消息参数相同，消息共同前缀按本地估算 token 占第二次约 99.59%。随后 12:09:38 的请求工具数变为 65，属于另一个确实发生请求结构变化的样本，不能混作相同条件。

发现审计盲点：旧实现把“缺少缓存读取字段”和“明确报告 0”都记为 0，旧日志无法追溯区分。已补 `cache_read_reported`：缺报时 `cache_hit_ratio=null`，明确 0 才为 0；原生 Gemini 与 Anthropic 归一化保留字段是否存在的信息，兼容原有数值计数，并新增缺报计数。只改诊断，不改请求内容、工具、记忆、压缩阈值或路由。旧日志的非零缓存量是有效证据，零值只能视为“零或缺报”。新诊断需下次正常重启加载，本轮没有为此重启服务。

因此目前更值得核查反代的路由、缓存保留和 usage 转发，但不能据此断言全部由反代造成，也不能把共享改动前后的性能验收标为完成。历史审计缺少逐次 request ID，存在重试/并行时的关联歧义；批量筛选结果仅作定位线索，关键结论使用上面的独立样本。

建议实测：固定一个角色、会话、模型及代理路线，正常连续聊 8～10 轮（至少一轮调用工具），记录起止时间；再单独测试另一模型。先分出首次请求、切换或压缩，保留全量统计，同时统计稳定连续段；缺报样本独立列出并给出覆盖率。两端共享启用后的同样测试另做，不把模型变化和共享改动混在一组。按各组缓存读取 token 总和除以明确报告缓存的输入 token 总和计算，并保留全量缺报比例；不平均各轮百分比。若仍有前缀稳定且明确为零的样本，再用可控的固定上游进行对照。

目标是让同一角色在桌宠和主人 QQ 私聊中接着同一段经历聊天，并使用一致的精力、饥饿、好感和亲密阶段。同时修正 QQ 各会话共用角色状态的问题：各群、其他人的私聊分别维护角色状态，用户资产跨会话共用。保留各端的提示词、流式显示、语音、工具权限和投递方式。共享记忆以主人当前已有的 QQ 私聊记忆为接续基准，启用后的两端新消息共同延续该历史。本文用于用户审阅，也可交给执行模型按阶段落实。

## 已确定的设计

1. 共享范围为同一运行实例、同一主人、同一正式角色的桌宠与 QQ 私聊。群聊、非主人私聊和辅助人物保留各自的记忆范围；不同角色不能混入同一段历史。
2. 近期助手历史保留模型完整原始输出，原生工具调用与返回保持对应关系。中文语义正文继续单独保存，聊天压缩沿用 MemCore 的语义视图。
3. 新用户消息带精简、可信的客户端来源。每轮只提供当前客户端的输出格式，不同时注入 QQ 和桌宠两份协议。
4. 去掉模型输出的 `reply_medium`，QQ 投递由指令和宿主设置决定；去掉模型输出的 `activity`，音乐操作通过真实工具执行。
5. 保留 `utterances` 的中文 `text`、配音 `say` 和声音 `style`。继续按标点分句，一组不等于一次合成；表情 `emotion` 与声音风格独立。
6. 普通回复回到本轮接收消息的客户端。已有主动搭话沿用其触发端，明确指定的提醒沿用其目标，不根据最近一次聊天位置自动改投。
7. 两端共享必要的会话顺序和私人互动状态，避免并发污染历史或连续重复打扰；继续复用现有 Agent、工具、收件箱和任务能力。
8. 缓存、上下文占用和压缩频率分别验收。QQ 当前约 97%～98% 是用户观察值，桌宠尚缺统计；实施前补采基线，不能写成已验证结果。
9. 按用户补充，桌宠现有记忆及旧桌宠记忆可以舍弃，不做历史合并、摘要搬运、专门检索保留或恢复兼容。本轮共享接入面向 `desktop_pet_next`，不增加旧 Electron 桌宠的适配任务。舍弃指不再作为共享接续数据使用，本计划不安排物理清库操作。
10. 按用户最新补充，角色状态按会话区分。桌宠与主人 QQ 私聊在绑定后视为一个陪伴会话，共用身体和关系状态；各 QQ 群及其他用户的私聊分别保存，不再共同消耗一份饥饿和精力。好感属于当前会话中角色与具体用户的关系，同群不同成员仍各有好感。
11. 用户的金币、兑换额度、背包等资产跨 QQ 会话共用。拆分角色状态时不能把资产也复制成各群一份；用户和角色之间的账户边界，以及主人桌宠的资产接入方式，按下面的推荐选择审阅。

## 本执行单提出的具体选择

以下是便于实施的推荐方案，随本文一起审阅，尚未应用到运行环境。

| 选择 | 推荐处理 | 实际影响 |
| --- | --- | --- |
| 主人两端绑定 | 使用实例设置中的一个绑定开关，默认关闭，控制主人桌宠与 QQ 私聊的记忆和养成归属；复用现有设置服务和界面 | QQ 角色状态按会话隔离是独立修复，关闭两端绑定也不恢复全 QQ 共用身体；MemCore 不承担 QQ 专用开关 |
| 状态接续 | 将旧角色身体与 QQ 好感冻结为一次迁移基准，为已有会话建立独立初值；主人私聊的这一份供桌宠接续 | 旧数据没有会话维度，不能还原各群过去各自的数值；初始化后各自变化，新会话使用角色默认值 |
| 资产边界 | 推荐沿用同一实例、同一角色、同一用户的账户，跨 QQ 群和私聊共用；绑定后的主人桌宠也使用该账户 | 不跨用户或角色合并资产，不改变商品价格和各渠道支付规则；桌宠旧资产另留快照，不自动相加或清空 |
| 原有自动回复模式 | 新指令保留 `/回复 文字`、`/回复 语音`、`/回复 双发`、`/回复 默认`；已有 `auto` 设置一次性归一为文字 | 不再由模型决定投递介质；已有明确语音或双发设置不变，`默认` 恢复宿主设置 |

共享机制支持正式角色包，不硬编码塞西莉亚。首次验收只启用塞西莉亚与主人私聊，验证后再按同一机制使用其他角色。

## 用户能看到的行为

| 场景 | 用户看到的行为 |
| --- | --- |
| 第一次启用共享 | 桌宠直接接上当前角色已有的主人 QQ 私聊历史，启用前的桌宠记录不并入 |

| 桌宠看屏幕后主动搭话 | 在桌宠显示；有实际回复时写入共享记忆，不向 QQ 复制发送一遍 |
| 正在 QQ 私聊，桌宠本地长时间没有输入 | 桌宠能识别主人最近仍有私人互动，不把本地无输入直接当成主人一直没说话 |
| 主人在桌宠或 QQ 私聊投喂、休息、增加好感 | 这两个入口使用同一份最新身体和关系状态，不改变任一群中的角色状态 |
| 在 87 群投喂或长时间聊天 | 只影响 87 群中该角色的身体及与相关用户的好感，其他群和主人私人会话不受影响 |
| 同群的另一位成员查看饱腹度与好感 | 饱腹和精力相同，好感是角色对该成员的数值，不混用其他人的关系 |
| 同一用户换群查看金币、额度或背包 | 同一角色下仍是同一份账户；在一处消费，其他入口查询能看到变化 |
| 群聊、其他 QQ 用户或售货员对话 | 记忆、权限和调度继续隔离，不加入主人的共享私人历史；售货员仍服务目标角色的商店 |

第一版不增加无来源的全局定时问候，也不增加新的跨端发送工具。未来若加入“主动去找主人”，单独设置默认联系端；明确指定的任务目标优先。

## 阶段二 固定消息来源和当前格式约定

新用户消息的模型可见形式在现有渲染中增加一个可选来源，示意如下：

```text
channel: desktop
time: 2026-10-02 周五 18:00
message_id: <消息标识>
text:
  刚才那件事继续吧。
```

QQ 主人私聊对应 `channel: qq_private`。来源由可信入口设置，不从用户正文、昵称、模型输出或任意外部参数推断。具体键名沿用现有通用元数据约定，实施前固定，避免并存多套含义相同的字段。

- [ ] 贯通来源的入队、落库、模型回放及必要的摘要语义，重启和重试后仍能恢复。只存入 payload 而模型渲染不到，不算完成。
- [ ] 来源和事件时间在接收时确定，随后保持不变；切换客户端时不重写已有历史。旧消息缺少来源时保留原状，不在请求热路径补写或迁移。
- [ ] 主动轮和后台完成事件也保留真实来源及投递上下文，不伪造用户在该端发送了一句话。沉默轮沿用现有隐藏事件和无助手正文语义。
- [x] 当前客户端的稳定输出约定只补充一句：`输出遵循本轮客户端的格式要求，历史回复的字段不作为当前格式约定。`
- [ ] 保留最近助手原始输出和原生工具结构，不给助手历史额外套来源文本外壳，不把工具轨迹拼成群聊转述。

MemCore 继续作为通用系统。优先复用已有元数据和渲染扩展；若缺少通用来源字段的展示能力，应在 MemCore 源码中增加最小、可选的能力并验证旧行为，再通过正常依赖打包接入。不得直接修改 `.venv` 安装目录，也不得在 MemCore 中硬编码主人 QQ、塞西莉亚或 Akane 客户端权限。

## 阶段三 接入共享私人记忆

宿主集中解析三类身份，整轮固定使用：

| 身份 | 用途 | 共享后的处理 |
| --- | --- | --- |
| 真实用户与角色 | 权限、人设、业务归属 | 继续由既有可信身份和角色解析产生 |
| 客户端会话和投递目标 | QQ 收件人、桌宠连接、界面状态、指令设置、原消息引用 | 保留原值，不用共享记忆 ID 替换 |
| 记忆会话和协调范围 | MemCore 历史、工具轨迹、压缩、默认检索、私人回合顺序 | 仅对已启用并验证的主人两端解析到同一范围 |

- [ ] 在宿主记忆适配边界建立统一解析，调用方不各自拼接特殊 ID。开关关闭、群聊、非主人、辅助人物和不同角色均按原规则解析。
- [ ] 共享目标直接使用该角色已有的主人 QQ 私聊记忆范围，保留 QQ 原始消息、摘要、索引和工具轨迹；桌宠首次接入不复制自身旧历史，也不另建空白共享会话替代 QQ 既有记忆。
- [ ] 入口只接受经过身份核验的绑定。不能凭一个客户端传入的 `real_user_id=master` 或记忆 ID 获得主人范围。
- [ ] 覆盖历史读取、用户与助手写入、工具批次、中间消息、隐藏事件、后台完成、附件材料事件、语音投影、摘要、索引与检索的完整生命周期。
- [ ] 默认检索读取绑定后的当前记忆会话；显式会话选择沿用现有权限。会话列表清楚表示共享范围，别名解析去重，不扩大为全库检索。
- [ ] 原有角色 domain 和服务人物归属保持稳定。同一主人切换正式角色后，只读该角色对应的共享历史。
- [ ] 检查材料句柄和附件权限使用的是哪种身份。关联后的主人两端按已有授权读取共享材料，不能因改了记忆键产生大量失效引用，也不能借此扩大到其他用户或群的材料。
- [ ] 保存原生工具调用 ID、Provider 协议、轮次和重试身份。现有工具卡片展开、原文读取和文件工作区流程继续可用。
- [ ] 工具权限按当前客户端和真实用户判断；工具目录快照继续区分授权范围。不能因共享压缩版本而相互覆盖，也不能每次换端就重建整段历史或追加重复目录事件。
- [ ] 两端保留各自的稳定提示词和工具能力。缓存使用稳定的会话身份及原有客户端配置，不强行合成单一缓存键。

不要只修改 `MemcoreManager._get_system`，也不要直接把桌宠 `user_id` 全部改成 `master`。需要逐项确认记忆归属、客户端连接、身体、好感、用户资产、工具权限和文件归属使用的身份；养成会话与用户账户在下一阶段分别解析，不能共用一个键来决定所有业务归属。

## 阶段四 分离会话状态与用户资产

当前饥饿和精力只按角色保存，QQ 好感与用户资产也混放在一份关系记录里。按最新讨论改为下面三类归属；继续复用现有养成服务、商品配置及事务，不引入第二套养成引擎。MemCore 记录对话和有意义的事件，不充当实时数值数据库。

| 数据 | 存储归属 | 具体行为 |
| --- | --- | --- |
| 饥饿、精力及恢复时钟 | 实例＋角色＋养成会话 | 一个群共用该群身体，不同群和私聊各自独立；绑定后的主人桌宠与 QQ 私聊共用一个养成会话 |
| 好感、亲密阶段、关系锚点和阶段事件 | 实例＋角色＋养成会话＋真实用户 | 同群不同成员各有关系，同一人在不同群和私聊也各自发展；主人绑定后的两端共用其私人关系 |
| 金币、额度、背包及个人领取记录 | 实例＋角色＋真实用户 | 同一账户跨会话访问，不按群复制；推荐主人绑定后的桌宠接入同一账户 |
| 状态档位 | 从当前身体或关系及统一阈值计算 | 模型、桌宠面板和 QQ 图卡使用同一套规则；`hunger` 沿用现有“值越大越饱”的语义 |
| 商品定义、角色累计供奉等非身体数据 | 沿用其现有业务归属 | 不因目前存放在 body 中就随身体复制到每个会话；不新增售货员自己的商店或养成记录 |

- [ ] 在宿主统一解析养成会话、关系主体和资产账户，作为一次业务操作的固定上下文。QQ 群使用稳定群身份，私聊使用稳定私聊身份，桌宠使用持久私人身份；不能用页面连接号、临时轮次或昵称作会话键。主人的两端绑定复用上一阶段的可信身份校验。
- [ ] 覆盖普通回复、主动轮、后台续轮、状态查询、模型 `state_request.affinity`、投喂、道具、戳一戳、供奉和抽签等真实读写入口。队列与后台任务保存接收时的养成会话和角色，不能在完成时误用界面刚切换的对象。无有效归属时不回退到旧全局身体写入。
- [ ] 将好感及关系事件从账户语义中分开。不能简单给整份旧 relation 增加会话键，否则会复制金币和背包；也不能只隔离身体却继续跨群修改同一份好感。
- [ ] 投喂事务从真实操作者的共用背包扣物品，只改变当前会话身体及该人与角色的当前会话关系。消费、状态效果、事件回执在现有存储中原子提交；两个群同时消费同一件物品，只能成功一次，失败不得留下半笔扣款或效果。
- [ ] 保留个人签到、领取、额度与支付的已有账户限制，不因换群、转私聊或打开桌宠而重置。原本属于群互动节奏的冷却继续按群，不能把所有群对话合成一个模型串行队列；资产写入只做必要的短事务互斥。
- [ ] 按推荐资产边界适配主人桌宠余额和背包的读取、购买、使用及回执。QQ 背包保存商品详情，桌宠现有形状以数量为主，应通过既有服务做视图适配，保留商品来源、下架快照和渠道可用规则；不维护两份可分别消费的账户。
- [ ] 每个身体独立保存自然衰减与恢复时间戳。统一结算实现，明确角色配置优先级，推荐以当前 QQ 有效口径为基准；同一会话的同一时间区间只结算一次，主人两端轮询顺序不影响恢复，各群时钟互不推进。
- [ ] 每个有效回复、投喂或休息事件按业务语义结算一次。流式片段、重试、最终帧、查询和历史回放不重复加好感或扣精力；复用事件与回执身份，作用域包含实际会话及角色，不新增模型填写字段。模型感知投喂结果时不能再次应用商品效果。
- [ ] 阶段事件由对应会话和用户消费一次，页面查询或后台轮询不抢先吞掉交给模型的变化；初始化时不把旧全局待消费事件复制给所有群。无明确用户的群主动轮不凭空修改某个成员的好感。
- [ ] 复用 `CareRuntimeStore` 服务端权威与版本机制。状态快照标识其实际归属，桌宠换角色、重启、重新进入或慢请求返回都不能用旧本地快照覆盖新值，也不能把上一会话的结果画到当前界面。
- [ ] 模型每轮只获得当前会话的身体和相关用户的关系状态。移除“全 QQ 与桌宠共享身体”及绑定范围内“两端独立好感”的过时说明；沿用现有动态状态位置，不向稳定系统前缀或缓存键加入变化数值，不把其他群状态附上作对照。
- [ ] 更新桌宠面板、QQ 养成图卡、背包、购买和投喂回执及文字兜底。查询使用正确身体、关系和账户的组合，缓存必须区分会话、角色、用户及展示版本。QQ 下次查询取最新值，已发送图片不回改；同步更新帮助文档中旧的共享范围说明。
- [ ] 非主人资产与关系仍只属于本人，角色包之间保持分开，权限仍依赖真实身份。表情与语音风格继续由当前回复决定，售货员沿用所服务角色的业务能力。

例如：同一用户在 87 群用掉一块草莓蛋糕，其余群查询背包时也少一块，但只有 87 群的角色增加饱腹和对应好感。主人在 QQ 私聊投喂时，桌宠会读到相同变化；87 群、42 群和其他人的私聊保持各自状态。

## 阶段五 协调顺序和主动搭话

- [ ] 复用现有持久化收件箱与 `TurnCoordinator`，让共享私人会话拥有一致的顺序范围和领取权威。物理入口、角色、投递目标及绑定版本随队列项保存，不另造第二套顺序队列。
- [ ] 第一版跨端新输入排为下一轮，当前轮保持原客户端协议和目标；同端沿用已有安全 steer。正常换端不隐式取消正在执行的任务。
- [ ] 后台任务仍在登记后让出模型回合，完成后回到登记时的目标。只把事实写入共享记忆，不让两端分别请求一次模型或重复通知。
- [ ] 共用最近真实私人互动时间、活动回合状态和最近成功主动投递时间。QQ 与桌宠的自身事件、重试和静默判断不冒充用户互动。
- [ ] 沿用桌宠现有间隔和开关，引入共享状态后，先在宿主侧抑制明显重复的主动请求，模型仍可基于历史决定安静或开口。
- [ ] 在主动轮启动及首次投递前检查新用户活动和请求有效性，避免用户已转到另一端聊天，旧主动轮仍继续打扰。已有真实工具效果不能因取消而伪装成未发生。
- [ ] 实际回复、沉默、失败和中断分别记录；投递目标不可用时沿用该端已有失败或等待语义，不自动改投另一端。
- [ ] 实时语音保留已播放和中断的现有投影语义。不能将尚未播出的合成内容全部当成主人已经听到的对话。

共享记忆只供下一轮读取，不是消息转发总线。写入一条记录不能触发另一端再次回复，避免形成反馈循环。群聊节奏不使用这份私人冷却状态。

## 阶段六 接续数据、启用及回退

- [ ] 启用前对 QQ 接续数据、旧角色身体、关系与资产建立一致性备份和迁移清单，记录已有会话、用户、角色及版本。SQLite 使用适合活跃数据库的备份方式，养成存储沿用其安全持久化机制。用户只明确允许舍弃桌宠旧记忆，不据此删除其旧资产。
- [ ] 在安全写入边界冻结旧状态基准。推荐按已有会话清单初始化身体；仅为已有的会话与用户关系承接旧 QQ 好感值，并标记迁移来源。旧结构无法还原各群独立历史，不伪造不同初值或把旧跨会话计数解释成某群经历。新会话和新关系使用角色默认值。
- [ ] 迁移幂等且有版本，恢复或重试不重复初始化。旧全局身体退出新 QQ 写入链路；不能延迟到首次访问时读取仍在变化的旧全局值，也不能在缺少会话参数时悄悄回落旧共享状态。旧关系中的资产保留一份，金币、额度、物品数量和领取记录不因分会话增加。
- [ ] 主人私聊承接旧 QQ 好感及迁移后的私人身体，桌宠绑定后直接访问这一份。按推荐资产方案使用 QQ 主人账户，不自动合计两端原余额或背包；桌宠旧资产保留独立快照，列出差异供审阅，不作为第二个仍可消费的余额来源。
- [ ] 在隔离副本验证桌宠直接读取已有 QQ 历史、两端新消息只写一次、重复恢复不重放。QQ 原有摘要与工具链沿用，不合并桌宠旧记录、压缩版本或索引。
- [ ] 桌宠启用后停止向原独立记忆范围写入新对话；不补写旧桌宠摘要、不建立双向同步任务，也不为废弃历史新增检索入口。历史数据不参与新链路即可，不以删除文件或数据库记录作为完成条件。
- [ ] QQ 状态隔离与主人两端绑定分别交付、验收。迁移和开关切换在相关活动回合及写入完成后的安全边界生效，受影响任务排空或用兼容版本接续，不允许半轮改变状态或记忆归属。两端共享仍需等待顺序协调通过才启用。
- [ ] 关闭主人绑定时保全 QQ 历史、当前私人状态与账户，桌宠恢复独立入口；明确其后续状态和资产来源，不能复活已花掉的余额，或用启用前数值覆盖 QQ 最新值。无需恢复已舍弃的桌宠旧记忆，也不反向复制共享历史。
- [ ] QQ 分会话状态迁移单独保留回退方案。关闭桌宠绑定不把各群重新并成一个身体；已产生不同会话状态后，不自动求和、平均或任选一份恢复旧全局状态。程序回退须兼容新数据或在隔离环境完整恢复，不能丢掉迁移后有效交易。
- [ ] 阶段完成后分别记录验证结果和剩余限制；发布、重启和提交按用户后续指令处理。

## 缓存与性能验收

缓存比率采用 Provider 实际返回的 token 数据，按模型与上游口径统一分母后计算：

```text
缓存命中率 = 缓存读取输入 token 总量 / 输入 token 总量
```

不按“有一次缓存命中的请求数量”计算，也不直接平均每轮百分比。缺少 usage 的样本标记未知并说明覆盖率。

- [ ] 在相同模型、代理路线和相近上下文规模下，分别采集修改前后的 QQ 与桌宠基线；共享测试不能顺带换模型、改工具预算或调整压缩阈值。
- [ ] 连续 QQ、连续桌宠、双向切换、多轮工具、压缩后继续聊天分别统计。95% 作为目标验收底线，QQ 原有约 97%～98% 作为需要保持的对照，不能把下降到 95% 自动视为无回归。
- [ ] 同时给出包含首次启用冷缓存、切换和压缩的全量统计，以及分场景统计。不能删掉低命中样本后声称达标，也不承诺每一个请求都能达到 95%。
- [ ] 分别报告请求输入 token、首段文字延迟、首段语音延迟、模型完成时间和压缩触发频率。高缓存命中不代替上下文与实际延迟验收。
- [ ] QQ 各群状态隔离前后补做对照，确认状态查询、图卡和数值事务不新增模型调用、不注入其他会话快照，也不在请求热路径扫描全库或迁移全部历史。
- [ ] 不通过向每次请求重复填充固定内容提高比例，也不为了保持比例盲目扩大上下文、延后压缩或删除原始工具轨迹。
- [ ] 若某端、切换场景或全量指标未达预期，保留样本和归因，明确报告限制并停止扩大启用范围；不能只靠代码前缀检查宣称缓存验收完成。

复用现有 prompt usage 审计，新增诊断只记录完成定位所需的来源、绑定标识摘要和指标；不把完整私人聊天、凭据或运行数据库加入仓库。

### 2026-10-03 桌宠鉴权修复

共享主人记忆要求可信桌宠身份，原来的普通 Tauri HTTP 请求没有附带凭据，导致聊天及共享材料入口返回 `admin_auth_required`。管理凭据由原生进程持有，前端通过既有 `backend_admin_request` 获取十分钟有效的桌宠会话凭据；仅限当前 Bot 的聊天、养成操作和材料接口，不授予商店管理、项目绑定或其他管理权限。凭据不持久化，不进入 URL、提示词或记忆。

聊天继续使用原来的流式 HTTP 传输，带限定用途的请求头；后端重启使旧凭据失效时只刷新并重试一次。并发请求复用凭据获取，取消或切换对象后的响应仍受现有请求作用域保护。桌宠、工作区和角色工坊复用同一传输模块。实时语音通过 WebSocket 协议头传递凭据并完成握手，继续复用既有语音会话和播放逻辑。原生管理代理仍不允许直接代理 `/think`，避免整段缓冲回复。

鉴权测试覆盖无凭据、伪造、到期、后端重启、跨 Bot、越权管理、共享主人记忆和语音握手。前端行为检查覆盖并发获取、失败恢复、取消、401 重试以及首段数据在流关闭前可读。浏览器检查覆盖真实入口的发送、失败、慢回复时切换会话和重新进入。部署后后端健康、桌宠 ready、设备执行器 online；真实原生客户端获取凭据和读取共享工作区均返回 200，主人 presence 校验为 shared。未用测试消息污染实际聊天历史；真实麦克风采集及完整 TTS 播放仍需用户实际体验。
