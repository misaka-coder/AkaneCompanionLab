# 能力目录差量更新和运行绑定执行单

> 2026-10-08 实施修正：工具调用减负已完成代码与隔离验收。当前源码以[工具暴露执行单第 12 节](tool_exposure_memcore_execution_plan_20260910.md#12-2026-10-08-工具调用减负已实施)替代本文“声明或实现升级一律使旧引用失效、重新加载后恢复”的约定；本文原完成项保留为当时的实施记录。

日期：2026-10-03。状态：三个切片已实施，本地行为和协议验证见[实施记录](capability_catalog_delta_and_runtime_binding_implementation_v1.md)；线上缓存计量待重启后实测。

本轮解决三个已确认的问题：能力变化后在尾部重复追加完整目录；MCP 探测失败和恢复反复改变目录；插件或 MCP 的运行实例变化被当作工具契约变化。目标是让模型收到必要的新信息，同时保持已发布上下文稳定，执行时仍能准确判断权限、契约和实际连接状态。

插件管理操作目前会重建整批已启用插件。这是另一个问题，本轮只处理它对目录和契约判定的影响，不改造插件进程复用。

## 一、已确认的实现和证据

### 目录更新重复了完整内容

`companion_v01/memcore_integration/catalog.py` 的 `reconcile_capability_catalog` 已经计算新增、移除和契约变化，但生成 update 时，在这些变化之后又附上完整目录。Skill 简表也会一起重复。

10 月 3 日同一压缩代的两条更新合计 35,522 字符，其中重复追加的完整目录有 32,571 字符，约占 91.7%。第二条更新只是四个 AnySearch 工具恢复，附带的目录正文却与原基线完全相同。AnySearch 四个工具的描述合计约 19,907 字符，进一步放大了这个问题。

`companion_v01/engine_services/response_catalog.py` 已支持保留本代更新的时间线位置，并在新的真实压缩代过滤旧代通知。因此不需要另建一套记忆或定时清理机制。

### MCP 探测参与了请求构建

`companion_v01/capability_adapters/mcp_stdio.py` 在成功探测后保留约 15 秒结果，失败后约 5 秒再允许重试。它不是每 15 秒独立运行的后台定时器，而是后续请求触发探测；强制刷新还会绕过这段有效期。

探测失败会清空该适配器当次提供的工具列表，恢复后又重新提供。`capability_exposure.py`、`capability_discovery.py` 和 `engine_services/tool_rounds.py` 的调用链会把这些结果用于能力选择和契约检查，造成网络短暂异常影响目录。

日志能确认四个工具消失后又恢复，但当时的原始传输错误未保留下来，不能据此断言具体是超时、DNS 或服务端故障。

### 契约指纹包含运行实例身份

`companion_v01/capability_contracts.py` 的公开契约指纹包含 `provider_revision`。插件绑定使用进程 generation ID；MCP 管理器使用启动 UUID 和服务 epoch。重启会改变这些值，即使工具名称、描述和参数没有变化，也可能形成新的公开契约引用。

一次后端重启后的样本中，16 个插件工具的公开声明完全相同，指纹却发生变化。这足以确认运行实例身份导致了一部分无效更新，不代表所有契约变化都可以忽略。

插件管理层的 `restart`、`reconfigure` 会构建整批已启用插件的候选运行代。正常聊天不会因此自动定时重启插件。MCP 的显式重启、配置变更和 SDK 连接恢复也不是同一件事：前两者可改变管理器 epoch；底层连接恢复不一定改变它。后端重启会创建新的管理器，本地 stdio 子进程随后按需启动；远程 MCP 服务不因此被后端自动重启。

## 二、最终行为

| 变化 | 模型上下文 | 执行链 |
| --- | --- | --- |
| 新增 Skill、插件工具或 MCP 工具 | 尾部追加该项的精确标识、用途及加载方式 | 通过既有入口加载、授权和调用 |
| 已有能力的声明或有效实现版本改变 | 只通知受影响的能力和必要的新事实 | 按新契约绑定，旧契约保留明确的失效处理 |
| 删除、禁用或撤销权限 | 通知对应能力的撤销，不重贴其他项目 | 立即阻止不再获准的调用 |
| 已知 MCP 暂时连接失败、随后恢复 | 不将整项能力反复移出、移入目录 | 返回真实失败原因，后续调用按需连接 |
| 后端或提供方重启，声明和有效实现版本均相同 | 不产生“工具契约更新”通知 | 换成新的内部执行绑定 |
| 真实压缩成功 | 合并最终状态建立新基线，旧代通知不再进入请求投影 | 沿用现有压缩代机制 |
| 压缩失败或取消 | 保留原基线和已发布更新 | 不提前切代、不强制整理 |

“能力声明”“连接状态”“公开契约”“运行实例”各有用途。保留已确认声明不表示连接健康，也不授予执行权限；加载过契约不表示当前仍有权限。

## 三、实施顺序

### 第一项：能力目录只追加变化项

主要入口：

- `companion_v01/memcore_integration/catalog.py`
- `companion_v01/capability_exposure.py`
- `companion_v01/engine_services/response_exposure.py`
- `companion_v01/engine_services/response_catalog.py`
- `companion_v01/engine_services/tool_prompt_context.py`
- `companion_v01/skill_runtime.py`

执行内容：

1. 从现有注册表和 Skill 快照取得结构化目录条目，使用精确 ID 或既有稳定名称比较。工具沿用当前目录选择和权限规则，Skill 沿用自身注册表，不新建独立的权限事实源。
2. 隐藏快照可以保留完整状态，供差异计算和重启恢复使用。模型可见 update 只包含本次新增、修改、移除的条目，不再拼接完整目录或未变化的 Skill 简表。
3. 新能力给出既有精确名称、用途和加载入口，保证模型当轮即可找到它；修改只说明必要的新事实，移除只指出该能力已撤销。使用固定代码模板，不额外请求模型总结目录。
4. 没有模型可见事实变化时不追加消息。同一状态重复同步也不重复追加。插件提示块摘要的变化不能单独触发整份目录重发，提示块继续遵循既有发布和撤销规则。
5. 同一压缩代已经发布的通知保留原位置，不删改历史。真实压缩成功后，新基线包含最后确认的目录状态；旧代通知仅从模型请求投影过滤，原始审计记录保留。
6. 保留客户端、会话、角色和授权作用域。QQ 与桌宠共享私聊记忆时，各自的目录投影不能串入另一客户端的专用工具声明。

本项先消除重复发布。第三方工具描述过长是另一个可独立处理的问题，不在本轮强制截断；不能用简单截字丢掉调用条件，也不把完整契约改成简略摘要。

验收：新增一个 Skill 只出现该 Skill；撤销一个工具只出现该工具；四个已知 MCP 工具仅连接恢复时不再重贴目录；无变化的同步追加零条通知。对历史 35,522 字符样本做只读回放，报告新通知长度和保留的信息。

### 第二项：普通请求不做 MCP 全量健康探测

主要入口：

- `companion_v01/capability_adapters/mcp_stdio.py`
- `companion_v01/mcp_host_manager.py`
- `companion_v01/capability_discovery.py`
- `companion_v01/capability_exposure.py`
- `companion_v01/engine_services/tool_rounds.py`

执行内容：

1. 目录依据最近一次成功确认的工具元数据，并继续叠加当前启用、模型可见性和权限配置。优先复用现有持久化工具配置，不另建周期性扫描目录的服务。
2. 普通聊天请求、已知目录的列举和已知契约的加载，不因 5 秒或 15 秒有效期到期而执行网络预检。不为一次工具调用顺带探测所有 MCP 提供方。
3. 初次接入、连接配置改变、明确刷新和真实工具列表变更时执行必要发现。服务支持时可利用 `notifications/tools/list_changed`，不将通知机制替换成固定频率全量探测。[MCP 官方工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)
4. 发现成功后一次性更新确认元数据；失败保留上次成功结果和当前失败原因。没有成功发现过的服务明确显示未确认状态，不虚构工具或可用状态。
5. 真正调用工具时才按需连接，并通过既有权限、契约和传输检查。首次连接或重新连接涉及声明确认时，只确认目标服务，避免使用未经确认的变更契约执行旧参数。
6. 禁用、删除和授权撤销立即生效，不能以“保留旧元数据”为由继续调用。真实调用失败提供配对结果和可理解原因，不为状态波动反复发布目录事件。
7. 连接失败后可以为后续请求恢复连接，但不静默重放可能已执行的副作用调用。保留现有传输层对发现重试和工具执行的区分。
8. 同一目标的并发初次发现或重连合并为一个在途操作。完成时检查配置代次，避免慢请求把新配置覆盖回旧配置。

先确认现有 MCP 客户端是否提供所需连接与发现回调。如需改依赖，在对应源码或可发布版本完成，不直接修改 `.venv` 下的已安装文件。不借本项重写整个 MCP 协议栈。

验收：服务已有确认元数据时，空闲后再次聊天不触发健康探测；断网和恢复不会改变公开目录指纹；实际调用离线工具返回真实失败；实际 tools/list 内容变化会产生对应条目的通知；首次发现、显式刷新、配置更新、禁用和撤销保持有效。

### 第三项：公开契约与内部执行绑定分开

主要入口：

- `companion_v01/capability_contracts.py`
- `companion_v01/capability_discovery.py`
- `companion_v01/plugin_active_generation.py`
- `companion_v01/plugin_generation.py`
- `companion_v01/plugin_installation.py`
- `companion_v01/mcp_host_manager.py`
- `companion_v01/capability_adapters/mcp_stdio.py`
- `companion_v01/engine_services/tool_rounds.py`

执行内容：

1. 公开契约指纹保留完整声明，以及确实影响执行语义的稳定实现修订。插件优先复用安装来源已有的产物 digest；内置实现使用能反映实际代码变化的稳定修订；MCP 使用确认的公开契约和提供方能明确声明的有效版本信息。
2. 启动 UUID、进程 generation、连接 epoch 继续用于内部生命周期和执行绑定，不再单独构成模型可见的契约变化。不能只删除 `provider_revision` 而忽略实际实现更新。
3. 声明和有效实现版本都相同时，为已发布契约重新绑定当前可用的处理器，模型继续使用原精确 ID 和契约引用，不要求重复加载。
4. 真正的声明或实现升级仍须改变公开契约。同输入 schema 下的实现变更也要覆盖，不能拿“参数没变”当作继续使用旧契约的依据。MCP 无法证明的内部代码版本不猜测。
5. 已开始的调用保留捕获的执行代和现有生命周期约束；新请求使用新绑定。保留权限撤销和过期契约检查，不在执行中途替换处理器，也不把旧参数静默转换后交给不同实现。
6. 当前代已经发布的原生声明按现有规则保留。确有契约变化时，旧调用返回明确且配对的未执行结果；模型加载新契约后通过固定入口恢复，到真实压缩边界再合并声明。
7. 契约指纹和通知不暴露密钥、私有路径或工作进程身份。历史工具回执仍只作为历史凭据，不恢复授权。

验收：真实插件 worker 或后端重启后，相同契约不发变更通知，下一次调用成功使用新处理器；升级插件实现但保留原参数 schema 时，旧契约仍正确失效；MCP 显式重启和自动连接恢复分别验证；在途调用不重复执行，撤销后新调用立即被拒绝。

## 四、历史和兼容边界

现有隐藏快照和已发布历史不做全库迁移、删除或重写。新代码应能读取旧记录；只有信息足以证明契约相同时才恢复原引用，否则允许一次真实的重新加载，不能假装旧记录具有从未保存过的实现修订。

旧的冗余通知在下一次正常、成功的压缩后自然退出模型投影。不为了这次改动触发强制压缩，也不把目录通知送入长期语义检索或聊天摘要。

继续保留[工具偏好下一请求生效](tool_exposure_next_request_20260917.md)的已有规则：用户明确修改常驻、按需和搜索偏好时，不要求等待压缩。本轮稳定性要求不覆盖这项用户操作，也不覆盖即时撤销。

实施完成后同步更新[能力目录生命周期](capability_catalog_context_lifecycle_v1.md)：其中将可用性和运行 generation 变化视作目录更新的表述，应改为区分真实声明变化、连接健康和内部执行实例。其他发布边界沿用[工具暴露执行单](tool_exposure_memcore_execution_plan_20260910.md)和[MCP 作用域约定](mcp_scope_contract_v1.md)。

## 五、验证和上线

先完成三个小切片及其必要测试，再做一次整体协议检查。全部使用临时数据库、独立提供方和脱敏样本；不向真实 QQ 会话重发历史消息，不把运行数据放入仓库。

| 场景 | 必须验证的结果 |
| --- | --- |
| 目录新增、修改、移除、净零变化及重复同步 | 通知仅涉及变化项，无事实变化不追加 |
| 成功压缩、失败压缩、后端重启和待合并事件恢复 | 真实边界生效，旧代过滤正确，历史不改写 |
| QQ、桌宠、群聊和不同用户 | 工具目录、契约引用和权限不串作用域 |
| MCP 断网、恢复、慢发现、并发刷新和旧请求完成 | 目录声明稳定，状态真实，新配置不被覆盖 |
| 同契约重启、同 schema 实现升级、移除和撤销 | 重新绑定正确，真正变更和授权检查仍有效 |
| 普通和流式模型请求、原生和按需调用 | tools/system 与已发布消息前缀稳定，工具调用和结果保持配对 |

优先补充和运行相关用例：`tests.test_tool_exposure_memcore`、`tests.test_capability_exposure`、`tests.test_capability_discovery`、`tests.test_capability_adapter_mcp_stdio`、`tests.test_mcp_host_manager`、`tests.test_plugin_active_generation`。协议闭环使用 `tests.test_tool_exposure_wire` 和 `tests.test_tool_exposure_provider_wire`，结合真实安装插件 worker 与 MCP stdio 子进程。只选相关测试，不为这次后端切片强制运行前端构建。

实施验证至少包含 `git diff --check`、受影响 Python 文件编译检查和上述行为检查。结果记录每个切片的通过项、外部服务限制和剩余不确定性。

缓存验收分开看请求结构和上游计量：

- 固定模型与配置，预热后连续对话，确认无能力变化时没有网络预检、目录增量或无效契约通知；检查实际普通与流式协议请求，不用 JSON 键顺序推断 token 前缀。
- 使用上游实际返回的 cached/input token 计算加权命中率，目标仍为稳定连续聊天达到 95% 以上。分别记录部署冷启动、正常压缩、真实能力变更和工具长正文；缺少缓存计量的请求标为未知，不按零或成功计算。
- 目录尾部膨胀主要增加未缓存内容并加快压缩，不等同于每轮重写整个前缀。不能用全天平均数掩盖连续低命中；无法确认的反代因素保留证据，交由真实聊天继续验证。

确认后再按用户要求提交和重启。三个切片分别保持可回滚，不加入新的定时任务、模型总结请求或大量提示词；必要说明沿用现有能力加载和真实失败反馈。

## 六、本轮不做

- 不改插件整批重建的进程管理架构。
- 不重排角色提示词、记忆检索、聊天输出字段或工具轮数。
- 不另建权限注册表、目录记忆库或前端配置面板。
- 不强制删历史、压缩上下文或截断第三方完整工具契约。

完成标准：普通聊天不再因 MCP 短暂故障反复换目录；真正的能力变更只追加该项；同契约重启不再要求模型重新学习工具，执行权限和真实升级判定仍完整有效。
