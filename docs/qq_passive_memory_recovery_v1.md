# QQ 被动记忆恢复与排队边界

本轮在塞西莉亚的失败回执、稳定来源 ID 和持久重试实现上补齐入口与调度边界。基线为宿主 `ca514504`、正常安装的 MemCore `0.1.7`。当前状态：实现已提交，当前实例已重启，连接检查通过；生产消息延迟仍待真实会话观察。

## 恢复行为

1. 空闲被动消息保留原来的直接记录路径；成功不增加一次入队或回读。失败回执和本地写入异常都进入持久恢复。原始失败仍在回执中，入队失败也不会伪装成成功。
2. 有 QQ 消息编号时用同一个来源 ID 重放。没有编号的直接写入提前生成宿主身份；持久队列用已有 inbox ID 生成身份。身份只服务于落库与去重，不新增模型提示。
3. 首次富化后旧库已有记录时，重试回读该记录的正文、时间、指向关系与转发节点，不重新解析转发、下载素材或改写正文。旧库复用原记录，MemCore 复用同一个来源。没有旧库记录时才重新准备。记录范围不一致保留明确错误；临时数据库锁等待仍进入有限重试。
4. 相邻的群观察消息在同一会话、角色、客户端模式、record-only 状态内批量处理，允许不同发言人。真实聊天、不同角色和其他状态构成批量边界。继续使用队列已有的批量数量与字节限制，维护调度和主动观察按批次处理。
5. 保留原修复的最多三次尝试与五秒退避。但等待中的 `passive_memory_record_failed` 可以让后续已就绪消息先处理；新消息唤醒该会话 worker，无须等满退避。正在执行的写入仍在现有会话边界内完成，普通未来可用时间的消息仍是 FIFO 屏障。
6. 被动写入和私聊记忆导入显式设置 `accepts_steering=False`。主人此时发来的消息会重新排队，不会进入没有模型消费者的干预邮箱。普通开发轮仍接受原有主人干预。

这些修改不新增数据库表、全库扫描、模型调用或提示通知；不修改普通压缩阈值、工具轮阈值、冻结的动态提示和工具配对方式。恢复后的记录按现有追加方式进入历史，保留原时间，不倒插到已经发送的前缀中。

相关用例去重后 **178 项通过**。均使用隔离库与替代外部服务；其中使用真实宿主 MemoryStore 和正常安装的 MemCore 验证了部分媒体批次写入与去重，没有调用真实 LLM。

- 重点组 91 项通过：被动回执、恢复、批次、对话所有权、私聊记忆导入和关闭恢复。

- 新增恢复组 16 项，覆盖直接写入失败及异常、恢复入队失败、无 QQ 编号、媒体重启恢复、真实 MemCore 部分批次去重、旧库回读锁、错误范围、批量边界、新消息唤醒、冻结重试批次、普通 FIFO、主人在维护期间重新排队并交付。
- 任务文件 Ruff 与 `git diff --check` 通过。没有前端改动，无需额外构建桌宠。

私聊记忆测试里原有的 JSON 历史断言已经过期；本轮只将它对齐既有的文本历史投影，仍验证原始日语输出保留在回读来源中。没有恢复 JSON 历史渲染。

此前复审中戳一戳用例的旧 `actor_stable_id` 缺席断言不在此次选择的六项路由用例内，没有为全绿移除真实发言人身份，也没有声称全仓测试通过。
