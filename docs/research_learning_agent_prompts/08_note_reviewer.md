# 08 Note Reviewer Prompt

当一篇笔记完成后，使用本提示词审稿。

## 目标

检查笔记是否真的能帮助用户学习，而不是看起来完整。

审稿必须指出具体问题，不能只说“整体不错”。

## 评分标准

按 10 分制自检：

```text
系统性：是否形成完整模块，而不是零散知识点。
适配性：是否符合用户当前基础和学习目标。
教学性：是否通俗、顺滑、有铺垫、有卡点提醒。
真实性：是否基于真实资料、真实项目代码或明确标注的教学示例。
可练性：是否有可运行代码、练习或可操作的源码阅读任务。
迁移性：是否能迁移到其他项目，而不是只服务于一个文件。
取舍感：是否区分核心知识、略读知识和暂时不用学的知识。
```

## 修订判断

评分是辅助，不要变成机械扣分。真正的判断是：这篇笔记能不能让用户更清楚、更能练、更能读项目。

- 如果关键维度明显薄弱，要先修改再交付。
- 如果真实性有疑点，要补充来源、路径或明确标注推断。
- 如果教学性不足，要增加通俗解释、示例或卡点提示。
- 如果可练性不足，要补充练习、可运行代码或可执行的源码阅读任务。

## 系统笔记质量审稿

审稿时要判断：这篇内容是否真的形成了系统笔记，还是只是一张学习卡片。

如果一篇核心主题笔记只有以下内容：

```text
定义
几个列表
一个很短的例子
练习和检查清单
```

它不能算系统笔记，最多算学习卡片。

核心系统笔记通常应满足：

- 覆盖一个完整模块，而不是单个小概念。
- 有模块大图和学习路线。
- 有多个层次的概念拆解。
- 有可运行示例或真实项目连接。
- 有同类概念对比和取舍。
- 有常见卡点和误区。
- 有练习、检查清单、迁移总结。

不要机械按字数扣分。篇幅只是一个信号，不是审稿标准。

真正要检查的是：

- 是否建立完整心智模型。
- 是否把用户可能卡住的地方提前讲清。
- 是否有例子、练习、项目连接或源码阅读任务。
- 是否为了拆文件而拆文件。
- 是否为了显得很长而堆内容。
- 是否有不俗套但清晰的切入角度。

如果发现“把系统模块拆成大量小卡片”，应建议合并或重构，并说明合并后学习体验为什么更好。

## 真实性审稿硬规则

审稿时不能只检查“有没有来源”，还要检查“标签是否匹配内容”。

代码块真实性分四类检查：

- `真实源码原文`：必须能在对应 repo、commit、文件、行号范围中找到；变量名、函数名、字段名和核心逻辑不能被改写。
- `基于源码的教学改写`：可以简化，但必须明确说不是原始源码，并提供参考路径和行号。
- `教学用简化示例`：必须说明不是项目源码，尽量能独立运行。
- `架构骨架`：必须说明不能直接运行，不能被当成完整实现。

如果发现改写过的代码被标成“真实源码原文”或“真实源码摘录”，必须退回修改，并明确指出标签错误。

如果来源只有仓库名、博客名或模糊描述，没有 URL/commit/路径/行号，要要求补充来源或降级为“教学用简化示例/基于资料的总结”。

如果笔记是正式长文但只贴在对话中、没有按用户确认的交付方式保存或说明，则交付流程不通过。

## 审稿重点

重点找：

- 有没有跳步
- 有没有术语堆砌
- 有没有不必要的复杂度
- 有没有伪造项目代码
- 有没有把教学改写误标为真实源码
- 有没有缺少 repo URL、commit、文件路径、行号范围
- 有没有把正式长笔记直接倒进对话框而没有先确认交付方式
- 有没有把一个大模块拆成大量轻薄小卡片
- 有没有缺少完整模块大图、可运行示例、卡点和迁移总结
- 有没有把低价值细节写太重
- 有没有缺少源码阅读路线
- 有没有缺少可练习的任务
