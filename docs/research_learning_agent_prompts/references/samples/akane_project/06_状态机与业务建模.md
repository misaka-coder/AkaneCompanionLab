# 状态机与业务建模

> 很多真实项目不是“输入 -> 输出”这么简单。  
> 它们更像一堆对象在不同状态之间流转。

Akane 里到处都是状态：

```text
提醒 reminder：
pending -> fired / cancelled

附件 attachment：
pending_observation -> ready / failed / cleared

任务工作区 task workspace：
queued -> running -> waiting_user -> completed -> cleaned

视觉观察 vision observation：
pending -> running -> ready / error

流式响应 stream：
stream_start -> turn_start -> speech_chunk -> final -> stream_end

并发保护 guard：
空闲 -> acquire -> active_thinks + 1 -> release -> active_thinks - 1
```

这篇笔记的目标：

```text
学会从真实项目中识别状态机
学会读懂业务对象如何建模
学会用状态、事件、条件、动作去理解复杂流程
```

学习路线：

```text
状态是什么
→ 状态机是什么
→ 状态 / 事件 / 转移 / 条件 / 动作
→ 业务建模是什么
→ 用 dataclass / Enum 建一个小状态机
→ Akane 的提醒状态
→ Akane 的附件状态
→ Akane 的任务工作区状态
→ Akane 的视觉观察状态
→ Akane 的流式事件状态
→ 状态机测试
→ 常见坑
→ 源码阅读路线
```

## 一、为什么要学状态机

你写小脚本时，逻辑通常是：

```text
输入
处理
输出
```

比如：

```python
def add(a, b):
    return a + b
```

但真实业务经常是：

```text
一件事现在做到哪一步了？
它能不能继续？
它是不是在等用户？
它失败了还能不能重试？
它完成后要不要清理？
```

比如“提醒”：

```text
刚创建：pending
到时间：fired
用户取消：cancelled
```

如果不用状态，你可能会写很多零散字段：

```text
is_done
is_cancelled
is_sent
is_deleted
```

然后逻辑越来越乱。

状态机的作用是：

```text
把一个对象可能处于哪些阶段、能怎么流转，明确写出来。
```

---

## 二、状态机是什么

状态机可以拆成五个东西：

```text
state       当前状态
event       触发事件
transition  状态转移
guard       转移条件
action      转移时做的事
```

以提醒为例：

| 概念 | 例子 |
|---|---|
| state | `pending` |
| event | 时间到了 |
| guard | `due_ts <= now_ts` |
| transition | `pending -> fired` |
| action | 设置 `fired_at` |

画成文本：

```text
pending --到时间--> fired
pending --用户取消--> cancelled
fired --不能再触发--> fired
cancelled --不能再触发--> cancelled
```

一句话：

```text
状态机就是“对象在规则约束下切换状态”。
```

---

## 三、状态不是变量名那么简单

状态表示：

```text
这个对象现在处于哪个业务阶段。
```

比如：

```text
pending
running
waiting_user
completed
failed
cleaned
```

这些不是随便起的字符串。

它们背后都有业务含义：

| 状态 | 业务含义 |
|---|---|
| `pending` | 已创建，但还没处理完 |
| `queued` | 已排队，等待开始 |
| `running` | 正在执行 |
| `waiting_user` | 卡住了，需要用户回答 |
| `ready` | 已准备好，可以使用 |
| `failed` | 失败了 |
| `completed` | 完成了 |
| `cleaned` | 已清理，不再作为活跃任务 |

读代码时看到 `status`，不要只想：

```text
这是一个字符串字段。
```

要问：

```text
这个状态代表什么阶段？
它能从哪里来？
它下一步能去哪里？
谁负责改它？
```

## 四、状态机的五个核心问题

读一个业务模块时，先问五个问题：

```text
1. 这个对象有哪些状态？
2. 初始状态是什么？
3. 什么事件会改变状态？
4. 状态改变时会做什么副作用？
5. 哪些状态不能继续改变？
```

以任务工作区为例：

```text
对象：task workspace
初始状态：queued 或 running
事件：更新步骤、登记产物、询问用户、完成、清理
副作用：写 task_workspace_events、返回 stream_events
终态：cleaned
```

这比一行一行读代码更有效。

## 五、业务建模是什么

业务建模就是：

```text
把真实世界里的概念，变成代码里的对象、字段和规则。
```

比如 Akane 的“任务工作区”不是数据库表名那么简单。

它代表：

```text
一次多步任务的临时白板。
```

它包含：

```text
任务目标
当前状态
步骤列表
产物列表
待确认问题
最近事件
后台工坊交接信息
```

这就是业务对象。

代码里可能是 dict：

```python
task = {
    "task_id": "task::123",
    "status": "running",
    "normalized_goal": "把视频下载、转写并整理成 Markdown。",
    "steps": [
        {"title": "下载视频", "status": "done"},
        {"title": "转写音频", "status": "running"},
    ],
    "artifacts": [],
}
```

也可能是 dataclass：

```python
from dataclasses import dataclass


@dataclass
class Task:
    task_id: str
    status: str
    goal: str
```

重点不是用哪种语法。

重点是：

```text
你有没有把业务概念和业务规则表达清楚。
```

## 六、从 if else 到状态机

初学时容易这样写：

```python
def handle_task(task):
    if task["done"]:
        return "已完成"
    if task["failed"]:
        return "失败了"
    if task["waiting"]:
        return "等用户"
    return "处理中"
```

问题：

```text
多个布尔字段可能互相矛盾。
比如 done=True 同时 failed=True。
```

更好的方式：

```python
def handle_task(task):
    status = task["status"]
    if status == "completed":
        return "已完成"
    if status == "failed":
        return "失败了"
    if status == "waiting_user":
        return "等用户"
    if status == "running":
        return "处理中"
    return "未知状态"
```

状态字段的好处：

```text
同一时刻只有一个主状态
业务阶段更清楚
更容易列出允许的流转
更容易测试
```

## 七、用 Enum 写一个小状态机

Python 里可以用 `Enum` 表达状态。

```python
from enum import Enum


class ReminderStatus(str, Enum):
    PENDING = "pending"
    FIRED = "fired"
    CANCELLED = "cancelled"
```

最小提醒状态机：

```python
from dataclasses import dataclass
from enum import Enum


class ReminderStatus(str, Enum):
    PENDING = "pending"
    FIRED = "fired"
    CANCELLED = "cancelled"


@dataclass
class Reminder:
    content: str
    due_ts: int
    status: ReminderStatus = ReminderStatus.PENDING
    fired_at: int = 0


def claim(reminder: Reminder, now_ts: int) -> bool:
    if reminder.status != ReminderStatus.PENDING:
        return False
    if reminder.due_ts > now_ts:
        return False

    reminder.status = ReminderStatus.FIRED
    reminder.fired_at = now_ts
    return True


def cancel(reminder: Reminder, now_ts: int) -> bool:
    if reminder.status != ReminderStatus.PENDING:
        return False

    reminder.status = ReminderStatus.CANCELLED
    reminder.fired_at = now_ts
    return True
```

测试一下：

```python
reminder = Reminder(content="背单词", due_ts=100)

print(reminder.status)
print(claim(reminder, now_ts=120))
print(reminder.status)
print(claim(reminder, now_ts=130))
```

结果：

```text
ReminderStatus.PENDING
True
ReminderStatus.FIRED
False
```

这个例子说明：

```text
pending 可以变 fired
fired 不能再次 fired
```

这就是状态机的约束。

## 八、Akane 里为什么大量用字符串状态

Akane 里很多状态是字符串：

```text
pending
ready
failed
running
waiting_user
completed
cleaned
```

比如：

```python
status="pending_observation"
status="ready"
status="failed"
```

为什么不用全套 Enum？

常见原因：

```text
状态要存进 SQLite
状态要写进 JSON
状态要跨前后端传输
状态要在 prompt 里显示给 LLM
状态可能需要向后兼容
```

字符串状态很适合工程落地。

但代价是：

```text
容易拼错
没有类型检查
状态集合不集中
非法状态可能混进来
```

所以工程里要配合：

```text
常量
normalize 函数
测试
文档
契约
```

Akane 里就有：

```python
ACTIVE_ATTACHMENT_STATUSES = ("ready", "pending_observation", "failed")
READY_ATTACHMENT_STATUSES = ("ready",)
```

这就是把常见状态集中起来。

## 九、Akane 示例一：PublicThinkGuard

真实代码：

```text
companion_v01/public_guard.py
```

它不是传统意义上的业务对象，但它有明显状态：

```text
enabled
_active_thinks
_used_today
_day_key
```

它解决的问题：

```text
限制公共入口同时思考数量
限制每天可使用次数
跨天自动重置 daily counter
```

核心决策对象：

```python
@dataclass(frozen=True)
class GuardDecision:
    allowed: bool
    acquired: bool
    reason: str
    message: str = ""
```

这很漂亮。

因为 `try_acquire()` 不只返回 True / False，而是返回：

```text
是否允许 allowed
是否占用了一个并发名额 acquired
为什么 reason
给用户什么 message
```

状态流转：

```text
disabled
  -> allowed=True, acquired=False

enabled + daily limit reached
  -> allowed=False, reason=daily_limit

enabled + active_thinks >= max
  -> allowed=False, reason=busy

enabled + allowed
  -> active_thinks += 1
  -> used_today += 1
  -> acquired=True

finally release
  -> active_thinks -= 1
```

核心代码简化：

```python
def try_acquire(self) -> GuardDecision:
    if not self.enabled:
        return GuardDecision(allowed=True, acquired=False, reason="disabled")

    with self._lock:
        self._rollover_day_if_needed()

        if self.daily_think_limit > 0 and self._used_today >= self.daily_think_limit:
            return GuardDecision(allowed=False, acquired=False, reason="daily_limit")

        if self.max_concurrent_thinks > 0 and self._active_thinks >= self.max_concurrent_thinks:
            return GuardDecision(allowed=False, acquired=False, reason="busy")

        self._active_thinks += 1
        self._used_today += 1
        return GuardDecision(allowed=True, acquired=True, reason="ok")
```

注意：

```text
try_acquire 成功后，一定要 release。
```

Akane 在 `/think` 里用 `finally`：

```python
finally:
    if guard_decision.acquired:
        public_guard.release()
```

这是状态机中的资源释放问题。

如果忘了 release：

```text
active_thinks 永远不降
系统会误以为一直很忙
后续请求被 429 拦住
```

## 十一、Akane 示例二：Reminder 提醒状态

真实代码：

```text
companion_v01/store.py

claim_due_reminders
list_reminders
cancel_reminder
```

提醒的状态很简单：

```text
pending
fired
cancelled
```

创建提醒：

```python
reminder = {
    "reminder_id": f"reminder::{uuid.uuid4()}",
    "content": str(content),
    "due_ts": int(due_ts),
    "status": "pending",
    "created_at": int(time.time()),
    "fired_at": 0,
}
```

状态图：

```text
pending --到期并被 claim--> fired
pending --用户取消--> cancelled
fired --不能取消 pending--> fired
cancelled --不能触发--> cancelled
```

为什么 `claim_due_reminders` 只查 pending？

```python
WHERE profile_user_id = ?
AND status = 'pending'
AND due_ts <= ?
```

因为：

```text
只有 pending 才能触发。
已经 fired 的不能重复触发。
已经 cancelled 的不能触发。
```

触发后立刻更新：

```python
UPDATE reminders
SET status = 'fired', fired_at = ?
WHERE reminder_id IN (...)
```

这保护了一个重要业务规则：

```text
提醒只能触发一次。
```

取消提醒也只允许取消 pending：

```python
SELECT * FROM reminders
WHERE reminder_id = ?
AND profile_user_id = ?
AND session_id = ?
AND status = 'pending'
```

这表示：

```text
已经 fired 的提醒不能再取消。
```

## 十四、wait_for_attachments_settled

这个函数很像状态机轮询器。

它等待一批附件从：

```text
pending_observation
```

变成：

```text
ready / failed / missing
```

简化逻辑：

```python
while True:
    latest = load_items()
    pending = [
        item_id
        for item_id in ids
        if latest[item_id]["status"] == "pending_observation"
    ]
    if not pending or timeout:
        break
    sleep()

return {
    "ok": not pending_final,
    "ready": ready,
    "failed": failed,
    "pending": pending_final,
    "missing": missing,
}
```

它的设计点：

```text
不直接假设所有附件都会成功。
而是把 ready / failed / pending / missing 分类返回。
```

这很工程化。

因为真实文件处理会遇到：

```text
图片还在识别
下载失败
文件丢失
部分成功
超时未完成
```

状态机让这些情况都有位置放。

## 十七、TaskWorkspaceService 的职责

`TaskWorkspaceService` 是业务服务层。

它不直接处理视频，也不直接调用 LLM。

它负责：

```text
创建任务
更新任务
追加事件
列出任务
构造 prompt context
完成任务
清理任务
生成前台状态摘要
```

创建任务：

```python
def create_task(..., status: str = "queued"):
    task = self.store.add_task_workspace(
        ...
        status=status,
        steps=steps or [],
        artifacts=artifacts or [],
    )
    self.store.append_task_workspace_event(
        task_id=str(task["task_id"]),
        event_type="task_created",
        status="handled",
    )
    return task
```

完成任务：

```python
def complete_task(...):
    updated = self.store.update_task_workspace(
        task_id=task_id,
        status="completed",
        artifacts=artifacts,
        completed_at=effective_ts,
    )
    if updated:
        self.append_event(
            task_id=task_id,
            event_type="task_completed",
            status="handled",
        )
    return updated
```

清理任务：

```python
def cleanup_task(...):
    updated = self.store.update_task_workspace(
        task_id=task_id,
        status="cleaned",
        metadata=metadata,
        cleaned_at=effective_ts,
    )
    self.store.append_task_workspace_event(
        task_id=task_id,
        event_type="task_cleaned",
        status="handled",
    )
    return updated
```

模式：

```text
改 task 的状态
追加一条 task event
返回更新后的 task
```

这是业务系统很常见的设计：

```text
主表记录当前状态
事件表记录发生过什么
```

这表示：


## 二十一、从步骤推导任务状态

Akane 里有：

```python
def _derive_task_status_from_steps(self, steps):
    statuses = {step["status"] for step in steps}
    if "waiting_user" in statuses:
        return "waiting_user"
    if "running" in statuses:
        return "running"
    if statuses and statuses.issubset({"done", "completed"}):
        return "completed"
    return "running"
```

意思：

```text
只要有一步等待用户，整个任务就 waiting_user。
只要有一步运行，整个任务就 running。
如果所有步骤都 done，整个任务 completed。
否则默认 running。
```

这是业务规则。

不是语法技巧。

你可以把它画成优先级：

```text
waiting_user 最高
running 其次
all done -> completed
其他 -> running
```

读这类函数时要问：

```text
为什么 waiting_user 优先级最高？
```

因为只要任务需要用户回答，前台就必须停下来问用户。

## 二十二、Akane 示例五：VisionObservation 视觉观察状态

真实代码：

```text
companion_v01/vision_service.py
```

视觉观察状态：

```text
pending
running
ready
error
```

状态图：

```text
pending --后台线程开始--> running
running --分析成功--> ready
running --分析失败--> error
error --允许重试--> pending / running
pending/running --超时--> 允许重试
ready --复用缓存--> ready
```

核心逻辑：

```python
def _can_reuse_existing_observation(self, observation):
    status = observation["status"]
    if status == "ready":
        return True
    if status in {"pending", "running"}:
        return not self._should_retry_observation(observation)
    return False
```

这表示：

```text
ready 可以直接复用。
pending/running 如果还没过期，就继续等，不要重复开任务。
error 不复用，可以重试。
```

重试判断：

```python
if status == "error":
    return True
if status == "pending":
    return age_seconds >= 15
if status == "running":
    return age_seconds >= running_stale_seconds
```

这是状态机里的超时规则。

## 二十三、后台任务和 in-flight 集合

视觉观察里还有：

```python
self._jobs_in_flight.add(job_key)
```

作用：

```text
同一个目标不要重复启动多个后台观察线程。
```

简化逻辑：

```python
with self._lock:
    if job_key in self._jobs_in_flight:
        return pending
    self._jobs_in_flight.add(job_key)

thread.start()
```

线程结束时：

```python
finally:
    with self._lock:
        self._jobs_in_flight.discard(job_key)
```

这和 `PublicThinkGuard` 很像：

```text
进入时登记
结束时释放
必须放在 finally
```

状态机不仅是业务状态，也包括资源状态：

```text
这个 job 是否正在飞行中
这个请求是否占用了并发槽位
这个任务是否还处于活跃列表
```

## 二十七、状态机测试怎么写

状态机测试的基本套路：

```text
1. 准备一个初始状态
2. 触发一个事件
3. 检查状态变成什么
4. 检查副作用是否发生
5. 检查非法重复操作是否被挡住
```

以提醒为例：

```python
def test_claim_due_reminders_marks_rows_as_fired(self):
    reminder = store.add_reminder(...)

    claimed = store.claim_due_reminders(now_ts=120)

    self.assertEqual(claimed[0]["status"], "fired")

    claimed_again = store.claim_due_reminders(now_ts=130)
    self.assertEqual(claimed_again, [])
```

它测了：

```text
pending -> fired
fired 不能再次被 claim
```

以任务工作区为例：

```python
created_result = handler.execute(action="create")
self.assertEqual(service.get_task(task_id)["status"], "running")

ask_result = handler.execute(action="ask_user")
self.assertEqual(service.get_task(task_id)["status"], "waiting_user")

complete_result = handler.execute(action="complete")
self.assertEqual(service.get_task(task_id)["status"], "completed")

cleanup_result = handler.execute(action="cleanup")
self.assertEqual(service.get_task(task_id)["status"], "cleaned")
```

它测的是完整流转：

```text
running -> waiting_user -> completed -> cleaned
```

## 二十八、自己写一个小任务状态机

下面是一个可运行的迷你任务模型。

```python
from dataclasses import dataclass, field
from enum import Enum


class TaskStatus(str, Enum):
    QUEUED = "queued"
    RUNNING = "running"
    WAITING_USER = "waiting_user"
    COMPLETED = "completed"
    FAILED = "failed"
    CLEANED = "cleaned"


@dataclass
class Task:
    task_id: str
    goal: str
    status: TaskStatus = TaskStatus.QUEUED
    steps: list[dict] = field(default_factory=list)
    artifacts: list[dict] = field(default_factory=list)
    pending_question: str = ""
    events: list[str] = field(default_factory=list)


def start_task(task: Task) -> None:
    if task.status != TaskStatus.QUEUED:
        raise ValueError(f"只有 queued 可以 start，当前是 {task.status}")
    task.status = TaskStatus.RUNNING
    task.events.append("task_started")


def ask_user(task: Task, question: str) -> None:
    if task.status not in {TaskStatus.RUNNING, TaskStatus.QUEUED}:
        raise ValueError(f"当前状态不能 ask_user: {task.status}")
    task.status = TaskStatus.WAITING_USER
    task.pending_question = question
    task.events.append("user_question")


def complete_task(task: Task, artifacts: list[dict] | None = None) -> None:
    if task.status not in {TaskStatus.RUNNING, TaskStatus.WAITING_USER}:
        raise ValueError(f"当前状态不能 complete: {task.status}")
    task.status = TaskStatus.COMPLETED
    task.artifacts.extend(artifacts or [])
    task.pending_question = ""
    task.events.append("task_completed")


def cleanup_task(task: Task) -> None:
    if task.status != TaskStatus.COMPLETED:
        raise ValueError(f"只有 completed 可以 cleanup，当前是 {task.status}")
    task.status = TaskStatus.CLEANED
    task.events.append("task_cleaned")


task = Task(task_id="task::001", goal="把视频整理成 Markdown")
print(task.status)

start_task(task)
print(task.status)

ask_user(task, "要不要保留时间轴？")
print(task.status, task.pending_question)

complete_task(task, artifacts=[{"id": "gen_001", "kind": "md"}])
print(task.status, task.artifacts)

cleanup_task(task)
print(task.status)
print(task.events)
```

输出：

```text
TaskStatus.QUEUED
TaskStatus.RUNNING
TaskStatus.WAITING_USER 要不要保留时间轴？
TaskStatus.COMPLETED [{'id': 'gen_001', 'kind': 'md'}]
TaskStatus.CLEANED
['task_started', 'user_question', 'task_completed', 'task_cleaned']
```

这个例子体现了：

```text
状态
允许的流转
非法流转报错
事件记录
产物记录
```

这就是 Akane 任务工作区的缩小版。

## 二十九、用表驱动状态机

如果状态流转很多，可以用表。

```python
ALLOWED_TRANSITIONS = {
    "queued": {"running", "waiting_user", "failed"},
    "running": {"waiting_user", "completed", "failed"},
    "waiting_user": {"running", "completed", "failed"},
    "completed": {"cleaned"},
    "failed": {"cleaned", "running"},
    "cleaned": set(),
}


def can_transition(current: str, target: str) -> bool:
    return target in ALLOWED_TRANSITIONS.get(current, set())


def transition(task: dict, target: str) -> dict:
    current = str(task.get("status") or "queued")
    if not can_transition(current, target):
        raise ValueError(f"不能从 {current} 变成 {target}")

    updated = dict(task)
    updated["status"] = target
    return updated


task = {"task_id": "task::1", "status": "queued"}
task = transition(task, "running")
task = transition(task, "completed")
task = transition(task, "cleaned")
print(task)
```

好处：

```text
允许的流转集中在一张表
新增状态时更容易检查
测试可以遍历这张表
```

什么时候用表？

```text
状态多
非法流转多
规则比较稳定
需要清楚地审查业务流程
```

什么时候不用？

```text
状态很少
业务动作本身比状态复杂
每个动作副作用差异很大
```

Akane 现在很多地方是”动作函数 + 字符串状态”的方式。

这是务实的。

> **附：社区里的状态机库** — Python 有一个流行的第三方库叫 `transitions`（`pip install transitions`），能用装饰器声明状态和流转规则，自动校验非法跳转。Akane 没有用它，但如果你以后自己设计复杂状态机，值得了解。核心思想和你这篇学的一样：state / transition / guard / action。

## 三十、状态机常见坑

### 30.1 状态太散

坏味道：

```text
is_running
is_done
is_failed
is_waiting
is_deleted
```

这些布尔值可能互相打架。

更好：

```text
status = running / completed / failed / waiting_user / cleaned
```

### 30.2 没有终态

如果没有终态，数据会永远活跃。

比如任务完成后不清理：

```text
prompt context 里一直出现旧任务
Akane 可能反复提旧事情
前端工作区越来越乱
```

所以需要：

```text
completed
cleaned
archived
deleted
```

### 30.3 状态改了但事件没记

如果只改状态，不记录事件：

```text
现在知道任务完成了
但不知道为什么完成、谁完成、带了什么产物
```

所以任务工作区会：

```text
update task status
append task event
```

### 30.4 事件有了但状态没改

反过来也不行。

如果记录了 `task_completed` 事件，但 task.status 还在 `running`：

```text
查询当前任务时仍然显示 running
前端状态不一致
LLM prompt context 混乱
```

### 30.5 忘记释放资源状态

比如：

```text
try_acquire 成功后忘记 release
jobs_in_flight 添加后忘记 discard
```

应该用：

```python
try:
    ...
finally:
    release()
```

### 30.6 允许非法跳转

比如：

```text
cleaned -> running
fired -> pending
cancelled -> fired
```

这些通常不应该随便允许。

如果确实需要恢复，要有明确动作：

```text
retry
reopen
restore
```

## 三十五、我自己的复述

状态机不是很玄的概念。

它就是在问：

```text
这个东西现在处于什么阶段？
什么事情会让它进入下一个阶段？
进入下一个阶段时要做什么？
哪些阶段不能再回头？
```

Akane 里很多复杂感都来自状态：

```text
附件不是“有/没有”，而是 pending_observation、ready、failed。
提醒不是“有/没有”，而是 pending、fired、cancelled。
任务不是“做/没做”，而是 queued、running、waiting_user、completed、cleaned。
流式响应不是“一次返回”，而是一串 event type。
```

所以读 Akane 的时候，不要只盯着函数。

要顺着状态走：

```text
它从哪里创建？
创建时是什么状态？
谁会改状态？
改状态时有没有写事件？
前端或 LLM 会不会看到这个状态？
测试有没有保护这条流转？
```

能这样读代码，你就能从“看一堆文件”变成“看一套业务系统”。
