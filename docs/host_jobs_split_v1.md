## 调用链与状态归属

`bot_runtime.py` 继续从 `engine.store.db_path` 创建一个 `HostJobStore`，并传给工具、执行、工作流、子代理及插件 Task 运行时。管理路由继续通过原入口和既有运行时发出控制请求；完成通知仍通过既有事件路由、会话队列及交付层发送。

各职责通过同一实例组合，不新增数据库、状态副本或任务调度器。内部只使用明确的包内导入，没有反向导入兼容入口或运行时方法注入。所有事务正文的原始边界保留：领取、控制、恢复等仍在原 `BEGIN IMMEDIATE` 中完成读取和更新，交付回执继续使用原子的条件更新。原有表结构、升级规则、幂等键、领取令牌和完成事件身份保留。

`status=paused` 表示尚未领取的任务被暂停，可以直接取消。已经运行的协作暂停仍是 `status=running`、`control_state=paused`，领取令牌由原执行方持有；撤销或停止请求不能据此宣称任务已终止。丢失的运行任务仍标记结果未知并隔离旧令牌，不自动重放可能已经产生外部效果的工作。

## 同轮复现与修复

1. 现有恢复测试在修改前已失败：插件代次被撤销后，旧令牌仍能提交成功结果。现在插件 Task 的成功、失败、重排和取消确认均在原事务内校验代次撤销标记，拒绝旧代次修改任务事实。运行中的任务保持原领取状态，真实丢失领取时再进入结果未知。宿主工具、执行、工作流和子代理仍能报告实际结果；取消请求只阻止重试，不伪造已取消。
2. 撤销尚未领取的暂停任务时，原逻辑只改了终态，漏掉取消标志、结束时间和完成通知状态。现在这些字段与终态一起更新，按原 `completion_mode`/`memory_mode` 决定静默或待通知，不需要重开数据库才能补上通知。
3. 发出停止请求后，协作暂停可能覆盖 `stopping`，使原执行方无法确认取消。现在暂停和恢复都保留正在取消的状态并返回 `host_job_cancel_requested`，不清除原领取令牌。
4. 结果未知的任务即使能力或代次已经撤销，直接恢复仍能将其重排。现在返回 `host_job_scope_revoked`，保留原失败事实、撤销原因和完成事件，不使失效任务再次可领取。
5. 产物 JSON 允许 `NaN`/无穷值，与载荷、结果和检查点的严格 JSON 校验不一致。现在产物也拒绝这些值，返回原有 `host_job_artifacts_not_json_safe`，失败验证不消耗领取令牌。对象与通用值共用同一编码实现，移除重复的序列化分支。
6. 连接初始化设置失败发生在清理范围之外，可能漏关已打开的数据库连接。现在初始化和事务都处于同一清理范围，设置、正文或提交失败后释放句柄。

新增 `tests/test_host_job_boundaries.py` 的 14 项检查使用真实临时 SQLite、两个独立 Store 实例和并发线程；只在连接初始化和行映射失败处注入故障。覆盖暂停撤销的各入口及通知策略、旧代次结果隔离、宿主真实结果、取消优先级、撤销后恢复、无效产物、并发幂等/领取和事务回滚。修复前，10 个测试方法复现相关失败；没有修改旧测试的断言。
