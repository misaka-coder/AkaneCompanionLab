# 最终回复恢复与双语语音交付

## 现象和原因

QQ 配置为同时发送文字和语音，部分工具任务完成后仍只收到文字。记录里有
`json_external_text` 恢复和 `speech_units_required`：交付帧失去了朗读用的
`utterances`。旧恢复反馈只要求把正文放进 `speech`，没有沿用当前客户端字段。

另一条路径是流式输出中途断开：旧逻辑把已经交付的中文句子合回最终正文，
却没有保留这些句子对应的 `say/style/emotion`。QQ 在最终帧合成整段音频，
因此会漏掉前半段；桌宠已经逐句播放，需要避免最终帧再次播放它们。

## 实现

- 恢复反馈沿用当前客户端字段；删除 `engine.py` 中覆盖已导入文案的重复定义。
- JSON 边界单次扫描，未闭合外层对象里的子对象不再误判为对象外的散文。
- 待执行 `tool_call` 只检查根对象字段，完整及截断输出采用同一语义；
  正文的代码示例、嵌套元数据都不会触发误拦截。
- 一个请求保留自身真实流式事件中已闭合的显示文字及已提交的朗读句子。
  重试的尾段合入最终 `utterances`，原始语气和表情随之保留；重复前缀只留一份。
  缺少译文的部分保持 `say: null`，不补造日语，也不新增翻译请求。
- QQ 只补发未发送的文字，用完整最终 `utterances` 合成一次语音。
  桌宠及 VoiceCore 用已交付序列的位置去重最终前缀，保留新的重复句子。
  正常成功路径保持原输出字段，纯文字回复不会被改成双语协议。

这份保留记录只存在于当前请求，既不扫描记忆库，也不修改工具结果与记忆落库机制。
恢复仍仅修改请求尾部；系统提示、工具定义和缓存键保持不变。

## 验证和边界

- 七个相关 Python 模块共 99 项检查：97 项通过，两项已有基线失败，无新增失败。
  覆盖真实 JSON 流式解析器、流式/非流式恢复、截断朗读、多次中断、混合前缀、
  QQ 单次合成、VoiceCore 事件交付和请求隔离。
- 浏览器检查调用实际 chat/bubble/TTS 控制器和 HTMLAudioElement；覆盖两个恢复
  阶段和完整最终帧、重复 final/final_ui、旧请求取消以及表情同步。
- 前端构建及 `git diff --check` 通过。缓存前缀由请求参数一致性断言验证，
  未把真实服务商缓存命中率称为本轮已经验收。
- 合成的 59,714 字符截断样本：旧分类耗时约 326 ms，本轮七次中位数约 3.5 ms。
  分类只在根边界尝试解码，不随内部对象数量反复扫描前缀。
- 两条基线失败：不可达服务重试次数旧断言、33 工具样本未计入
  `turn_progress` 的旧事件断言；不为本次修复改动这些行为。
- 实际 Irodori 服务此前返回连接失败，在线 QQ 音频听感尚未验收。
  浏览器和交付检查控制合成传输，不等于真实声线合成成功。

没有额外系统提示清单，也没有为该个案增加工具能力限制。
