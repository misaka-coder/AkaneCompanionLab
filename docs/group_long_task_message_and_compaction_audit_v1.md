## 2. 开发过程中未 @ 的文字和图片怎样进入记忆

1. 正常接收的群友消息携带发言人、原始时间、消息来源和接收对象。未 @ 的内容走被动记录入口，不自动成为一次必须回答的聊天。
2. 当前会话忙、队列尚有工作，或者内容需要附件/转发处理时，先写入持久队列。当前轮释放会话后再追加到 MemCore，保留原始时间，但不按时间戳插回已有上下文前缀。
3. 空闲时的普通文字可直接入库。图片先登记附件，下载和处理走后台；被动入口使用 `observe_images=False`。入库的图片引用不等于已经理解图片内容。
4. 被动文字入库后，可以按该群的主动搭话模式成为观察依据。87 群目前为 `adaptive`；会话忙或有排队工作时，主动搭话不会抢先执行。图片本身不新建主动搭话轮，可以补充已有观察轮的图片依据。主动观察也允许模型保持安静。
5. 机器人自己发送的 OneBot 事件由协议接收层忽略，不作为新的群友消息回灌。

依据：`qq_gateway_runtime/inbound.py`、`qq_passive_messages.py`、`qq_session_queue.py`、`qq_attention_runtime.py`、`attachment_ingest_runtime/api.py`；自发事件判断在安装的 `channelcore_onebot/admission.py`。

### 已验证的被动批量入口缺口

生产使用 `DurableSessionWorkQueue`。QQ 注册的批量键只有 `completion_batch_key`，该函数只识别后台任务完成通知，对 `passive` 返回空字符串。旧内存队列支持的被动批量策略没有接入持久队列。

实际已有 `record_passive_qq_messages` 批量记录实现，但连续被动消息仍逐条领取、逐条记录、逐次安排维护。隔离测试加入 12 条兼容的被动消息，实际只领取 1 条。下午任务结束后有 72 条被动消息逐条处理。

这会增加开销，但不能用它单独解释图片项近四分钟的耗时。改进应恢复连续被动项的批量处理，复用现有批次边界，不新增收集等待、不越过真实聊天消息。

### 另一处成功状态不够准确

`desktop_care_pet.py::_record_passive_qq_message` 在旧记录写入后调用 MemCore，但顶层固定返回 `ok=True`，即使嵌套的 `memcore` 返回失败。批量汇总和队列因此可能误认该消息已正常进入模型记忆。

这是代码边界风险；Olivia 的实例已找到真实 MemCore 记录，不属于这个情况。修复时需保留旧记录证据，并保证重试不会重复写入，不能只改报错文字。

## 3. 只有入库工作的会话也可能误接收主人干预

被动批次使用 `turn_coordinator.hold(profile_user_id, session_id)`，没有声明模型消费者；私人记忆导入使用 `turn_kind="private_memory_import"`。两者仍会注册一个 `running` 的活动会话。

主人输入可以绕过普通队列领取顺序，随后被 `offer_steer(... allow_other_actor=True)` 接收。上述维护操作没有模型来消费干预信箱，而 `hold` 退出时直接移除活动会话，未处理的干预不会立即归还队列。

隔离测试验证了这两个入口：输入被接收，退出后信箱不存在；持久记录仍为 `claimed`，下一次普通领取返回 `busy`。租约到期后再次领取可以恢复，但到期本身不保证立即重新调度，因此可能表现为暂时不回复或等待下一次调度/重启。

**这是可复现的代码风险，不是下午已证明的根因。** 下午 17:20:26 的那条聊天只有一次领取，没有证据命中这个边界；当时的几分钟等待不能归给它。

建议：只有真正运行模型并消费干预的轮接收干预；入库、记忆导入期间的新输入走原来的持久队列。保留主人对真实开发任务的干预能力。

## 4. 开发结束后的压缩顺序和阈值

完成轮的实际顺序为：

```text
提交最终答复并关闭轮
  → 按冻结策略把工具轨迹收成可回读的历史投影（代码处理）
  → 调度后台摘要维护
  → 计算剩余未摘要记录的投影 token
  → 达到阈值时选取旧的完整轮，生成阶段摘要并提交
```

原始工具调用和结果仍保留用于检索/回读；判断阈值使用已收起的投影，不使用这些完整原文的历史总 token。剩余聊天正文和短工具骨架仍会计入。阶段摘要另有数量归并规则，不把摘要本身算进 raw 的触发值。

当前运行配置为：raw 触发线 **48000**，每批计划移除约 **3.2 万**投影 token（触发线 × 0.67）。从旧到新选择完整、已结束的轮，保留近期尾部，不拆开原生工具调用配对。计划量不是硬切片大小，完整大轮可以超过计划量。一次调用处理一批 raw，再检查阶段摘要是否需要归并；新入库/完成轮可以合并调度后续检查。一个尚未结束的巨大开发轮，不会仅因 token 多就被强行截成普通摘要。

下午该开发轮（主要是工具轨迹）的完整投影约 **241857** 估算 token，结束后投影约 **47450**。它单独略低于 48000，但前面还存在未摘要的群消息。

| 摘要提交时间 | 未摘要 raw 投影变化 | 含可见记忆的投影变化 |
| --- | --- | --- |
| 17:18:35 | 67259 → 47450 | 78598 → 59642 |
| 17:23:33 | 49528 → 2078 | 61720 → 15086 |

第一批收起较早的前文，留下最近的开发大轮。之后新消息让剩余 raw 再次越过触发线；第二批包含该轮的 291 条来源记录。两批均成功，不能将本次归为摘要失败一直堆积。上述数字为 MemCore 估算，不等同于模型供应商账单。

注意：触发阈值的投影大小与摘要模型实际收到的正文不是同一口径。后台完成通知当前仍被归入叙事事件，会携带操作输出进入摘要输入；具体重建结果见第 8 节。

依据：安装 SDK 的 `memory_system.py::complete_turn`、`compaction.py::_summarize_timeline` / `_compaction_due_target`，以及产品层 `memcore_integration/compaction.py`。

## 5. 压缩是否会挡聊天，压缩中收到新消息怎么办

通常为后台操作，聊天不等待摘要模型完成。会话的压缩锁防止两次压缩同时执行，不是普通读写必须获取的聊天锁。压缩只提交它选定的快照，提交时校验来源版本和轮状态；后来追加的消息不属于该批，仍作为未摘要记录保留。快照失效也有明确状态和有限重取，不通过静默删除输入来完成压缩。

隔离测试让真实 MemCore 压缩链的摘要提供者停在等待状态；在其返回前，新消息入库约 **3.5 ms**，上下文读取约 **4.1 ms**。随后摘要成功提交，新消息仍存在且未被摘要。这验证机制允许并发，不代表大生产库永远没有锁竞争。

另有请求预算的同步压缩路径：只有 `LLM_AUTO_COMPACT_TOKEN_LIMIT > 0` 且实际请求超出该预算才进入。当前运行后端的该值为 **0**，此路径关闭；不能据此反推下午运行时的历史设置。当前后台摘要 worker 为 1，多个会话摘要会排队，但普通聊天没有等待这个 worker 的要求。

数据库读取和原子提交仍有共享锁和 I/O；压缩“在后台”不能证明这些本地步骤没有耗时。只读抽查发现摘要提交的投影 hash 校验，在未全部命中 settled 记录时会读取该会话的历史投影账本；当前 87 群约 6.9 万行，单次读取及解析约 **2.64 秒**。这是后续值得缩小扫描范围的点，尚不足以解释几分钟等待，也没有修改安装的 SDK。

| 实际阶段 | 观察 |

| Olivia 聊天轮打开 → 首次聊天请求审计 | 17:14:11 → 17:18:08，约 **237 秒** |
| 一条被动图片队列项领取 → 完成 | 17:19:23 → 17:23:21，约 **238 秒** |

前两项分别在模型请求构建前和被动处理链中发生，不能全算为聊天模型生成耗时。第三项确实等待前方被动内容处理。

那条图片的附件在 16:23:10 已为 ready，标记未进行视觉分析，因此也不能将 238 秒直接解释成图片下载。下午的分阶段旧日志已不完整，无法可靠拆出当时的附件注册、会话执行权、记忆入库、上下文投影和预算阶段各占多少。现有耗时边界已覆盖这些步骤，下一次自然出现长任务后的延迟时可以继续定位；不为复现而向群内投放消息。

本次只读检查时，87 群持久队列没有剩余的 `queued` / `claimed` 项。此前成功压缩与当前无积压，不意味着上面的边界问题已经解决。

## 7. 建议的后续切片与验证

1. 修复只有入库/导入工作的活动会话误接收干预；验证输入立即保持可调度，不依赖租约到期。
2. 补齐持久队列的被动批量入口；验证连续文字/图片、真实 @ 的批次边界、失败和重试，不添加等待窗。
3. 让被动记录的成功结果与 MemCore 真正写入一致，并验证可重复恢复。
4. 单独讨论主人普通聊天与另一位群友聊天的合并语义；保留开发期间的主人干预，不靠关键词猜任务或追加冗长提示。
5. 用已有阶段耗时确定剩余慢点，再决定是否改账本查询；不把扩大阈值、提高 worker 数或加超时当成根因修复。

隔离探针：`.tmp/group_compaction_concurrency_probe.py`。四组输出通过，使用临时数据库、假摘要提供者和假时钟，没有模型网络请求或生产写入。生产数据读取使用 SQLite `mode=ro`，运行配置通过本机只读设置目录接口确认。探针留在忽略目录，不作为生产功能或提交内容。

## 8. 开发轮实际用于生成聊天摘要的内容

继续核对该轮的聊天阶段摘要来源：291 条来源中，264 条为工具 action / observation，归入代码生成的操作摘要；27 条进入聊天摘要。按落库来源和当前 SDK 的同一渲染函数只读重建如下，未重新请求模型，也不是历史网络请求抓包：

| 输入类别 | 条数 | 渲染后的字符数 |
| --- | --- | --- |
| 用户消息（切换模型后的询问及开发任务） | 2 | 500 |
| 助手中途进度 | 5 | 777 |
| 助手最终交付正文 | 1 | 401 |
| 后台任务完成通知 `event.task.work.completed` | 19 | 80731 |

加上条目间换行，待摘要正文共 **82435 字符 / 21904 估算 token**。再加摘要用户模板及上一条聊天摘要参考（272 字符），摘要用户消息共 **82851 字符 / 22236 估算 token**，不包含摘要系统提示和角色身份。

系统部分使用 MemCore 专用摘要规则和角色身份，要求日记式回忆、固定 JSON 字段、事实归属及时间锚定，并补充群聊/私人交流的场景区分。它不是主聊天的整套系统提示或工具目录。

正文使用源消息的语义文本、发言人/接收对象/时间/来源来渲染，不把最终输出的整份语音 JSON 作为聊天正文重放。只有紧邻前文的一条聊天阶段摘要作为参考，不加入操作摘要作为参考。

后台完成通知来自 `engine_services/turn_completions.py::collect_turn_completions`，将 `result.followup_context` 保存为事件的 `result`。SDK 的 `_is_episode_entry` 排除 action、observation 和 material，却没有将这类 intermediate 任务完成事件归入操作摘要。因此工具结果可以通过通知包装重新进入聊天摘要，其中包括测试输出和错误堆栈；本轮最长一条约 **16828 字符**。正常对话和进度合计约 1700 字符，通知占正文约 98%。

这修正了“工具记录由代码收起”的适用范围：直接工具调用和返回是如此，当前后台通知中的输出尚未被同样分流。下一步需要保留任务终态、必要交付结论和回读证据，避免将完整操作输出作为聊天摘要正文；不应将所有事件一概删除。

重建探针：`.tmp/render_development_summary_input_probe.py`，仅使用只读连接、无构造初始化的 SDK 对象和纯渲染函数。

## 9. 重建时进一步定位的参考摘要慢查询

`SQLiteMemoryStore.get_previous_episodic_summary` 的查询在共享 store 锁内执行。本轮只读重建的完整调用出现长等待。查询计划显示，其用于排序的 `MAX(seq_no)` 子查询先扫描当前会话的消息，再遍历候选摘要的 JSON 来源 ID；当前该会话有 248 条聊天阶段摘要。这是本地摘要准备步骤，发生在摘要模型请求之前。

只读对比同一 SDK SQL 的连接顺序：原查询在限定 4 秒的探针中仍未完成；仅让该排序子查询按 JSON 中的来源 ID 查消息主键，约 **517 ms** 得到上一条聊天摘要。改变连接顺序的试验没有移除归属校验或缩小候选范围；没有创建索引、修改数据库或修改安装 SDK。

这是已经定位的本地慢查询，不能再把所有长等待都视为摘要供应商耗时。共享锁也意味着其它 MemCore 读写可能等待该查询。它与下午两段长等待的形态吻合，但历史日志没有对应阶段的精确时间，尚不能断言那两段全部由它造成。

探针：`.tmp/probe_previous_summary_query_readonly.py`。4 秒仅为只读诊断的中止界限，不是建议给生产摘要新增超时。下一步应在 MemCore 的受维护源码中修查询，并验证前文选择、来源归属、回填和空态语义，不在 site-packages 留临时补丁。
